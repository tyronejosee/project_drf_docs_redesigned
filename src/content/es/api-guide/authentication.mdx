# Autenticación

> La autenticación debe ser conectable.
>
> &mdash; Jacob Kaplan-Moss, ["Peores prácticas de REST"][cite]

La autenticación es el mecanismo de asociar una petición entrante con un conjunto de credenciales de identificación, como el usuario del que proviene la petición, o el token con el que fue firmada. Las políticas de [permisos] y [limitación] pueden entonces usar esas credenciales para determinar si la petición debe ser permitida.

REST framework proporciona varios esquemas de autenticación listos para usar, y también te permite implementar esquemas personalizados.

La autenticación siempre se ejecuta al principio de la vista, antes de que ocurran las verificaciones de permisos y limitación, y antes de que se permita proceder a cualquier otro código.

La propiedad `request.user` normalmente se establecerá en una instancia de la clase `User` del paquete `contrib.auth`.

La propiedad `request.auth` se usa para cualquier información de autenticación adicional, por ejemplo, puede usarse para representar un token de autenticación con el que fue firmada la petición.

---

**Nota:** No olvides que **la autenticación por sí sola no permitirá ni denegará una petición entrante**, simplemente identifica las credenciales con las que se realizó la petición.

Para información sobre cómo configurar las políticas de permisos para tu API, por favor consulta la [documentación de permisos][permission].

---

## Cómo se determina la autenticación

Los esquemas de autenticación siempre se definen como una lista de clases. REST framework intentará autenticarse con cada clase en la lista, y establecerá `request.user` y `request.auth` usando el valor de retorno de la primera clase que se autentique exitosamente.

Si ninguna clase se autentica, `request.user` se establecerá en una instancia de `django.contrib.auth.models.AnonymousUser`, y `request.auth` se establecerá en `None`.

El valor de `request.user` y `request.auth` para peticiones no autenticadas puede modificarse usando las configuraciones `UNAUTHENTICATED_USER` y `UNAUTHENTICATED_TOKEN`.

## Configuración del esquema de autenticación

Los esquemas de autenticación predeterminados pueden establecerse globalmente, usando la configuración `DEFAULT_AUTHENTICATION_CLASSES`. Por ejemplo:

```python
REST_FRAMEWORK = {
    'DEFAULT_AUTHENTICATION_CLASSES': [
        'rest_framework.authentication.BasicAuthentication',
        'rest_framework.authentication.SessionAuthentication',
    ]
}
```

También puedes establecer el esquema de autenticación por vista o por viewset,
usando las vistas basadas en clases `APIView`.

```python
from rest_framework.authentication import SessionAuthentication, BasicAuthentication
from rest_framework.permissions import IsAuthenticated
from rest_framework.response import Response
from rest_framework.views import APIView

class ExampleView(APIView):
    authentication_classes = [SessionAuthentication, BasicAuthentication]
    permission_classes = [IsAuthenticated]

    def get(self, request, format=None):
        content = {
            'user': str(request.user),  # Instancia de `django.contrib.auth.User`.
            'auth': str(request.auth),  # None
        }
        return Response(content)
```

O, si estás usando el decorador `@api_view` con vistas basadas en funciones:

```python
@api_view(['GET'])
@authentication_classes([SessionAuthentication, BasicAuthentication])
@permission_classes([IsAuthenticated])
def example_view(request, format=None):
    content = {
        'user': str(request.user),  # Instancia de `django.contrib.auth.User`.
        'auth': str(request.auth),  # None
    }
    return Response(content)
```

## Respuestas No Autorizado y Prohibido

Cuando una petición no autenticada es denegada por permisos, hay dos códigos de error diferentes que pueden ser apropiados.

- [HTTP 401 No Autorizado][http401]
- [HTTP 403 Permiso Denegado][http403]

Las respuestas HTTP 401 siempre deben incluir un encabezado `WWW-Authenticate`, que instruye al cliente cómo autenticarse. Las respuestas HTTP 403 no incluyen el encabezado `WWW-Authenticate`.

El tipo de respuesta que se usará depende del esquema de autenticación. Aunque múltiples esquemas de autenticación pueden estar en uso, solo un esquema puede usarse para determinar el tipo de respuesta. **La primera clase de autenticación establecida en la vista se usa al determinar el tipo de respuesta**.

Ten en cuenta que cuando una petición puede autenticarse exitosamente, pero aún así es denegada la permisión para realizar la petición, en cuyo caso siempre se usará una respuesta `403 Permiso Denegado`, independientemente del esquema de autenticación.

## Django 5.1+ `LoginRequiredMiddleware`

Si estás ejecutando Django 5.1+ y usas el [`LoginRequiredMiddleware`][login-required-middleware], ten en cuenta que todas las vistas de DRF están excluidas de este middleware. Esto es porque la autenticación en DRF se basa en clases de autenticación y permisos, que pueden determinarse después de que se haya aplicado el middleware. Además, cuando la petición no está autenticada, el middleware redirige al usuario a la página de inicio de sesión, lo cual no es adecuado para peticiones de API, donde es preferible devolver un código de estado 401.

REST framework ofrece un mecanismo equivalente para vistas de DRF a través de las configuraciones globales, `DEFAULT_AUTHENTICATION_CLASSES` y `DEFAULT_PERMISSION_CLASSES`. Deben cambiarse en consecuencia si necesitas forzar que las peticiones de API estén iniciadas.

## Configuración específica de Apache mod_wsgi

Ten en cuenta que si despliegas en [Apache usando mod_wsgi][mod_wsgi_official], el encabezado de autorización no se pasa a una aplicación WSGI por defecto, ya que se asume que la autenticación será manejada por Apache, en lugar de a nivel de aplicación.

Si estás desplegando en Apache, y usas cualquier autenticación no basada en sesiones, necesitarás configurar explícitamente mod_wsgi para pasar los encabezados requeridos a la aplicación. Esto puede hacerse especificando la directiva `WSGIPassAuthorization` en el contexto apropiado y estableciéndola en `'On'`.

```txt
# esto puede ir en la configuración del servidor, host virtual, directorio o .htaccess
WSGIPassAuthorization On
```

# Referencia de API

## BasicAuthentication

Este esquema de autenticación usa [Autenticación Básica HTTP][basicauth], firmada contra el nombre de usuario y contraseña de un usuario. La autenticación básica generalmente solo es apropiada para pruebas.

Si se autentica exitosamente, `BasicAuthentication` proporciona las siguientes credenciales:

- `request.user` será una instancia de Django `User`.
- `request.auth` será `None`.

Las respuestas no autenticadas que son denegadas por permisos resultarán en una respuesta `HTTP 401 No Autorizado` con un encabezado WWW-Authenticate apropiado. Por ejemplo:

```http
WWW-Authenticate: Basic realm="api"
```

**Nota:** Si usas `BasicAuthentication` en producción, debes asegurar que tu API solo esté disponible sobre `https`. También debes asegurar que tus clientes de API siempre volverán a solicitar el nombre de usuario y contraseña al iniciar sesión, y nunca almacenarán esos detalles en almacenamiento persistente.

## TokenAuthentication

---

**Nota:** La autenticación por token proporcionada por Django REST framework es una implementación bastante simple.

Para una implementación que permite más de un token por usuario, tiene detalles de implementación de seguridad más estrictos, y soporta expiración de tokens, por favor consulta el paquete de terceros [Django REST Knox][django-rest-knox].

---

Este esquema de autenticación usa un esquema simple de Autenticación HTTP basado en tokens. La autenticación por token es apropiada para configuraciones cliente-servidor, como clientes de escritorio nativos y móviles.

Para usar el esquema `TokenAuthentication`, necesitarás [configurar las clases de autenticación](#configuración-del-esquema-de-autenticación) para incluir `TokenAuthentication`, y adicionalmente incluir `rest_framework.authtoken` en tu configuración `INSTALLED_APPS`:

```python
INSTALLED_APPS = [
    ...
    'rest_framework.authtoken'
]
```

Asegúrate de ejecutar `manage.py migrate` después de cambiar tu configuración.

La aplicación `rest_framework.authtoken` proporciona migraciones de base de datos de Django.

También necesitarás crear tokens para tus usuarios:

```python
from rest_framework.authtoken.models import Token

token = Token.objects.create(user=...)
print(token.key)
```

Para que los clientes se autentiquen, la clave del token debe incluirse en el encabezado HTTP `Authorization`. La clave debe estar precedida por el literal de cadena "Token", con espacio en blanco separando las dos cadenas. Por ejemplo:

```http
Authorization: Token 9944b09199c62bcf9418ad846dd0e4bbdfc6ee4b
```

_Si quieres usar una palabra clave diferente en el encabezado, como `Bearer`, simplemente subclasifica `TokenAuthentication` y establece la variable de clase `keyword`._

Si se autentica exitosamente, `TokenAuthentication` proporciona las siguientes credenciales:

- `request.user` será una instancia de Django `User`.
- `request.auth` será una instancia de `rest_framework.authtoken.models.Token`.

Las respuestas no autenticadas que son denegadas por permisos resultarán en una respuesta `HTTP 401 No Autorizado` con un encabezado WWW-Authenticate apropiado. Por ejemplo:

```http
WWW-Authenticate: Token
```

La herramienta de línea de comandos `curl` puede ser útil para probar APIs autenticadas por token. Por ejemplo:

```bash
curl -X GET http://127.0.0.1:8000/api/example/ -H 'Authorization: Token 9944b09199c62bcf9418ad846dd0e4bbdfc6ee4b'
```

---

**Nota:** Si usas `TokenAuthentication` en producción, debes asegurar que tu API solo esté disponible sobre `https`.

### Generación de Tokens

#### Usando señales

Si quieres que cada usuario tenga un Token generado automáticamente, simplemente puedes capturar la señal `post_save` del User.

```python
from django.conf import settings
from django.db.models.signals import post_save
from django.dispatch import receiver
from rest_framework.authtoken.models import Token

@receiver(post_save, sender=settings.AUTH_USER_MODEL)
def create_auth_token(sender, instance=None, created=False, **kwargs):
    if created:
        Token.objects.create(user=instance)
```

Ten en cuenta que querrás asegurar que coloques este fragmento de código en un módulo `models.py` instalado, o en algún otro lugar que será importado por Django al iniciar.

Si ya has creado algunos usuarios, puedes generar tokens para todos los usuarios existentes así:

```python
from django.contrib.auth.models import User
from rest_framework.authtoken.models import Token

for user in User.objects.all():
    Token.objects.get_or_create(user=user)
```

#### Exponiendo un endpoint de API

Cuando usas `TokenAuthentication`, puedes querer proporcionar un mecanismo para que los clientes obtengan un token dado el nombre de usuario y contraseña. REST framework proporciona una vista incorporada para proporcionar este comportamiento. Para usarla, añade la vista `obtain_auth_token` a tu URLconf:

```python
from rest_framework.authtoken import views
urlpatterns += [
    path('api-token-auth/', views.obtain_auth_token)
]
```

Ten en cuenta que la parte de la URL del patrón puede ser lo que quieras usar.

La vista `obtain_auth_token` devolverá una respuesta JSON cuando campos válidos de `username` y `password` se envíen a la vista usando datos de formulario o JSON:

```json
{
  "token": "9944b09199c62bcf9418ad846dd0e4bbdfc6ee4b"
}
```

Ten en cuenta que la vista `obtain_auth_token` predeterminada usa explícitamente peticiones y respuestas JSON, en lugar de usar las clases de renderizador y parser predeterminadas en tu configuración.

Por defecto, no hay permisos o limitación aplicados a la vista `obtain_auth_token`. Si deseas aplicar limitación, necesitarás sobrescribir la clase de vista,
e incluirlas usando el atributo `throttle_classes`.

Si necesitas una versión personalizada de la vista `obtain_auth_token`, puedes hacerlo subclasificando la clase de vista `ObtainAuthToken`, y usándola en tu configuración de URLs en su lugar.

Por ejemplo, puedes devolver información adicional del usuario más allá del valor del `token`:

```python
from rest_framework.authtoken.views import ObtainAuthToken
from rest_framework.authtoken.models import Token
from rest_framework.response import Response

class CustomAuthToken(ObtainAuthToken):

    def post(self, request, *args, **kwargs):
        serializer = self.serializer_class(data=request.data,
                                            context={'request': request})
        serializer.is_valid(raise_exception=True)
        user = serializer.validated_data['user']
        token, created = Token.objects.get_or_create(user=user)
        return Response({
            'token': token.key,
            'user_id': user.pk,
            'email': user.email
        })
```

Y en tu `urls.py`:

```python
urlpatterns += [
    path('api-token-auth/', CustomAuthToken.as_view())
]
```

#### Con el admin de Django

También es posible crear Tokens manualmente a través de la interfaz de administración. En caso de que estés usando una base de usuarios grande, recomendamos que apliques un monkey patch a la clase `TokenAdmin` para personalizarla a tus necesidades, más específicamente declarando el campo `user` como `raw_field`.

`your_app/admin.py`:

```python
from rest_framework.authtoken.admin import TokenAdmin

TokenAdmin.raw_id_fields = ['user']
```

#### Usando el comando manage.py de Django

Desde la versión 3.6.4 es posible generar un token de usuario usando el siguiente comando:

```bash
./manage.py drf_create_token <username>
```

este comando devolverá el token de API para el usuario dado, creándolo si no existe:

```bash
Generated token 9944b09199c62bcf9418ad846dd0e4bbdfc6ee4b for user user1
```

En caso de que quieras regenerar el token (por ejemplo si ha sido comprometido o filtrado) puedes pasar un parámetro adicional:

```bash
./manage.py drf_create_token -r <username>
```

## SessionAuthentication

Este esquema de autenticación usa el backend de sesión predeterminado de Django para autenticación. La autenticación de sesión es apropiada para clientes AJAX que se ejecutan en el mismo contexto de sesión que tu sitio web.

Si se autentica exitosamente, `SessionAuthentication` proporciona las siguientes credenciales:

- `request.user` será una instancia de Django `User`.
- `request.auth` será `None`.

Las respuestas no autenticadas que son denegadas por permisos resultarán en una respuesta `HTTP 403 Prohibido`.

Si estás usando una API estilo AJAX con SessionAuthentication, necesitarás asegurarte de incluir un token CSRF válido para cualquier llamada a método HTTP "inseguro", como peticiones `PUT`, `PATCH`, `POST` o `DELETE`. Consulta la [documentación de CSRF de Django][csrf-ajax] para más detalles.

**Advertencia**: Siempre usa la vista de inicio de sesión estándar de Django al crear páginas de inicio de sesión. Esto asegurará que tus vistas de inicio de sesión estén protegidas adecuadamente.

La validación CSRF en REST framework funciona ligeramente diferente del Django estándar debido a la necesidad de soportar tanto autenticación basada en sesiones como no basada en sesiones en las mismas vistas. Esto significa que solo las peticiones autenticadas requieren tokens CSRF, y las peticiones anónimas pueden enviarse sin tokens CSRF. Este comportamiento no es adecuado para vistas de inicio de sesión, que siempre deben tener validación CSRF aplicada.

## RemoteUserAuthentication

Este esquema de autenticación te permite delegar la autenticación a tu servidor web, que establece la variable de entorno `REMOTE_USER`.

Para usarlo, debes tener `django.contrib.auth.backends.RemoteUserBackend` (o una subclase) en tu configuración `AUTHENTICATION_BACKENDS`. Por defecto, `RemoteUserBackend` crea objetos `User` para nombres de usuario que no existen ya. Para cambiar esto y otro comportamiento, consulta la [documentación de Django](https://docs.djangoproject.com/en/stable/howto/auth-remote-user/).

Si se autentica exitosamente, `RemoteUserAuthentication` proporciona las siguientes credenciales:

- `request.user` será una instancia de Django `User`.
- `request.auth` será `None`.

Consulta la documentación de tu servidor web para información sobre cómo configurar un método de autenticación, por ejemplo:

- [Apache Authentication How-To](https://httpd.apache.org/docs/2.4/howto/auth.html)
- [NGINX (Restricting Access)](https://docs.nginx.com/nginx/admin-guide/security-controls/configuring-http-basic-authentication/)

# Autenticación personalizada

Para implementar un esquema de autenticación personalizado, subclasifica `BaseAuthentication` y sobrescribe el método `.authenticate(self, request)`. El método debe devolver una tupla de dos elementos de `(user, auth)` si la autenticación tiene éxito, o `None` en caso contrario.

En algunas circunstancias, en lugar de devolver `None`, puedes querer lanzar una excepción `AuthenticationFailed` desde el método `.authenticate()`.

Típicamente, el enfoque que debes tomar es:

- Si no se intenta la autenticación, devuelve `None`. Cualquier otro esquema de autenticación también en uso seguirá siendo verificado.
- Si se intenta la autenticación pero falla, lanza una excepción `AuthenticationFailed`. Se devolverá una respuesta de error inmediatamente, independientemente de cualquier verificación de permisos, y sin verificar ningún otro esquema de autenticación.

También _puedes_ sobrescribir el método `.authenticate_header(self, request)`. Si se implementa, debe devolver una cadena que se usará como el valor del encabezado `WWW-Authenticate` en una respuesta `HTTP 401 No Autorizado`.

Si el método `.authenticate_header()` no se sobrescribe, el esquema de autenticación devolverá respuestas `HTTP 403 Prohibido` cuando una petición no autenticada sea denegada el acceso.

---

**Nota:** Cuando tu autenticador personalizado es invocado por las propiedades `.user` o `.auth` del objeto de petición, puedes ver un `AttributeError` relanzado como `WrappedAttributeError`. Esto es necesario para evitar que la excepción original sea suprimida por el acceso a la propiedad externa. Python no reconocerá que el `AttributeError` se origina en tu autenticador personalizado y en su lugar asumirá que el objeto de petición no tiene una propiedad `.user` o `.auth`. Estos errores deben ser corregidos o manejados de otra manera por tu autenticador.

---

## Ejemplo

El siguiente ejemplo autenticará cualquier petición entrante como el usuario dado por el nombre de usuario en un encabezado de petición personalizado llamado 'X-USERNAME'.

```python
from django.contrib.auth.models import User
from rest_framework import authentication
from rest_framework import exceptions

class ExampleAuthentication(authentication.BaseAuthentication):
    def authenticate(self, request):
        username = request.META.get('HTTP_X_USERNAME')
        if not username:
            return None

        try:
            user = User.objects.get(username=username)
        except User.DoesNotExist:
            raise exceptions.AuthenticationFailed('No such user')

        return (user, None)
```

# Paquetes de terceros

Los siguientes paquetes de terceros también están disponibles.

## django-rest-knox

La biblioteca [Django-rest-knox][django-rest-knox] proporciona modelos y vistas para manejar autenticación basada en tokens de una manera más segura y extensible que el esquema incorporado TokenAuthentication - pensando en Aplicaciones de Una Sola Página y clientes móviles. Proporciona tokens por cliente, y vistas para generarlos cuando se proporciona alguna otra autenticación (usualmente autenticación básica), para eliminar el token (proporcionando un cierre de sesión forzado por servidor) y para eliminar todos los tokens (cierra sesión en todos los clientes en los que un usuario ha iniciado sesión).

## Django OAuth Toolkit

El paquete [Django OAuth Toolkit][django-oauth-toolkit] proporciona soporte para OAuth 2.0 y funciona con Python 3.4+. El paquete es mantenido por [jazzband][jazzband] y usa la excelente [OAuthLib][oauthlib]. El paquete está bien documentado, y bien soportado y es actualmente nuestro **paquete recomendado para soporte de OAuth 2.0**.

### Instalación y configuración

Instala usando `pip`.

```bash
pip install django-oauth-toolkit
```

Añade el paquete a tu `INSTALLED_APPS` y modifica tu configuración de REST framework.

```python
INSTALLED_APPS = [
    ...
    'oauth2_provider',
]

REST_FRAMEWORK = {
    'DEFAULT_AUTHENTICATION_CLASSES': [
        'oauth2_provider.contrib.rest_framework.OAuth2Authentication',
    ]
}
```

Para más detalles, consulta la documentación [Django REST framework - Getting started][django-oauth-toolkit-getting-started].

## Django REST framework OAuth

El paquete [Django REST framework OAuth][django-rest-framework-oauth] proporciona soporte tanto para OAuth1 como OAuth2 para REST framework.

Este paquete fue previamente incluido directamente en REST framework pero ahora es soportado y mantenido como un paquete de terceros.

### Instalación y configuración

Instala el paquete usando `pip`.

```bash
pip install djangorestframework-oauth
```

Para detalles sobre configuración y uso, consulta la documentación de Django REST framework OAuth para [autenticación][django-rest-framework-oauth-authentication] y [permisos][django-rest-framework-oauth-permissions].

## JSON Web Token Authentication

JSON Web Token es un estándar bastante nuevo que puede usarse para autenticación basada en tokens. A diferencia del esquema incorporado TokenAuthentication, la autenticación JWT no necesita usar una base de datos para validar un token. Un paquete para autenticación JWT es [djangorestframework-simplejwt][djangorestframework-simplejwt] que proporciona algunas características así como una aplicación de lista negra de tokens conectable.

## Hawk HTTP Authentication

La biblioteca [HawkREST][hawkrest] se construye sobre la biblioteca [Mohawk][mohawk] para permitirte trabajar con peticiones y respuestas firmadas por [Hawk][hawk] en tu API. [Hawk][hawk] permite que dos partes se comuniquen de forma segura entre sí usando mensajes firmados por una clave compartida. Se basa en [Autenticación de acceso MAC HTTP][mac] (que se basó en partes de [OAuth 1.0][oauth-1.0a]).

## HTTP Signature Authentication

HTTP Signature (actualmente un [borrador IETF][http-signature-ietf-draft]) proporciona una manera de lograr autenticación de origen e integridad de mensajes para mensajes HTTP. Similar al [esquema de Firma HTTP de Amazon][amazon-http-signature], usado por muchos de sus servicios, permite autenticación sin estado, por petición. [Elvio Toccalino][etoccalino] mantiene el paquete [djangorestframework-httpsignature][djangorestframework-httpsignature] (obsoleto) que proporciona un mecanismo de Autenticación de Firma HTTP fácil de usar. Puedes usar la versión actualizada del fork de [djangorestframework-httpsignature][djangorestframework-httpsignature], que es [drf-httpsig][drf-httpsig].

## Djoser

La biblioteca [Djoser][djoser] proporciona un conjunto de vistas para manejar acciones básicas como registro, inicio de sesión, cierre de sesión, restablecimiento de contraseña y activación de cuenta. El paquete funciona con un modelo de usuario personalizado y usa autenticación basada en tokens. Esta es una implementación REST lista para usar del sistema de autenticación de Django.

## django-rest-auth / dj-rest-auth

Esta biblioteca proporciona un conjunto de endpoints de API REST para registro, autenticación (incluyendo autenticación de redes sociales), restablecimiento de contraseña, recuperación y actualización de detalles de usuario, etc. Al tener estos endpoints de API, tus aplicaciones cliente como AngularJS, iOS, Android, y otras pueden comunicarse con tu sitio backend de Django independientemente a través de APIs REST para gestión de usuarios.

Actualmente hay dos forks de este proyecto:

- [Django-rest-auth][django-rest-auth] es el proyecto original, [pero actualmente no recibe actualizaciones](https://github.com/Tivix/django-rest-auth/issues/568).
- [Dj-rest-auth][dj-rest-auth] es un fork más nuevo del proyecto.

## drf-social-oauth2

[Drf-social-oauth2][drf-social-oauth2] es un framework que te ayuda a autenticarte con principales proveedores de oauth2 sociales, como Facebook, Google, Twitter, Orcid, etc. Genera tokens de manera JWT con una configuración fácil.

## drfpasswordless

[drfpasswordless][drfpasswordless] añade soporte sin contraseña (inspirado en Medium, Square Cash) al esquema TokenAuthentication de Django REST Framework. Los usuarios inician sesión y se registran con un token enviado a un punto de contacto como una dirección de correo electrónico o un número de móvil.

## django-rest-authemail

[django-rest-authemail][django-rest-authemail] proporciona una interfaz API RESTful para registro de usuario y autenticación. Las direcciones de correo electrónico se usan para autenticación, en lugar de nombres de usuario. Los endpoints de API están disponibles para registro, verificación de correo de registro, inicio de sesión, cierre de sesión, restablecimiento de contraseña, verificación de restablecimiento de contraseña, cambio de correo, verificación de cambio de correo, cambio de contraseña, y detalles de usuario. Se incluye un proyecto de ejemplo completamente funcional e instrucciones detalladas.

## Django-Rest-Durin

[Django-Rest-Durin][django-rest-durin] está construido con la idea de tener una biblioteca que haga autenticación por token para múltiples clientes de API Web/CLI/Móvil a través de una interfaz pero permite diferente configuración de token para cada Cliente de API que consume la API. Proporciona soporte para múltiples tokens por usuario a través de modelos personalizados, vistas, permisos que funcionan con Django-Rest-Framework. El tiempo de expiración del token puede ser diferente por cliente de API y es personalizable a través de la Interfaz de Administración de Django.

Más información puede encontrarse en la [Documentación](https://django-rest-durin.readthedocs.io/en/latest/index.html).

## django-pyoidc

[dango-pyoidc][django_pyoidc] añade soporte para autenticación OpenID Connect (OIDC). Esto te permite delegar la gestión de usuarios a un Proveedor de Identidad, que puede usarse para implementar Single-Sign-On (SSO). Proporciona soporte para la mayoría de casos de uso, como personalizar cómo se mapea la información de token a modelos de usuario, usar audiencias OIDC para control de acceso, etc.

Más información puede encontrarse en la [Documentación](https://django-pyoidc.readthedocs.io/latest/index.html).
