# Excepciones

> Las excepciones... permiten organizar el manejo de errores de forma clara en un punto central o de alto nivel dentro de la estructura del programa.
>
> &mdash; Doug Hellmann, [Python Exception Handling Techniques][cite]

## Manejo de excepciones en vistas de REST framework

Las vistas de REST framework gestionan diversas excepciones y devuelven respuestas de error apropiadas.

Las excepciones manejadas son:

- Subclases de `APIException` lanzadas dentro de REST framework.
- La excepción `Http404` de Django.
- La excepción `PermissionDenied` de Django.

En cada caso, REST framework devolverá una respuesta con un código de estado y un tipo de contenido apropiados. El cuerpo de la respuesta incluirá cualquier detalle adicional sobre la naturaleza del error.

La mayoría de las respuestas de error incluirán una clave `detail` en el cuerpo de la respuesta.

Por ejemplo, la siguiente solicitud:

```http
DELETE http://api.example.com/foo/bar HTTP/1.1
Accept: application/json
```

Podría recibir una respuesta de error indicando que el método `DELETE` no está permitido en ese recurso:

```http
HTTP/1.1 405 Method Not Allowed
Content-Type: application/json
Content-Length: 42
```

```json
{ "detail": "Method 'DELETE' not allowed." }
```

Los errores de validación se manejan de forma ligeramente distinta e incluirán los nombres de los campos como claves en la respuesta. Si el error de validación no es específico de un campo en particular, usará la clave "non_field_errors" o el valor de cadena configurado en la opción `NON_FIELD_ERRORS_KEY`.

Un ejemplo de error de validación podría verse así:

```http
HTTP/1.1 400 Bad Request
Content-Type: application/json
Content-Length: 94
```

```json
{
  "amount": ["A valid integer is required."],
  "description": ["This field may not be blank."]
}
```

## Manejo de excepciones personalizado

Puede implementar un manejo de excepciones personalizado creando una función handler que convierta las excepciones lanzadas en sus vistas de API en objetos `Response`. Esto le permite controlar el estilo de las respuestas de error usadas por su API.

La función debe aceptar un par de argumentos: el primero es la excepción a manejar y el segundo es un diccionario que contiene contexto adicional, como la vista que se está procesando. La función handler debe devolver un objeto `Response`, o `None` si la excepción no puede ser manejada. Si el handler devuelve `None`, la excepción volverá a lanzarse y Django devolverá una respuesta HTTP 500 estándar ('server error').

Por ejemplo, puede que quiera asegurarse de que todas las respuestas de error incluyan el código de estado HTTP en el cuerpo de la respuesta, de la siguiente manera:

```http
HTTP/1.1 405 Method Not Allowed
Content-Type: application/json
Content-Length: 62
```

```json
{
  "status_code": 405,
  "detail": "Method 'DELETE' not allowed."
}
```

Para alterar el estilo de la respuesta, podría escribir el siguiente handler de excepción personalizado:

```python
from rest_framework.views import exception_handler

def custom_exception_handler(exc, context):
    # Llama primero al handler de excepciones por defecto de REST framework
    # para obtener la respuesta de error estándar.
    response = exception_handler(exc, context)

    # Ahora añade el código de estado HTTP a la respuesta.
    if response is not None:
        response.data['status_code'] = response.status_code

    return response
```

El argumento `context` no es utilizado por el handler por defecto, pero puede ser útil si el handler personalizado necesita información adicional, como la vista en proceso, que puede obtenerse como `context['view']`.

El handler de excepciones también debe configurarse en sus settings, usando la clave `EXCEPTION_HANDLER`. Por ejemplo:

```python
REST_FRAMEWORK = {
    'EXCEPTION_HANDLER': 'my_project.my_app.utils.custom_exception_handler'
}
```

Si no se especifica, la opción `'EXCEPTION_HANDLER'` por defecto es el handler estándar proporcionado por REST framework:

```python
REST_FRAMEWORK = {
    'EXCEPTION_HANDLER': 'rest_framework.views.exception_handler'
}
```

Tenga en cuenta que el handler de excepciones solo se llamará para respuestas generadas por excepciones lanzadas. No se usará para respuestas que la vista devuelva directamente, como las respuestas `HTTP_400_BAD_REQUEST` que devuelven las vistas genéricas cuando la validación del serializer falla.

# Referencia de la API

## APIException

**Firma:** `APIException()`

La **clase base** para todas las excepciones lanzadas dentro de una clase `APIView` o `@api_view`.

Para proporcionar una excepción personalizada, herede de `APIException` y establezca los atributos `.status_code`, `.default_detail` y `.default_code` en la clase.

Por ejemplo, si su API depende de un servicio externo que a veces puede no estar disponible, podría implementar una excepción para la respuesta HTTP "503 Service Unavailable" así:

```python
from rest_framework.exceptions import APIException

class ServiceUnavailable(APIException):
    status_code = 503
    default_detail = 'Service temporarily unavailable, try again later.'
    default_code = 'service_unavailable'
```

#### Inspección de excepciones de API

Hay varias propiedades disponibles para inspeccionar el estado de una excepción de API. Puede usarlas para crear manejo de excepciones personalizado en su proyecto.

Los atributos y métodos disponibles son:

- `.detail` - Devuelve la descripción textual del error.
- `.get_codes()` - Devuelve el identificador de código del error.
- `.get_full_details()` - Devuelve tanto la descripción textual como el identificador de código.

En la mayoría de los casos el detalle del error será un elemento simple:

```bash
>>> print(exc.detail)
You do not have permission to perform this action.
>>> print(exc.get_codes())
permission_denied
>>> print(exc.get_full_details())
{'message':'You do not have permission to perform this action.','code':'permission_denied'}
```

En el caso de errores de validación, el detalle del error será una lista o un diccionario de elementos:

```bash
>>> print(exc.detail)
{"name":"This field is required.","age":"A valid integer is required."}
>>> print(exc.get_codes())
{"name":"required","age":"invalid"}
>>> print(exc.get_full_details())
{"name":{"message":"This field is required.","code":"required"},"age":{"message":"A valid integer is required.","code":"invalid"}}
```

## ParseError

**Firma:** `ParseError(detail=None, code=None)`

Se lanza si la solicitud contiene datos malformados al acceder a `request.data`.

Por defecto, esta excepción produce una respuesta con el código de estado HTTP "400 Bad Request".

## AuthenticationFailed

**Firma:** `AuthenticationFailed(detail=None, code=None)`

Se lanza cuando una solicitud entrante incluye credenciales de autenticación incorrectas.

Por defecto, esta excepción produce una respuesta con el código de estado HTTP "401 Unauthenticated", pero también puede resultar en una respuesta "403 Forbidden", dependiendo del esquema de autenticación en uso. Consulte la [documentación de autenticación][authentication] para más detalles.

## NotAuthenticated

**Firma:** `NotAuthenticated(detail=None, code=None)`

Se lanza cuando una solicitud no autenticada no supera las comprobaciones de permisos.

Por defecto, esta excepción produce una respuesta con el código de estado HTTP "401 Unauthenticated", pero también puede resultar en una respuesta "403 Forbidden", dependiendo del esquema de autenticación en uso. Consulte la [documentación de autenticación][authentication] para más detalles.

## PermissionDenied

**Firma:** `PermissionDenied(detail=None, code=None)`

Se lanza cuando una solicitud autenticada no supera las comprobaciones de permisos.

Por defecto, esta excepción produce una respuesta con el código de estado HTTP "403 Forbidden".

## NotFound

**Firma:** `NotFound(detail=None, code=None)`

Se lanza cuando un recurso no existe en la URL dada. Esta excepción es equivalente a la excepción estándar `Http404` de Django.

Por defecto, esta excepción produce una respuesta con el código de estado HTTP "404 Not Found".

## MethodNotAllowed

**Firma:** `MethodNotAllowed(method, detail=None, code=None)`

Se lanza cuando una solicitud entrante no tiene un método manejador en la vista.

Por defecto, esta excepción produce una respuesta con el código de estado HTTP "405 Method Not Allowed".

## NotAcceptable

**Firma:** `NotAcceptable(detail=None, code=None)`

Se lanza cuando una solicitud entrante incluye una cabecera `Accept` que no puede ser satisfecha por ninguno de los renderizadores disponibles.

Por defecto, esta excepción produce una respuesta con el código de estado HTTP "406 Not Acceptable".

## UnsupportedMediaType

**Firma:** `UnsupportedMediaType(media_type, detail=None, code=None)`

Se lanza si no hay parsers que puedan manejar el tipo de contenido de los datos de la solicitud al acceder a `request.data`.

Por defecto, esta excepción produce una respuesta con el código de estado HTTP "415 Unsupported Media Type".

## Throttled

**Firma:** `Throttled(wait=None, detail=None, code=None)`

Se lanza cuando una solicitud entrante no supera las comprobaciones de limitación (throttling).

Por defecto, esta excepción produce una respuesta con el código de estado HTTP "429 Too Many Requests".

## ValidationError

**Firma:** `ValidationError(detail=None, code=None)`

La excepción `ValidationError` es ligeramente distinta de las demás clases `APIException`:

- El argumento `detail` puede ser una lista o un diccionario de detalles del error, y también puede ser una estructura de datos anidada. Al usar un diccionario, puede especificar errores a nivel de campo durante la validación a nivel de objeto en el método `validate()` de un serializer. Por ejemplo: `raise serializers.ValidationError({'name': 'Please enter a valid name.'})`
- Por convención debe importar el módulo `serializers` y usar la forma totalmente cualificada `ValidationError` para diferenciarla de la excepción de validación incorporada de Django. Por ejemplo: `raise serializers.ValidationError('This field must be an integer value.')`

La clase `ValidationError` debe usarse para la validación de serializers y campos, y por las clases validadoras. También se lanza cuando se llama a `serializer.is_valid` con el argumento `raise_exception`:

```python
serializer.is_valid(raise_exception=True)
```

Las vistas genéricas usan el flag `raise_exception=True`, lo que significa que puede anular el estilo de las respuestas de error de validación globalmente en su API. Para ello, use un handler de excepciones personalizado, como se describió arriba.

Por defecto, esta excepción produce una respuesta con el código de estado HTTP "400 Bad Request".

# Vistas de error genéricas

Django REST Framework proporciona dos vistas de error adecuadas para ofrecer respuestas JSON genéricas para `500` Server Error y `400` Bad Request. (Las vistas de error por defecto de Django ofrecen respuestas HTML, que pueden no ser apropiadas para una aplicación solo API.)

Úselas según la [documentación de Django sobre personalización de vistas de error][django-custom-error-views].

## `rest_framework.exceptions.server_error`

Devuelve una respuesta con código de estado `500` y tipo de contenido `application/json`.

Configúrelo como `handler500`:

```python
handler500 = 'rest_framework.exceptions.server_error'
```

## `rest_framework.exceptions.bad_request`

Devuelve una respuesta con código de estado `400` y tipo de contenido `application/json`.

Configúrelo como `handler400`:

```python
handler400 = 'rest_framework.exceptions.bad_request'
```

## Paquetes de terceros

Los siguientes paquetes de terceros también están disponibles.

### DRF Standardized Errors

El paquete [drf-standardized-errors][drf-standardized-errors] proporciona un handler de excepciones que genera el mismo formato para todas las respuestas 4xx y 5xx. Es un reemplazo plug-and-play del handler por defecto y permite personalizar el formato de la respuesta de error sin reescribir todo el handler. El formato estandarizado de respuesta de error es más fácil de documentar y de manejar para los consumidores de la API.
