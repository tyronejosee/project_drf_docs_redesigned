# Campos del serializer

> Cada campo en una clase Form es responsable no solo de validar datos, sino también de "limpiarlos" &mdash; normalizarlos a un formato consistente.
>
> &mdash; [Documentación de Django][cite]

Los campos del serializer manejan la conversión entre valores primitivos y tipos de datos internos. También se encargan de validar los valores de entrada, así como de recuperar y establecer los valores de sus objetos principales.

---

**Nota:** Los campos del serializer se declaran en `fields.py`, pero por convención debes importarlos usando `from rest_framework import serializers` y referirte a los campos como `serializers.<NombreCampo>`.

---

## Argumentos principales

Cada constructor de clase de campo del serializer toma al menos estos argumentos. Algunas clases Field toman argumentos adicionales específicos del campo, pero los siguientes siempre deben ser aceptados:

### `read_only`

Los campos de solo lectura se incluyen en la salida de la API, pero no deben incluirse en la entrada durante las operaciones de creación o actualización. Cualquier campo 'read_only' que se incluya incorrectamente en la entrada del serializer será ignorado.

Establece esto en `True` para asegurar que el campo se use al serializar una representación, pero no se use al crear o actualizar una instancia durante la deserialización.

Por defecto es `False`

### `write_only`

Establece esto en `True` para asegurar que el campo puede usarse al actualizar o crear una instancia, pero no se incluye al serializar la representación.

Por defecto es `False`

### `required`

Normalmente se lanzará un error si un campo no se proporciona durante la deserialización.
Establece en `false` si este campo no necesita estar presente durante la deserialización.

Establecer esto en `False` también permite que el atributo del objeto o la clave del diccionario se omita de la salida al serializar la instancia. Si la clave no está presente, simplemente no se incluirá en la representación de salida.

Por defecto es `True`. Si estás usando [Model Serializer](https://www.django-rest-framework.org/api-guide/serializers/#modelserializer) el valor por defecto será `False` si has especificado `blank=True` o `default` o `null=True` en tu campo en tu `Model`.

### `default`

Si se establece, esto da el valor predeterminado que se usará para el campo si no se proporciona ningún valor de entrada. Si no se establece, el comportamiento predeterminado es no poblar el atributo en absoluto.

El `default` no se aplica durante las operaciones de actualización parcial. En el caso de actualización parcial, solo los campos que se proporcionan en los datos entrantes tendrán un valor validado devuelto.

Puede establecerse en una función u otro callable, en cuyo caso el valor se evaluará cada vez que se use. Cuando se llame, no recibirá argumentos. Si el callable tiene un atributo `requires_context = True`, entonces el campo del serializer se pasará como argumento.

Por ejemplo:

```python
class CurrentUserDefault:
    """
    Puede aplicarse como un valor `default=...` en un campo del serializer.
    Devuelve el usuario actual.
    """
    requires_context = True

    def __call__(self, serializer_field):
        return serializer_field.context['request'].user
```

Al serializar la instancia, se usará el valor predeterminado si el atributo del objeto o la clave del diccionario no está presente en la instancia.

Ten en cuenta que establecer un valor `default` implica que el campo no es requerido. Incluir tanto el argumento `default` como el argumento `required` es inválido y lanzará un error.

### `allow_null`

Normalmente se lanzará un error si `None` se pasa a un campo del serializer. Establece este argumento de palabra clave en `True` si `None` debe considerarse un valor válido.

Ten en cuenta que, sin un `default` explícito, establecer este argumento en `True` implicará un valor `default` de `null` para la salida de serialización, pero no implica un valor predeterminado para la deserialización de entrada.

Por defecto es `False`

### `source`

El nombre del atributo que se usará para poblar el campo. Puede ser un método que solo toma un argumento `self`, como `URLField(source='get_absolute_url')`, o puede usar notación de puntos para recorrer atributos, como `EmailField(source='user.email')`.

Al serializar campos con notación de puntos, puede ser necesario proporcionar un valor `default` si algún objeto no está presente o está vacío durante el recorrido de atributos. Ten cuidado con posibles problemas n+1 al usar el atributo source si estás accediendo a un modelo orm relacional. Por ejemplo:

```python
class CommentSerializer(serializers.Serializer):
    email = serializers.EmailField(source="user.email")
```

Este caso requeriría que el objeto de usuario se obtenga de la base de datos cuando no está precargado. Si no se desea eso, asegúrate de usar los métodos `prefetch_related` y `select_related` apropiadamente. Para más información sobre los métodos consulta la [documentación de django][django-docs-select-related].

El valor `source='*'` tiene un significado especial, y se usa para indicar que el objeto completo debe pasarse al campo. Esto puede ser útil para crear representaciones anidadas, o para campos que requieren acceso al objeto completo para determinar la representación de salida.

Por defecto es el nombre del campo.

### `validators`

Una lista de funciones validadoras que deben aplicarse a la entrada del campo entrante, y que lanzan un error de validación o simplemente devuelven un valor. Las funciones validadoras típicamente deben lanzar `serializers.ValidationError`, pero también se soporta el `ValidationError` incorporado de Django para compatibilidad con validadores definidos en la base de código de Django o paquetes de terceros de Django.

### `error_messages`

Un diccionario de códigos de error a mensajes de error.

### `label`

Una cadena de texto corta que puede usarse como el nombre del campo en campos de formulario HTML u otros elementos descriptivos.

### `help_text`

Una cadena de texto que puede usarse como descripción del campo en campos de formulario HTML u otros elementos descriptivos.

### `initial`

Un valor que debe usarse para pre-poblar el valor de los campos de formulario HTML. Puedes pasarle un callable, igual que
puedes hacer con cualquier `Field` regular de Django:

```python
import datetime
from rest_framework import serializers


class ExampleSerializer(serializers.Serializer):
    day = serializers.DateField(initial=datetime.date.today)
```

### `style`

Un diccionario de pares clave-valor que puede usarse para controlar cómo los renderizadores deben renderizar el campo.

Dos ejemplos aquí son `'input_type'` y `'base_template'`:

```python
# Usar <input type="password"> para la entrada.
password = serializers.CharField(
    style={'input_type': 'password'}
)

# Usar una entrada de radio en lugar de una entrada de selección.
color_channel = serializers.ChoiceField(
    choices=['red', 'green', 'blue'],
    style={'base_template': 'radio.html'}
)
```

Para más detalles consulta la documentación de [HTML & Forms][html-and-forms].

# Campos booleanos

## BooleanField

Una representación booleana.

Al usar entrada de formulario codificada en HTML, ten en cuenta que omitir un valor siempre se tratará como establecer un campo en `False`, incluso si tiene la opción `default=True` especificada. Esto se debe a que las entradas de checkbox de HTML representan el estado no marcado omitiendo el valor, por lo que REST framework trata la omisión como si fuera una entrada de checkbox vacía.

Ten en cuenta que Django 2.1 eliminó el kwarg `blank` de `models.BooleanField`.
Antes de Django 2.1 los campos `models.BooleanField` siempre eran `blank=True`. Por lo tanto,
desde Django 2.1 las instancias predeterminadas `serializers.BooleanField` se generarán
sin el kwarg `required` (es decir, equivalente a `required=True`) mientras que con
versiones anteriores de Django, las instancias predeterminadas `BooleanField` se generarán
con una opción `required=False`. Si quieres controlar este comportamiento manualmente,
declara explícitamente el `BooleanField` en la clase del serializer, o usa la
opción `extra_kwargs` para establecer la bandera `required`.

Corresponde a `django.db.models.fields.BooleanField`.

**Firma:** `BooleanField()`

# Campos de texto

## CharField

Una representación de texto. Opcionalmente valida que el texto sea más corto que `max_length` y más largo que `min_length`.

Corresponde a `django.db.models.fields.CharField` o `django.db.models.fields.TextField`.

**Firma:** `CharField(max_length=None, min_length=None, allow_blank=False, trim_whitespace=True)`

- `max_length` - Valida que la entrada no contenga más de este número de caracteres.
- `min_length` - Valida que la entrada contenga al menos este número de caracteres.
- `allow_blank` - Si se establece en `True` entonces la cadena vacía debe considerarse un valor válido. Si se establece en `False` entonces la cadena vacía se considera inválida y lanzará un error de validación. Por defecto es `False`.
- `trim_whitespace` - Si se establece en `True` entonces los espacios en blanco al inicio y al final se recortan. Por defecto es `True`.

La opción `allow_null` también está disponible para campos de texto, aunque su uso se desalienta en favor de `allow_blank`. Es válido establecer tanto `allow_blank=True` como `allow_null=True`, pero hacerlo significa que habrá dos tipos diferentes de valores vacíos permitidos para representaciones de texto, lo que puede llevar a inconsistencias de datos y errores sutiles en la aplicación.

## EmailField

Una representación de texto, valida que el texto sea una dirección de correo electrónico válida.

Corresponde a `django.db.models.fields.EmailField`

**Firma:** `EmailField(max_length=None, min_length=None, allow_blank=False)`

## RegexField

Una representación de texto, que valida que el valor dado coincida con una expresión regular específica.

Corresponde a `django.forms.fields.RegexField`.

**Firma:** `RegexField(regex, max_length=None, min_length=None, allow_blank=False)`

El argumento obligatorio `regex` puede ser una cadena o un objeto de expresión regular compilado de python.

Usa el `django.core.validators.RegexValidator` de Django para la validación.

## SlugField

Un `RegexField` que valida la entrada contra el patrón `[a-zA-Z0-9_-]+`.

Corresponde a `django.db.models.fields.SlugField`.

**Firma:** `SlugField(max_length=50, min_length=None, allow_blank=False)`

## URLField

Un `RegexField` que valida la entrada contra un patrón coincidente de URL. Espera URLs completamente calificadas de la forma `http://<host>/<path>`.

Corresponde a `django.db.models.fields.URLField`. Usa el `django.core.validators.URLValidator` de Django para la validación.

**Firma:** `URLField(max_length=200, min_length=None, allow_blank=False)`

## UUIDField

Un campo que asegura que la entrada es una cadena UUID válida. El método `to_internal_value` devolverá una instancia `uuid.UUID`. En la salida, el campo devolverá una cadena en el formato canónico con guiones, por ejemplo:

```text
"de305d54-75b4-431b-adb2-eb6b9e546013"
```

**Firma:** `UUIDField(format='hex_verbose')`

- `format`: Determina el formato de representación del valor uuid
  - `'hex_verbose'` - La representación hexadecimal canónica, incluyendo guiones: `"5ce0e9a5-5ffa-654b-cee0-1238041fb31a"`
  - `'hex'` - La representación hexadecimal compacta del UUID, sin incluir guiones: `"5ce0e9a55ffa654bcee01238041fb31a"`
  - `'int'` - Una representación de entero de 128 bits del UUID: `"123456789012312313134124512351145145114"`
  - `'urn'` - Representación URN RFC 4122 del UUID: `"urn:uuid:5ce0e9a5-5ffa-654b-cee0-1238041fb31a"`
    Cambiar los parámetros `format` solo afecta los valores de representación. Todos los formatos son aceptados por `to_internal_value`

## FilePathField

Un campo cuyas opciones se limitan a los nombres de archivo en un directorio determinado del sistema de archivos

Corresponde a `django.forms.fields.FilePathField`.

**Firma:** `FilePathField(path, match=None, recursive=False, allow_files=True, allow_folders=False, required=None, **kwargs)`

- `path` - La ruta absoluta del sistema de archivos a un directorio desde el cual este FilePathField debe obtener sus opciones.
- `match` - Una expresión regular, como cadena, que FilePathField usará para filtrar nombres de archivo.
- `recursive` - Especifica si deben incluirse todos los subdirectorios de la ruta. El valor predeterminado es `False`.
- `allow_files` - Especifica si deben incluirse los archivos en la ubicación especificada. El valor predeterminado es `True`. O esto o `allow_folders` debe ser `True`.
- `allow_folders` - Especifica si deben incluirse las carpetas en la ubicación especificada. El valor predeterminado es `False`. O esto o `allow_files` debe ser `True`.

## IPAddressField

Un campo que asegura que la entrada es una cadena IPv4 o IPv6 válida.

Corresponde a `django.forms.fields.IPAddressField` y `django.forms.fields.GenericIPAddressField`.

**Firma**: `IPAddressField(protocol='both', unpack_ipv4=False, **options)`

- `protocol` Limita las entradas válidas al protocolo especificado. Los valores aceptados son 'both' (predeterminado), 'IPv4' o 'IPv6'. La coincidencia no distingue mayúsculas/minúsculas.
- `unpack_ipv4` Desempaqueta direcciones IPv4 mapeadas como ::ffff:192.0.2.1. Si esta opción está habilitada, esa dirección se desempaquetaría a 192.0.2.1. El valor predeterminado está deshabilitado. Solo puede usarse cuando el protocolo está configurado en 'both'.

# Campos numéricos

## IntegerField

Una representación entera.

Corresponde a `django.db.models.fields.IntegerField`, `django.db.models.fields.SmallIntegerField`, `django.db.models.fields.PositiveIntegerField` y `django.db.models.fields.PositiveSmallIntegerField`.

**Firma**: `IntegerField(max_value=None, min_value=None)`

- `max_value` Valida que el número proporcionado no sea mayor que este valor.
- `min_value` Valida que el número proporcionado no sea menor que este valor.

## FloatField

Una representación de punto flotante.

Corresponde a `django.db.models.fields.FloatField`.

**Firma**: `FloatField(max_value=None, min_value=None)`

- `max_value` Valida que el número proporcionado no sea mayor que este valor.
- `min_value` Valida que el número proporcionado no sea menor que este valor.

## DecimalField

Una representación decimal, representada en Python por una instancia de `Decimal`.

Corresponde a `django.db.models.fields.DecimalField`.

**Firma**: `DecimalField(max_digits, decimal_places, coerce_to_string=None, max_value=None, min_value=None)`

- `max_digits` El número máximo de dígitos permitidos en el número. Debe ser `None` o un entero mayor o igual a `decimal_places`.
- `decimal_places` El número de lugares decimales para almacenar con el número.
- `coerce_to_string` Establecer en `True` si los valores de cadena deben ser devueltos para la representación, o `False` si los objetos `Decimal` deben ser devueltos. Por defecto es el mismo valor que la clave de configuración `COERCE_DECIMAL_TO_STRING`, que será `True` a menos que se anule. Si los objetos `Decimal` son devueltos por el serializador, entonces el formato de salida final será determinado por el renderizador. Tenga en cuenta que configurar `localize` forzará el valor a `True`.
- `max_value` Valida que el número proporcionado no sea mayor que este valor. Debe ser un entero u objeto `Decimal`.
- `min_value` Valida que el número proporcionado no sea menor que este valor. Debe ser un entero u objeto `Decimal`.
- `localize` Establecer en `True` para habilitar la localización de entrada y salida basada en la configuración regional actual. Esto también forzará `coerce_to_string` a `True`. Por defecto es `False`. Tenga en cuenta que el formateo de datos está habilitado si ha configurado `USE_L10N=True` en su archivo de configuración.
- `rounding` Establece el modo de redondeo utilizado al cuantificar a la precisión configurada. Los valores válidos son [modos de redondeo del módulo `decimal`][python-decimal-rounding-modes]. Por defecto es `None`.
- `normalize_output` Normalizará el valor decimal cuando se serialice. Esto eliminará todos los ceros finales y cambiará la precisión del valor a la precisión mínima requerida para poder representar el valor sin perder datos. Por defecto es `False`.

#### Ejemplo de uso

Para validar números hasta 999 con una resolución de 2 lugares decimales, usaría:

```python
serializers.DecimalField(max_digits=5, decimal_places=2)
```

Y para validar números hasta cualquier cosa menor a mil millones con una resolución de 10 lugares decimales:

```python
serializers.DecimalField(max_digits=19, decimal_places=10)
```

# Campos de fecha y hora

## DateTimeField

Una representación de fecha y hora.

Corresponde a `django.db.models.fields.DateTimeField`.

**Firma:** `DateTimeField(format=api_settings.DATETIME_FORMAT, input_formats=None, default_timezone=None)`

- `format` - Una cadena que representa el formato de salida. Si no se especifica, por defecto es el mismo valor que la clave de configuración `DATETIME_FORMAT`, que será `'iso-8601'` a menos que se configure. Establecer una cadena de formato indica que los valores de retorno de `to_representation` deben ser forzados a salida de cadena. Las cadenas de formato se describen a continuación. Establecer este valor en `None` indica que los objetos `datetime` de Python deben ser devueltos por `to_representation`. En este caso, la codificación de datetime será determinada por el renderizador.
- `input_formats` - Una lista de cadenas que representan los formatos de entrada que pueden ser utilizados para analizar la fecha. Si no se especifica, se usará la configuración `DATETIME_INPUT_FORMATS`, que por defecto es `['iso-8601']`.
- `default_timezone` - Una subclase `tzinfo` (`zoneinfo` o `pytz`) que representa la zona horaria. Si no se especifica y la configuración `USE_TZ` está habilitada, por defecto es la [zona horaria actual][django-current-timezone]. Si `USE_TZ` está deshabilitado, entonces los objetos datetime serán ingenuos.

#### Cadenas de formato de `DateTimeField`.

Las cadenas de formato pueden ser [formatos strftime de Python][strftime] que especifican explícitamente el formato, o la cadena especial `'iso-8601'`, que indica que deben usarse datetimes estilo [ISO 8601][iso8601]. (ej. `'2013-01-29T12:34:56.000000Z'`)

Cuando se usa un valor de `None` para el formato, los objetos `datetime` serán devueltos por `to_representation` y la representación de salida final será determinada por la clase del renderizador.

#### Campos de modelo `auto_now` y `auto_now_add`.

Al usar `ModelSerializer` o `HyperlinkedModelSerializer`, tenga en cuenta que cualquier campo de modelo con `auto_now=True` o `auto_now_add=True` usará campos de serializador que son `read_only=True` por defecto.

Si desea anular este comportamiento, necesitará declarar el `DateTimeField` explícitamente en el serializador. Por ejemplo:

```python
class CommentSerializer(serializers.ModelSerializer):
    created = serializers.DateTimeField()

    class Meta:
        model = Comment
```

# Campos de selección de opciones

## ChoiceField

Un campo que puede aceptar un valor de un conjunto limitado de opciones.

Es usado por `ModelSerializer` para generar campos automáticamente si el campo del modelo correspondiente incluye un argumento `choices=…`.

**Firma:** `ChoiceField(choices)`

- `choices` - Una lista de valores válidos, o una lista de tuplas `(key, display_name)`.
- `allow_blank` - Si se establece en `True` entonces la cadena vacía debe ser considerada un valor válido. Si se establece en `False` entonces la cadena vacía se considera inválida y lanzará un error de validación. Por defecto es `False`.
- `html_cutoff` - Si se establece, este será el número máximo de opciones que serán mostradas por un desplegable select de HTML. Puede usarse para asegurar que ChoiceFields generados automáticamente con selecciones posibles muy grandes no impidan que una plantilla se renderice. Por defecto es `None`.
- `html_cutoff_text` - Si se establece, mostrará un indicador textual si el número máximo de elementos ha sido cortado en un desplegable select de HTML. Por defecto es `"Más de {count} elementos…"`

Tanto `allow_blank` como `allow_null` son opciones válidas en `ChoiceField`, aunque es altamente recomendable que solo use una y no ambas. `allow_blank` debe preferirse para opciones textuales, y `allow_null` debe preferirse para opciones numéricas u otras opciones no textuales.

## MultipleChoiceField

Un campo que puede aceptar un conjunto de cero, uno o muchos valores, elegidos de un conjunto limitado de opciones. Toma un único argumento obligatorio. `to_internal_value` devuelve un `set` que contiene los valores seleccionados.

**Firma:** `MultipleChoiceField(choices)`

- `choices` - Una lista de valores válidos, o una lista de tuplas `(key, display_name)`.
- `allow_blank` - Si se establece en `True` entonces la cadena vacía debe ser considerada un valor válido. Si se establece en `False` entonces la cadena vacía se considera inválida y lanzará un error de validación. Por defecto es `False`.
- `html_cutoff` - Si se establece, este será el número máximo de opciones que serán mostradas por un desplegable select de HTML. Puede usarse para asegurar que ChoiceFields generados automáticamente con selecciones posibles muy grandes no impidan que una plantilla se renderice. Por defecto es `None`.
- `html_cutoff_text` - Si se establece, mostrará un indicador textual si el número máximo de elementos ha sido cortado en un desplegable select de HTML. Por defecto es `"Más de {count} elementos…"`

Al igual que con `ChoiceField`, ambas opciones `allow_blank` y `allow_null` son válidas, aunque es altamente recomendable que solo use una y no ambas. `allow_blank` debe preferirse para opciones textuales, y `allow_null` debe preferirse para opciones numéricas u otras opciones no textuales.

# Campos de carga de archivos

#### Parsers y carga de archivos.

Las clases `FileField` e `ImageField` solo son adecuadas para usar con `MultiPartParser` o `FileUploadParser`. La mayoría de los parsers, como por ejemplo JSON, no soportan carga de archivos.
Los [FILE_UPLOAD_HANDLERS] regulares de Django se usan para manejar archivos cargados.

## FileField

Una representación de archivo. Realiza la validación estándar de FileField de Django.

Corresponde a `django.forms.fields.FileField`.

**Firma:** `FileField(max_length=None, allow_empty_file=False, use_url=UPLOADED_FILES_USE_URL)`

- `max_length` - Designa la longitud máxima para el nombre del archivo.
- `allow_empty_file` - Designa si se permiten archivos vacíos.
- `use_url` - Si se establece en `True` entonces los valores de cadena URL serán usados para la representación de salida. Si se establece en `False` entonces los valores de cadena de nombre de archivo serán usados para la representación de salida. Por defecto es el valor de la clave de configuración `UPLOADED_FILES_USE_URL`, que es `True` a menos que se configure de otra manera.

## ImageField

Una representación de imagen. Valida el contenido del archivo cargado como coincidente con un formato de imagen conocido.

Corresponde a `django.forms.fields.ImageField`.

**Firma:** `ImageField(max_length=None, allow_empty_file=False, use_url=UPLOADED_FILES_USE_URL)`

- `max_length` - Designa la longitud máxima para el nombre del archivo.
- `allow_empty_file` - Designa si se permiten archivos vacíos.
- `use_url` - Si se establece en `True` entonces los valores de cadena URL serán usados para la representación de salida. Si se establece en `False` entonces los valores de cadena de nombre de archivo serán usados para la representación de salida. Por defecto es el valor de la clave de configuración `UPLOADED_FILES_USE_URL`, que es `True` a menos que se configure de otra manera.

Requiere el paquete `Pillow` o el paquete `PIL`. El paquete `Pillow` es recomendado, ya que `PIL` ya no se mantiene activamente.

# Campos compuestos

## ListField

Una clase de campo que valida una lista de objetos.

**Firma**: `ListField(child=<UNA_INSTANCIA_DE_CAMPO>, allow_empty=True, min_length=None, max_length=None)`

- `child` - Una instancia de campo que debe ser usada para validar los objetos en la lista. Si este argumento no se proporciona entonces los objetos en la lista no serán validados.
- `allow_empty` - Designa si se permiten listas vacías.
- `min_length` - Valida que la lista contiene no menos que este número de elementos.
- `max_length` - Valida que la lista contiene no más que este número de elementos.

Por ejemplo, para validar una lista de enteros podría usar algo como lo siguiente:

```python
scores = serializers.ListField(
    child=serializers.IntegerField(min_value=0, max_value=100)
)
```

La clase `ListField` también soporta un estilo declarativo que le permite escribir clases de campo de lista reutilizables.

```python
class StringListField(serializers.ListField):
    child = serializers.CharField()
```

Ahora podemos reutilizar nuestra clase `StringListField` personalizada a través de nuestra aplicación, sin tener que proporcionar un argumento `child`.

## DictField

Una clase de campo que valida un diccionario de objetos. Las claves en `DictField` siempre se asumen como valores de cadena.

**Firma**: `DictField(child=<UNA_INSTANCIA_DE_CAMPO>, allow_empty=True)`

- `child` - Una instancia de campo que debe ser usada para validar los valores en el diccionario. Si este argumento no se proporciona entonces los valores en el mapeo no serán validados.
- `allow_empty` - Designa si se permiten diccionarios vacíos.

Por ejemplo, para crear un campo que valide un mapeo de cadenas a cadenas, escribiría algo como esto:

```python
document = DictField(child=CharField())
```

También puede usar el estilo declarativo, como con `ListField`. Por ejemplo:

```python
class DocumentField(DictField):
    child = CharField()
```

## HStoreField

Un `DictField` preconfigurado que es compatible con el `HStoreField` de postgres de Django.

**Firma**: `HStoreField(child=<UNA_INSTANCIA_DE_CAMPO>, allow_empty=True)`

- `child` - Una instancia de campo que se usa para validar los valores en el diccionario. El campo hijo predeterminado acepta tanto cadenas vacías como valores nulos.
- `allow_empty` - Designa si se permiten diccionarios vacíos.

Tenga en cuenta que el campo hijo **debe** ser una instancia de `CharField`, ya que la extensión hstore almacena valores como cadenas.

## JSONField

Una clase de campo que valida que la estructura de datos entrante consiste en primitivos JSON válidos. En su modo binario alternativo, representará y validará cadenas binarias codificadas en JSON.

**Firma**: `JSONField(binary, encoder)`

- `binary` - Si se establece en `True` entonces el campo emitirá y validará una cadena codificada en JSON, en lugar de una estructura de datos primitiva. Por defecto es `False`.
- `encoder` - Use este codificador JSON para serializar el objeto de entrada. Por defecto es `None`.

# Campos misceláneos

## ReadOnlyField

Una clase de campo que simplemente devuelve el valor del campo sin modificación.

Este campo se usa por defecto con `ModelSerializer` al incluir nombres de campo que se relacionan con un atributo en lugar de un campo de modelo.

**Firma**: `ReadOnlyField()`

Por ejemplo, si `has_expired` era una propiedad en el modelo `Account`, entonces el siguiente serializador lo generaría automáticamente como un `ReadOnlyField`:

```python
class AccountSerializer(serializers.ModelSerializer):
    class Meta:
        model = Account
        fields = ['id', 'account_name', 'has_expired']
```

## HiddenField

Una clase de campo que no toma un valor basado en la entrada del usuario, sino que toma su valor de un valor predeterminado o un callable.

**Firma**: `HiddenField()`

Por ejemplo, para incluir un campo que siempre proporcione la hora actual como parte de los datos validados del serializador, usaría lo siguiente:

```python
modified = serializers.HiddenField(default=timezone.now)
```

La clase `HiddenField` generalmente solo se necesita si tiene alguna validación que necesita ejecutarse basándose en algunos valores de campo pre-proporcionados, pero no desea exponer todos esos campos al usuario final.

Para más ejemplos sobre `HiddenField` consulte la documentación de [validadores](validators.md).

---

**Nota:** `HiddenField()` no aparece en el serializador `partial=True` (al hacer una solicitud `PATCH`).

---

## ModelField

Un campo genérico que puede estar vinculado a cualquier campo de modelo arbitrario. La clase `ModelField` delega la tarea de serialización/deserialización a su campo de modelo asociado. Este campo se puede utilizar para crear campos de serializador para campos de modelo personalizados, sin tener que crear un nuevo campo de serializador personalizado.

Este campo es utilizado por `ModelSerializer` para corresponder a clases de campo de modelo personalizadas.

**Firma:** `ModelField(model_field=<instancia de Django ModelField>)`

La clase `ModelField` está generalmente destinada para uso interno, pero puede ser utilizada por su API si es necesario. Para instanciar correctamente un `ModelField`, se le debe pasar un campo que esté adjunto a un modelo instanciado. Por ejemplo: `ModelField(model_field=MyModel()._meta.get_field('custom_field'))`

## SerializerMethodField

Este es un campo de solo lectura. Obtiene su valor llamando a un método en la clase de serializador a la que está adjunto. Se puede usar para agregar cualquier tipo de datos a la representación serializada de su objeto.

**Firma**: `SerializerMethodField(method_name=None)`

- `method_name` - El nombre del método en el serializador que se llamará. Si no se incluye, esto por defecto es `get_<field_name>`.

El método del serializador referido por el argumento `method_name` debe aceptar un solo argumento (además de `self`), que es el objeto que se está serializando. Debe devolver lo que quiera que se incluya en la representación serializada del objeto. Por ejemplo:

```python
from django.contrib.auth.models import User
from django.utils.timezone import now
from rest_framework import serializers

class UserSerializer(serializers.ModelSerializer):
    days_since_joined = serializers.SerializerMethodField()

    class Meta:
        model = User
        fields = '__all__'

    def get_days_since_joined(self, obj):
        return (now() - obj.date_joined).days
```

# Campos personalizados

Si desea crear un campo personalizado, necesitará subclasificar `Field` y luego sobreescribir uno o ambos de los métodos `.to_representation()` y `.to_internal_value()`. Estos dos métodos se usan para convertir entre el tipo de dato inicial y un tipo de dato primitivo, serializable. Los tipos de datos primitivos normalmente serán cualquiera de número, cadena, booleano, `date`/`time`/`datetime` o `None`. También pueden ser cualquier objeto tipo lista o diccionario que solo contenga otros objetos primitivos. Otros tipos pueden ser soportados, dependiendo del renderizador que esté utilizando.

El método `.to_representation()` se llama para convertir el tipo de dato inicial en un tipo de dato primitivo, serializable.

El método `.to_internal_value()` se llama para restaurar un tipo de dato primitivo a su representación interna de python. Este método debe lanzar una `serializers.ValidationError` si los datos no son válidos.

## Ejemplos

### Un Campo Personalizado Básico

Veamos un ejemplo de serializar una clase que representa un valor de color RGB:

```python
class Color:
    """
    Un color representado en el espacio de color RGB.
    """
    def __init__(self, red, green, blue):
        assert(red >= 0 and green >= 0 and blue >= 0)
        assert(red < 256 and green < 256 and blue < 256)
        self.red, self.green, self.blue = red, green, blue

class ColorField(serializers.Field):
    """
    Los objetos de color se serializan en notación 'rgb(#, #, #)'.
    """
    def to_representation(self, value):
        return "rgb(%d, %d, %d)" % (value.red, value.green, value.blue)

    def to_internal_value(self, data):
        data = data.strip('rgb(').rstrip(')')
        red, green, blue = [int(col) for col in data.split(',')]
        return Color(red, green, blue)
```

Por defecto, los valores de los campos se tratan como mapeo a un atributo en el objeto. Si necesita personalizar cómo se accede y establece el valor del campo, necesita sobreescribir `.get_attribute()` y/o `.get_value()`.

Como ejemplo, creemos un campo que se pueda usar para representar el nombre de la clase del objeto que se está serializando:

```python
class ClassNameField(serializers.Field):
    def get_attribute(self, instance):
        # Pasamos la instancia del objeto a `to_representation`,
        # no solo el atributo del campo.
        return instance

    def to_representation(self, value):
        """
        Serializa el nombre de la clase del valor.
        """
        return value.__class__.__name__
```

### Lanzando errores de validación

Nuestra clase `ColorField` anterior actualmente no realiza ninguna validación de datos.
Para indicar datos no válidos, deberíamos lanzar una `serializers.ValidationError`, así:

```python
def to_internal_value(self, data):
    if not isinstance(data, str):
        msg = 'Tipo incorrecto. Se esperaba una cadena, pero se obtuvo %s'
        raise ValidationError(msg % type(data).__name__)

    if not re.match(r'^rgb\([0-9]+,[0-9]+,[0-9]+\)$', data):
        raise ValidationError('Formato incorrecto. Se esperaba `rgb(#,#,#)`.')

    data = data.strip('rgb(').rstrip(')')
    red, green, blue = [int(col) for col in data.split(',')]

    if any([col > 255 or col < 0 for col in (red, green, blue)]):
        raise ValidationError('Valor fuera de rango. Debe estar entre 0 y 255.')

    return Color(red, green, blue)
```

El método `.fail()` es un atajo para lanzar `ValidationError` que toma una cadena de mensaje del diccionario `error_messages`. Por ejemplo:

```python
default_error_messages = {
    'incorrect_type': 'Tipo incorrecto. Se esperaba una cadena, pero se obtuvo {input_type}',
    'incorrect_format': 'Formato incorrecto. Se esperaba `rgb(#,#,#)`.',
    'out_of_range': 'Valor fuera de rango. Debe estar entre 0 y 255.'
}

def to_internal_value(self, data):
    if not isinstance(data, str):
        self.fail('incorrect_type', input_type=type(data).__name__)

    if not re.match(r'^rgb\([0-9]+,[0-9]+,[0-9]+\)$', data):
        self.fail('incorrect_format')

    data = data.strip('rgb(').rstrip(')')
    red, green, blue = [int(col) for col in data.split(',')]

    if any([col > 255 or col < 0 for col in (red, green, blue)]):
        self.fail('out_of_range')

    return Color(red, green, blue)
```

Este estilo mantiene sus mensajes de error más limpios y separados de su código, y debe ser preferido.

### Usando `source='*'`

Aquí tomaremos un ejemplo de un modelo `DataPoint` _plano_ con atributos `x_coordinate` y `y_coordinate`.

```python
class DataPoint(models.Model):
    label = models.CharField(max_length=50)
    x_coordinate = models.SmallIntegerField()
    y_coordinate = models.SmallIntegerField()
```

Usando un campo personalizado y `source='*'` podemos proporcionar una representación anidada del par de coordenadas:

```python
class CoordinateField(serializers.Field):

    def to_representation(self, value):
        ret = {
            "x": value.x_coordinate,
            "y": value.y_coordinate
        }
        return ret

    def to_internal_value(self, data):
        ret = {
            "x_coordinate": data["x"],
            "y_coordinate": data["y"],
        }
        return ret


class DataPointSerializer(serializers.ModelSerializer):
    coordinates = CoordinateField(source='*')

    class Meta:
        model = DataPoint
        fields = ['label', 'coordinates']
```

Note que este ejemplo no maneja la validación. Parcialmente por esa razón, en un proyecto real, el anidamiento de coordenadas podría ser mejor manejado con un serializador anidado usando `source='*'`, con dos instancias de `IntegerField`, cada una con su propio `source` apuntando al campo relevante.

Los puntos clave del ejemplo, sin embargo, son:

- `to_representation` recibe el objeto `DataPoint` completo y debe mapear desde ese a la salida deseada.

```bash
>>> instance = DataPoint(label='Example', x_coordinate=1, y_coordinate=2)
>>> out_serializer = DataPointSerializer(instance)
>>> out_serializer.data
ReturnDict([('label', 'Example'), ('coordinates', {'x': 1, 'y': 2})])
```

- A menos que nuestro campo sea de solo lectura, `to_internal_value` debe mapear de vuelta a un diccionario adecuado para actualizar nuestro objeto objetivo. Con `source='*'`, el retorno de `to_internal_value` actualizará el diccionario raíz de datos validados, en lugar de una sola clave.

```bash
>>> data = {
...     "label": "Second Example",
...     "coordinates": {
...         "x": 3,
...         "y": 4,
...     }
... }
>>> in_serializer = DataPointSerializer(data=data)
>>> in_serializer.is_valid()
True
>>> in_serializer.validated_data
OrderedDict([('label', 'Second Example'),
                ('y_coordinate', 4),
                ('x_coordinate', 3)])
```

Para completar, hagamos lo mismo de nuevo pero con el enfoque de serializador anidado sugerido anteriormente:

```python
class NestedCoordinateSerializer(serializers.Serializer):
    x = serializers.IntegerField(source='x_coordinate')
    y = serializers.IntegerField(source='y_coordinate')


class DataPointSerializer(serializers.ModelSerializer):
    coordinates = NestedCoordinateSerializer(source='*')

    class Meta:
        model = DataPoint
        fields = ['label', 'coordinates']
```

Aquí el mapeo entre los pares de atributos objetivo y fuente (`x` y `x_coordinate`, `y` y `y_coordinate`) se maneja en las declaraciones de `IntegerField`. Es nuestro `NestedCoordinateSerializer` que toma `source='*'`.

Nuestro `DataPointSerializer` nuevo exhibe el mismo comportamiento que el enfoque de campo personalizado.

Serializando:

```bash
>>> out_serializer = DataPointSerializer(instance)
>>> out_serializer.data
ReturnDict([('label', 'testing'),
            ('coordinates', OrderedDict([('x', 1), ('y', 2)]))])
```

Deserializando:

```bash
>>> in_serializer = DataPointSerializer(data=data)
>>> in_serializer.is_valid()
True
>>> in_serializer.validated_data
OrderedDict([('label', 'still testing'),
                ('x_coordinate', 3),
                ('y_coordinate', 4)])
```

Pero también obtenemos la validación incorporada gratis:

```bash
>>> invalid_data = {
...     "label": "still testing",
...     "coordinates": {
...         "x": 'a',
...         "y": 'b',
...     }
... }
>>> invalid_serializer = DataPointSerializer(data=invalid_data)
>>> invalid_serializer.is_valid()
False
>>> invalid_serializer.errors
ReturnDict([('coordinates',
                {'x': ['A valid integer is required.'],
                'y': ['A valid integer is required.']})])
```

Por esta razón, el enfoque de serializador anidado sería el primero a intentar. Usaría el enfoque de campo personalizado cuando el serializador anidado se vuelve inviable o excesivamente complejo.

# Paquetes de terceros

Los siguientes paquetes de terceros también están disponibles.

## DRF Compound Fields

El paquete [drf-compound-fields][drf-compound-fields] proporciona campos de serializador "compuestos", como listas de valores simples, que pueden ser descritos por otros campos en lugar de serializadores con la opción `many=True`. También se proporcionan campos para diccionarios tipados y valores que pueden ser de un tipo específico o una lista de elementos de ese tipo.

## DRF Extra Fields

El paquete [drf-extra-fields][drf-extra-fields] proporciona campos de serializador adicionales para REST framework, incluyendo clases `Base64ImageField` y `PointField`.

## djangorestframework-recursive

el paquete [djangorestframework-recursive][djangorestframework-recursive] proporciona un `RecursiveField` para serializar y deserializar estructuras recursivas

## django-rest-framework-gis

El paquete [django-rest-framework-gis][django-rest-framework-gis] proporciona complementos geográficos para django rest framework como un campo `GeometryField` y un serializador GeoJSON.

## django-rest-framework-hstore

El paquete [django-rest-framework-hstore][django-rest-framework-hstore] proporciona un `HStoreField` para soportar el campo de modelo `DictionaryField` de [django-hstore][django-hstore].
