# Sufijos de formato

> La sección 6.2.1 no dice que la negociación de contenido deba
> usarse todo el tiempo.
>
> &mdash; Roy Fielding, [lista de correo REST discuss][cite]

Un patrón común para las APIs web es usar extensiones de nombre de archivo en las URLs para proporcionar un endpoint para un tipo de medio determinado. Por ejemplo, 'http://example.com/api/users.json' para servir una representación JSON.

Añadir patrones de sufijos de formato a cada entrada individual en la URLconf de tu API es propenso a errores y no sigue el principio DRY, por lo que REST framework proporciona un atajo para añadir estos patrones a tu URLConf.

## format_suffix_patterns

**Firma**: format_suffix_patterns(urlpatterns, suffix_required=False, allowed=None)

Devuelve una lista de patrones de URL que incluye patrones de sufijos de formato añadidos a cada uno de los patrones de URL proporcionados.

Argumentos:

- **urlpatterns**: Requerido. Una lista de patrones de URL.
- **suffix_required**: Opcional. Un booleano que indica si los sufijos en las URLs deben ser opcionales u obligatorios. Por defecto es `False`, lo que significa que los sufijos son opcionales por defecto.
- **allowed**: Opcional. Una lista o tupla de sufijos de formato válidos. Si no se proporciona, se usará un patrón de sufijo de formato comodín.

Ejemplo:

```python
from rest_framework.urlpatterns import format_suffix_patterns
from blog import views

urlpatterns = [
    path('', views.apt_root),
    path('comments/', views.comment_list),
    path('comments/<int:pk>/', views.comment_detail)
]

urlpatterns = format_suffix_patterns(urlpatterns, allowed=['json', 'html'])
```

Al usar `format_suffix_patterns`, debes asegurarte de añadir el argumento de palabra clave `'format'` a las vistas correspondientes. Por ejemplo:

```python
@api_view(['GET', 'POST'])
def comment_list(request, format=None):
    # hacer cosas...
```

O con vistas basadas en clases:

```python
class CommentList(APIView):
    def get(self, request, format=None):
        # hacer cosas...

    def post(self, request, format=None):
        # hacer cosas...
```

El nombre del kwarg utilizado puede modificarse usando la configuración `FORMAT_SUFFIX_KWARG`.

También ten en cuenta que `format_suffix_patterns` no soporta descender en patrones de URL `include`.

### Usando con `i18n_patterns`

Si usas la función `i18n_patterns` proporcionada por Django, así como `format_suffix_patterns`, debes asegurarte de que la función `i18n_patterns` se aplique como la función final o más externa. Por ejemplo:

```python
urlpatterns = [
    …
]

urlpatterns = i18n_patterns(
    format_suffix_patterns(urlpatterns, allowed=['json', 'html'])
)
```

## Formatos de parámetros de consulta

Una alternativa a los sufijos de formato es incluir el formato solicitado en un parámetro de consulta. REST framework proporciona esta opción por defecto, y se usa en la API navegable para cambiar entre diferentes representaciones disponibles.

Para seleccionar una representación usando su formato corto, usa el parámetro de consulta `format`. Por ejemplo: `http://example.com/organizations/?format=csv`.

El nombre de este parámetro de consulta puede modificarse usando la configuración `URL_FORMAT_OVERRIDE`. Establece el valor en `None` para desactivar este comportamiento.

## Cabeceras Accept vs. sufijos de formato

Parece haber una opinión en parte de la comunidad web de que las extensiones de nombre de archivo no son un patrón RESTful, y que siempre deberían usarse las cabeceras `HTTP Accept` en su lugar.

En realidad es un concepto erróneo. Por ejemplo, toma la siguiente cita de Roy Fielding discutiendo los méritos relativos de los indicadores de tipo de medio de parámetros de consulta vs. los indicadores de tipo de medio de extensión de archivo:

"Por eso siempre prefiero las extensiones. Ninguna de las dos opciones tiene nada que ver con REST." &mdash; Roy Fielding, [lista de correo REST discuss][cite2]

La cita no menciona las cabeceras Accept, pero sí deja claro que los sufijos de formato deben considerarse un patrón aceptable.
