# Vistas genéricas

> Las vistas genéricas de Django... se desarrollaron como un atajo para patrones de uso comunes... Toman ciertos modismos y patrones comunes encontrados en el desarrollo de vistas y los abstraen para que puedas escribir rápidamente vistas comunes de datos sin tener que repetirte.
>
> &mdash; [Django Documentation][cite]

Uno de los beneficios clave de las vistas basadas en clases es la forma en que te permiten componer bits de comportamiento reutilizable. REST framework se aprovecha de esto proporcionando una serie de vistas preconstruidas que proporcionan patrones comúnmente utilizados.

Las vistas genéricas proporcionadas por REST framework te permiten construir rápidamente vistas de API que se mapean estrechamente a tus modelos de base de datos.

Si las vistas genéricas no se adaptan a las necesidades de tu API, puedes pasar a usar la clase regular `APIView`, o reutilizar los mixins y clases base usados por las vistas genéricas para componer tu propio conjunto de vistas genéricas reutilizables.

## Ejemplos

Típicamente, cuando usas las vistas genéricas, sobreescribirás la vista y establecerás varios atributos de clase.

```python
from django.contrib.auth.models import User
from myapp.serializers import UserSerializer
from rest_framework import generics
from rest_framework.permissions import IsAdminUser

class UserList(generics.ListCreateAPIView):
    queryset = User.objects.all()
    serializer_class = UserSerializer
    permission_classes = [IsAdminUser]
```

Para casos más complejos también podrías querer sobreescribir varios métodos en la clase de vista. Por ejemplo:

```python
class UserList(generics.ListCreateAPIView):
    queryset = User.objects.all()
    serializer_class = UserSerializer
    permission_classes = [IsAdminUser]

    def list(self, request):
        # Nota el uso de `get_queryset()` en lugar de `self.queryset`
        queryset = self.get_queryset()
        serializer = UserSerializer(queryset, many=True)
        return Response(serializer.data)
```

Para casos muy simples podrías querer pasar cualquier atributo de clase usando el método `.as_view()`. Por ejemplo, tu URLconf podría incluir algo como la siguiente entrada:

```python
path('users/', ListCreateAPIView.as_view(queryset=User.objects.all(), serializer_class=UserSerializer), name='user-list')
```

# Referencia de la API

## GenericAPIView

Esta clase extiende la clase `APIView` de REST framework, añadiendo comportamiento comúnmente requerido para vistas estándar de lista y detalle.

Cada una de las vistas genéricas concretas proporcionadas se construye combinando `GenericAPIView` con una o más clases mixin.

### Atributos

**Configuración básica**:

Los siguientes atributos controlan el comportamiento básico de la vista.

- `queryset` - El queryset que debería usarse para devolver objetos desde esta vista. Típicamente, debes establecer este atributo o sobreescribir el método `get_queryset()`. Si estás sobrescribiendo un método de vista, es importante que llames a `get_queryset()` en lugar de acceder a esta propiedad directamente, ya que `queryset` se evaluará una sola vez, y esos resultados se cachearán para todas las solicitudes subsequentes.
- `serializer_class` - La clase de serializador que debería usarse para validar y deserializar la entrada, y para serializar la salida. Típicamente, debes establecer este atributo o sobreescribir el método `get_serializer_class()`.
- `lookup_field` - El campo del modelo que debería usarse para realizar la búsqueda de objetos de instancias de modelo individuales. Por defecto es `'pk'`. Ten en cuenta que cuando usas APIs enlazadas, necesitarás asegurar que tanto las vistas de API como las clases de serializador establezcan los campos de búsqueda si necesitas usar un valor personalizado.
- `lookup_url_kwarg` - El argumento de palabra clave de URL que debería usarse para la búsqueda de objetos. La configuración de URL debería incluir un argumento de palabra clave correspondiente a este valor. Si no se establece, por defecto usa el mismo valor que `lookup_field`.

**Paginación**:

Los siguientes atributos se usan para controlar la paginación cuando se usan con vistas de lista.

- `pagination_class` - La clase de paginación que debería usarse al paginar resultados de lista. Por defecto usa el mismo valor que la configuración `DEFAULT_PAGINATION_CLASS`, que es `'rest_framework.pagination.PageNumberPagination'`. Establecer `pagination_class=None` desactivará la paginación en esta vista.

**Filtrado**:

- `filter_backends` - Una lista de clases de backend de filtrado que deberían usarse para filtrar el queryset. Por defecto usa el mismo valor que la configuración `DEFAULT_FILTER_BACKENDS`.

### Métodos

**Métodos base**:

#### `get_queryset(self)`

Devuelve el queryset que debería usarse para vistas de lista, y que debería usarse como base para búsquedas en vistas de detalle. Por defecto devuelve el queryset especificado por el atributo `queryset`.

Este método siempre debería usarse en lugar de acceder a `self.queryset` directamente, ya que `self.queryset` solo se evalúa una vez, y esos resultados se cachearán para todas las solicitudes posteriores.

Puede ser sobrescrito para proporcionar comportamiento dinámico, como devolver un queryset específico para el usuario que realiza la solicitud.

Por ejemplo:

```python
def get_queryset(self):
    user = self.request.user
    return user.accounts.all()
```

---

**Nota:** Si el `serializer_class` usado en la vista genérica abarca relaciones orm, llevando a un problema n+1, podrías optimizar tu queryset en este método usando `select_related` y `prefetch_related`. Para obtener más información sobre el problema n+1 y casos de uso de los métodos mencionados, consulta la sección relacionada en la [documentación de Django][django-docs-select-related].

---

#### `get_object(self)`

Devuelve una instancia de objeto que debería usarse para vistas de detalle. Por defecto usa el parámetro `lookup_field` para filtrar el queryset base.

Puede ser sobrescrito para proporcionar comportamiento más complejo, como búsquedas de objetos basadas en más de un kwarg de URL.

Por ejemplo:

```python
def get_object(self):
    queryset = self.get_queryset()
    filter = {}
    for field in self.multiple_lookup_fields:
        filter[field] = self.kwargs[field]

    obj = get_object_or_404(queryset, **filter)
    self.check_object_permissions(self.request, obj)
    return obj
```

Nota que si tu API no incluye ningún permiso a nivel de objeto, puedes opcionalmente excluir `self.check_object_permissions`, y simplemente devolver el objeto de la búsqueda `get_object_or_404`.

#### `filter_queryset(self, queryset)`

Dado un queryset, filtra con los backends de filtro que estén en uso, devolviendo un nuevo queryset.

Por ejemplo:

```python
def filter_queryset(self, queryset):
    filter_backends = [CategoryFilter]

    if 'geo_route' in self.request.query_params:
        filter_backends = [GeoRouteFilter, CategoryFilter]
    elif 'geo_point' in self.request.query_params:
        filter_backends = [GeoPointFilter, CategoryFilter]

    for backend in list(filter_backends):
        queryset = backend().filter_queryset(self.request, queryset, view=self)

    return queryset
```

#### `get_serializer_class(self)`

Devuelve la clase que debería usarse para el serializador. Por defecto devuelve el atributo `serializer_class`.

Puede ser sobrescrito para proporcionar comportamiento dinámico, como usar diferentes serializadores para operaciones de lectura y escritura, o proporcionar diferentes serializadores para diferentes tipos de usuarios.

Por ejemplo:

```python
def get_serializer_class(self):
    if self.request.user.is_staff:
        return FullAccountSerializer
    return BasicAccountSerializer
```

**Ganchos de guardado y eliminación**:

Los siguientes métodos son proporcionados por las clases mixin, y proporcionan fácil sobrescritura del comportamiento de guardado o eliminación de objetos.

- `perform_create(self, serializer)` - Llamado por `CreateModelMixin` al guardar una nueva instancia de objeto.
- `perform_update(self, serializer)` - Llamado por `UpdateModelMixin` al guardar una instancia de objeto existente.
- `perform_destroy(self, instance)` - Llamado por `DestroyModelMixin` al eliminar una instancia de objeto.

Estos ganchos son particularmente útiles para establecer atributos que son implícitos en la solicitud, pero no son parte de los datos de la solicitud. Por ejemplo, podrías establecer un atributo en el objeto basado en el usuario de la solicitud, o basado en un argumento de palabra clave de URL.

```python
def perform_create(self, serializer):
    serializer.save(user=self.request.user)
```

Estos puntos de sobrescritura también son particularmente útiles para añadir comportamiento que ocurre antes o después de guardar un objeto, como enviar un correo de confirmación, o registrar la actualización.

```python
def perform_update(self, serializer):
    instance = serializer.save()
    send_email_confirmation(user=self.request.user, modified=instance)
```

También puedes usar estos ganchos para proporcionar validación adicional, lanzando un `ValidationError()`. Esto puede ser útil si necesitas que alguna lógica de validación se aplique en el punto de guardado en la base de datos. Por ejemplo:

```python
def perform_create(self, serializer):
    queryset = SignupRequest.objects.filter(user=self.request.user)
    if queryset.exists():
        raise ValidationError('Ya te has registrado')
    serializer.save(user=self.request.user)
```

**Otros métodos**:

Típicamente no necesitarás sobrescribir los siguientes métodos, aunque podrías necesitar llamarlos si estás escribiendo vistas personalizadas usando `GenericAPIView`.

- `get_serializer_context(self)` - Devuelve un diccionario que contiene cualquier contexto adicional que debería suministrarse al serializador. Por defecto incluye las claves `'request'`, `'view'` y `'format'`.
- `get_serializer(self, instance=None, data=None, many=False, partial=False)` - Devuelve una instancia de serializador.
- `get_paginated_response(self, data)` - Devuelve un objeto `Response` de estilo paginado.
- `paginate_queryset(self, queryset)` - Pagina un queryset si es requerido, ya sea devolviendo un objeto de página, o `None` si la paginación no está configurada para esta vista.
- `filter_queryset(self, queryset)` - Dado un queryset, filtra con los backends de filtro que estén en uso, devolviendo un nuevo queryset.

# Mixins

Las clases mixin proporcionan las acciones que se usan para proporcionar el comportamiento básico de la vista. Nota que las clases mixin proporcionan métodos de acción en lugar de definir los métodos handler, como `.get()` y `.post()`, directamente. Esto permite una composición más flexible del comportamiento.

Las clases mixin pueden ser importadas desde `rest_framework.mixins`.

## ListModelMixin

Proporciona un método `.list(request, *args, **kwargs)`, que implementa listar un queryset.

Si el queryset está poblado, devuelve una respuesta `200 OK`, con una representación serializada del queryset como el cuerpo de la respuesta. Los datos de respuesta pueden opcionalmente estar paginados.

## CreateModelMixin

Proporciona un método `.create(request, *args, **kwargs)`, que implementa crear y guardar una nueva instancia de modelo.

Si se crea un objeto, devuelve una respuesta `201 Created`, con una representación serializada del objeto como el cuerpo de la respuesta. Si la representación contiene una clave llamada `url`, entonces el encabezado `Location` de la respuesta será poblado con ese valor.

Si los datos de solicitud proporcionados para crear el objeto son inválidos, se devolverá una respuesta `400 Bad Request`, con los detalles del error como el cuerpo de la respuesta.

## RetrieveModelMixin

Proporciona un método `.retrieve(request, *args, **kwargs)`, que implementa devolver una instancia de modelo existente en una respuesta.

Si se puede recuperar un objeto, devuelve una respuesta `200 OK`, con una representación serializada del objeto como el cuerpo de la respuesta. De lo contrario, devolverá `404 Not Found`.

## UpdateModelMixin

Proporciona un método `.update(request, *args, **kwargs)`, que implementa actualizar y guardar una instancia de modelo existente.

También proporciona un método `.partial_update(request, *args, **kwargs)`, que es similar al método `update`, excepto que todos los campos para la actualización serán opcionales. Esto permite soporte para solicitudes HTTP `PATCH`.

Si un objeto es actualizado, devuelve una respuesta `200 OK`, con una representación serializada del objeto como el cuerpo de la respuesta.

Si los datos de solicitud proporcionados para actualizar el objeto son inválidos, se devolverá una respuesta `400 Bad Request`, con los detalles del error como el cuerpo de la respuesta.

## DestroyModelMixin

Proporciona un método `.destroy(request, *args, **kwargs)`, que implementa la eliminación de una instancia de modelo existente.

Si un objeto es eliminado, devuelve una respuesta `204 No Content`, de lo contrario devolverá `404 Not Found`.

# Clases de Vista Concretas

Las siguientes clases son las vistas genéricas concretas. Si estás usando vistas genéricas, normalmente este es el nivel en el que trabajarás a menos que necesites comportamiento muy personalizado.

Las clases de vista pueden ser importadas desde `rest_framework.generics`.

## CreateAPIView

Usada para endpoints de **solo creación**.

Proporciona un método handler `post`.

Extiende: [GenericAPIView], [CreateModelMixin]

## ListAPIView

Usada para endpoints de **solo lectura** para representar una **colección de instancias de modelo**.

Proporciona un método handler `get`.

Extiende: [GenericAPIView], [ListModelMixin]

## RetrieveAPIView

Usada para endpoints de **solo lectura** para representar una **instancia de modelo única**.

Proporciona un método handler `get`.

Extiende: [GenericAPIView], [RetrieveModelMixin]

## DestroyAPIView

Usada para endpoints de **solo eliminación** para una **instancia de modelo única**.

Proporciona un método handler `delete`.

Extiende: [GenericAPIView], [DestroyModelMixin]

## UpdateAPIView

Usada para endpoints de **solo actualización** para una **instancia de modelo única**.

Proporciona métodos handler `put` y `patch`.

Extiende: [GenericAPIView], [UpdateModelMixin]

## ListCreateAPIView

Usada para endpoints de **lectura-escritura** para representar una **colección de instancias de modelo**.

Proporciona métodos handler `get` y `post`.

Extiende: [GenericAPIView], [ListModelMixin], [CreateModelMixin]

## RetrieveUpdateAPIView

Usada para endpoints de **lectura o actualización** para representar una **instancia de modelo única**.

Proporciona métodos handler `get`, `put` y `patch`.

Extiende: [GenericAPIView], [RetrieveModelMixin], [UpdateModelMixin]

## RetrieveDestroyAPIView

Usada para endpoints de **lectura o eliminación** para representar una **instancia de modelo única**.

Proporciona métodos handler `get` y `delete`.

Extiende: [GenericAPIView], [RetrieveModelMixin], [DestroyModelMixin]

## RetrieveUpdateDestroyAPIView

Usada para endpoints de **lectura-escritura-eliminación** para representar una **instancia de modelo única**.

Proporciona métodos handler `get`, `put`, `patch` y `delete`.

Extiende: [GenericAPIView], [RetrieveModelMixin], [UpdateModelMixin], [DestroyModelMixin]

# Personalizando las vistas genéricas

A menudo querrás usar las vistas genéricas existentes, pero usar algo de comportamiento ligeramente personalizado. Si te encuentras reusando algún comportamiento personalizado en múltiples lugares, podrías querer refactorizar el comportamiento en una clase común que puedas simplemente aplicar a cualquier vista o viewset según sea necesario.

## Creando mixins personalizados

Por ejemplo, si necesitas buscar objetos basados en múltiples campos en la configuración de URL, podrías crear una clase mixin como la siguiente:

```python
class MultipleFieldLookupMixin:
    """
    Aplica este mixin a cualquier vista o viewset para obtener filtrado 
    de múltiples campos basado en un atributo `lookup_fields`, en lugar del 
    filtrado de campo único predeterminado.
    """
    def get_object(self):
        queryset = self.get_queryset()             # Obtener el queryset base
        queryset = self.filter_queryset(queryset)  # Aplicar cualquier backend de filtro
        filter = {}
        for field in self.lookup_fields:
            if self.kwargs.get(field): # Ignorar campos vacíos.
                filter[field] = self.kwargs[field]
        obj = get_object_or_404(queryset, **filter)  # Buscar el objeto
        self.check_object_permissions(self.request, obj)
        return obj
```

Luego puedes simplemente aplicar este mixin a una vista o viewset cada vez que necesites aplicar el comportamiento personalizado.

```python
class RetrieveUserView(MultipleFieldLookupMixin, generics.RetrieveAPIView):
    queryset = User.objects.all()
    serializer_class = UserSerializer
    lookup_fields = ['account', 'username']
```

Usar mixins personalizados es una buena opción si tienes comportamiento personalizado que necesita ser usado.

## Creando clases base personalizadas

Si estás usando un mixin a través de múltiples vistas, puedes dar un paso más y crear tu propio conjunto de vistas base que puedan ser usadas a través de todo tu proyecto. Por ejemplo:

```python
class BaseRetrieveView(MultipleFieldLookupMixin,
                        generics.RetrieveAPIView):
    pass

class BaseRetrieveUpdateDestroyView(MultipleFieldLookupMixin,
                                    generics.RetrieveUpdateDestroyAPIView):
    pass
```

Usar clases base personalizadas es una buena opción si tienes comportamiento personalizado que consistentemente necesita ser repetido a través de un gran número de vistas en todo tu proyecto.

# PUT como creación

Antes de la versión 3.0, los mixins de REST framework trataban `PUT` como una operación de actualización o creación, dependiendo de si el objeto ya existía o no.

Permitir `PUT` como operaciones de creación es problemático, ya que necesariamente expone información sobre la existencia o no existencia de objetos. Tampoco es obvio que permitir transparentemente recrear instancias previamente eliminadas sea necesariamente un mejor comportamiento predeterminado que simplemente devolver respuestas `404`.

Ambos estilos "`PUT` como 404" y "`PUT` como creación" pueden ser válidos en diferentes circunstancias, pero desde la versión 3.0 en adelante ahora usamos el comportamiento 404 como predeterminado, debido a que es más simple y obvio.

Si necesitas comportamiento genérico de PUT-como-creación, podrías querer incluir algo como [esta clase `AllowPUTAsCreateMixin`](https://gist.github.com/tomchristie/a2ace4577eff2c603b1b) como un mixin en tus vistas.
