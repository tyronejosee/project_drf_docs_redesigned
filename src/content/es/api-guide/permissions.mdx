# Permisos

> La autenticación o identificación por sí sola generalmente no es suficiente para obtener acceso a información o código. Para ello, la entidad que solicita acceso debe tener autorización.
>
> &mdash; [Apple Developer Documentation][cite]

Junto con la [autenticación] y la [estrangulación], los permisos determinan si una solicitud debe ser concedida o denegada el acceso.

Las verificaciones de permisos siempre se ejecutan al inicio de la vista, antes de que se permita proceder con cualquier otro código. Las verificaciones de permisos típicamente usarán la información de autenticación en las propiedades `request.user` y `request.auth` para determinar si la solicitud entrante debe ser permitida.

Los permisos se utilizan para conceder o denegar el acceso a diferentes clases de usuarios a diferentes partes de la API.

El estilo de permiso más simple sería permitir el acceso a cualquier usuario autenticado y denegar el acceso a cualquier usuario no autenticado. Esto corresponde a la clase `IsAuthenticated` en REST framework.

Un estilo de permiso ligeramente menos estricto sería permitir acceso completo a usuarios autenticados, pero permitir acceso de solo lectura a usuarios no autenticados. Esto corresponde a la clase `IsAuthenticatedOrReadOnly` en REST framework.

## Cómo se determinan los permisos

Los permisos en REST framework siempre se definen como una lista de clases de permisos.

Antes de ejecutar el cuerpo principal de la vista, se verifica cada permiso en la lista.
Si alguna verificación de permisos falla, se lanzará una excepción `exceptions.PermissionDenied` o `exceptions.NotAuthenticated`, y el cuerpo principal de la vista no se ejecutará.

Cuando las verificaciones de permisos fallan, se devolverá una respuesta "403 Forbidden" o "401 Unauthorized", según las siguientes reglas:

- La solicitud fue autenticada exitosamente, pero el permiso fue denegado. _&mdash; Se devolverá una respuesta HTTP 403 Forbidden._
- La solicitud no fue autenticada exitosamente, y la clase de autenticación de mayor prioridad _no_ usa encabezados `WWW-Authenticate`. _&mdash; Se devolverá una respuesta HTTP 403 Forbidden._
- La solicitud no fue autenticada exitosamente, y la clase de autenticación de mayor prioridad _sí_ usa encabezados `WWW-Authenticate`. _&mdash; Se devolverá una respuesta HTTP 401 Unauthorized, con un encabezado `WWW-Authenticate` apropiado._

## Permisos a nivel de objeto

Los permisos de REST framework también soportan permisos a nivel de objeto. Los permisos a nivel de objeto se utilizan para determinar si un usuario debe poder actuar sobre un objeto particular, que típicamente será una instancia de modelo.

Los permisos a nivel de objeto son ejecutados por las vistas genéricas de REST framework cuando se llama a `.get_object()`.
Al igual que con los permisos a nivel de vista, se lanzará una excepción `exceptions.PermissionDenied` si al usuario no se le permite actuar sobre el objeto dado.

Si estás escribiendo tus propias vistas y quieres aplicar permisos a nivel de objeto,
o si sobreescribes el método `get_object` en una vista genérica, entonces necesitarás llamar explícitamente al método `.check_object_permissions(request, obj)` en la vista en el punto en que has recuperado el objeto.

Esto lanzará una excepción `PermissionDenied` o `NotAuthenticated`, o simplemente retornará si la vista tiene los permisos apropiados.

Por ejemplo:

```python
def get_object(self):
    obj = get_object_or_404(self.get_queryset(), pk=self.kwargs["pk"])
    self.check_object_permissions(self.request, obj)
    return obj
```

---

**Nota**: Con la excepción de `DjangoObjectPermissions`, las clases de permisos
proporcionadas en `rest_framework.permissions` **no** implementan los métodos
necesarios para verificar permisos de objeto.

Si deseas usar las clases de permisos proporcionadas para verificar permisos de
objeto, **debes** crear subclases de ellas e implementar el método
`has_object_permission()` descrito en la sección [_Permisos personalizados_](#custom-permissions) (abajo).

---

#### Limitaciones de los permisos a nivel de objeto

Por razones de rendimiento, las vistas genéricas no aplicarán automáticamente permisos a nivel de objeto a cada instancia en un queryset cuando se devuelve una lista de objetos.

A menudo, cuando usas permisos a nivel de objeto, también querrás [filtrar el queryset][filtering] apropiadamente, para asegurar que los usuarios solo tengan visibilidad sobre las instancias que tienen permiso para ver.

Debido a que el método `get_object()` no es llamado, los permisos a nivel de objeto del método `has_object_permission()` **no son aplicados** al crear objetos. Para restringir la creación de objetos necesitas implementar la verificación de permisos ya sea en tu clase Serializer o sobreescribir el método `perform_create()` de tu clase ViewSet.

## Configuración de la política de permisos

La política de permisos predeterminada puede establecerse globalmente, usando la configuración `DEFAULT_PERMISSION_CLASSES`. Por ejemplo:

```python
REST_FRAMEWORK = {
    'DEFAULT_PERMISSION_CLASSES': [
        'rest_framework.permissions.IsAuthenticated',
    ]
}
```

Si no se especifica, esta configuración predeterminada permite acceso sin restricciones:

```python
'DEFAULT_PERMISSION_CLASSES': [
    'rest_framework.permissions.AllowAny',
]
```

También puedes establecer la política de autenticación por vista o por viewset,
usando las vistas basadas en clases `APIView`.

```python
from rest_framework.permissions import IsAuthenticated
from rest_framework.response import Response
from rest_framework.views import APIView

class ExampleView(APIView):
    permission_classes = [IsAuthenticated]

    def get(self, request, format=None):
        content = {
            'status': 'solicitud fue permitida'
        }
        return Response(content)
```

O, si estás usando el decorador `@api_view` con vistas basadas en funciones.

```python
from rest_framework.decorators import api_view, permission_classes
from rest_framework.permissions import IsAuthenticated
from rest_framework.response import Response

@api_view(['GET'])
@permission_classes([IsAuthenticated])
def example_view(request, format=None):
    content = {
        'status': 'solicitud fue permitida'
    }
    return Response(content)
```

**Nota:** cuando estableces nuevas clases de permisos a través del atributo de clase o decoradores, le estás diciendo a la vista que ignore la lista predeterminada establecida en el archivo **settings.py**.

Siempre que hereden de `rest_framework.permissions.BasePermission`, los permisos pueden componerse usando operadores bit a bit estándar de Python. Por ejemplo, `IsAuthenticatedOrReadOnly` podría escribirse:

```python
from rest_framework.permissions import BasePermission, IsAuthenticated, SAFE_METHODS
from rest_framework.response import Response
from rest_framework.views import APIView

class ReadOnly(BasePermission):
    def has_permission(self, request, view):
        return request.method in SAFE_METHODS

class ExampleView(APIView):
    permission_classes = [IsAuthenticated|ReadOnly]

    def get(self, request, format=None):
        content = {
            'status': 'solicitud fue permitida'
        }
        return Response(content)
```

**Nota:** soporta & (y), | (o) y ~ (no).

# Referencia de la API

## AllowAny

La clase de permisos `AllowAny` permitirá acceso sin restricciones, **independientemente de si la solicitud fue autenticada o no**.

Este permiso no es estrictamente necesario, ya que puedes lograr el mismo resultado usando una lista o tupla vacía para la configuración de permisos, pero puedes encontrar útil especificar esta clase porque hace la intención explícita.

## IsAuthenticated

La clase de permisos `IsAuthenticated` denegará el permiso a cualquier usuario no autenticado, y permitirá el permiso en caso contrario.

Este permiso es adecuado si quieres que tu API solo sea accesible para usuarios registrados.

## IsAdminUser

La clase de permisos `IsAdminUser` denegará el permiso a cualquier usuario, a menos que `user.is_staff` sea `True`, en cuyo caso se permitirá el permiso.

Este permiso es adecuado si quieres que tu API solo sea accesible para un subconjunto de administradores de confianza.

## IsAuthenticatedOrReadOnly

`IsAuthenticatedOrReadOnly` permitirá que los usuarios autenticados realicen cualquier solicitud. Las solicitudes de usuarios no autenticados solo se permitirán si el método de solicitud es uno de los métodos "seguros": `GET`, `HEAD` u `OPTIONS`.

Este permiso es adecuado si quieres que tu API permita permisos de lectura a usuarios anónimos, y solo permita permisos de escritura a usuarios autenticados.

## DjangoModelPermissions

Esta clase de permisos se integra con los [permisos de modelo estándar][contribauth] de Django `django.contrib.auth`. Este permiso solo debe aplicarse a vistas que tienen una propiedad `.queryset` o un método `get_queryset()`. La autorización solo se concederá si el usuario _está autenticado_ y tiene asignados los _permisos de modelo relevantes_. El modelo apropiado se determina verificando `get_queryset().model` o `queryset.model`.

- Las solicitudes `POST` requieren que el usuario tenga el permiso `add` en el modelo.
- Las solicitudes `PUT` y `PATCH` requieren que el usuario tenga el permiso `change` en el modelo.
- Las solicitudes `DELETE` requieren que el usuario tenga el permiso `delete` en el modelo.

El comportamiento predeterminado también puede ser sobrescrito para soportar permisos de modelo personalizados. Por ejemplo, podrías querer incluir un permiso de modelo `view` para solicitudes `GET`.

Para usar permisos de modelo personalizados, sobrescribe `DjangoModelPermissions` y establece la propiedad `.perms_map`. Consulta el código fuente para más detalles.

## DjangoModelPermissionsOrAnonReadOnly

Similar a `DjangoModelPermissions`, pero también permite que los usuarios no autenticados tengan acceso de solo lectura a la API.

## DjangoObjectPermissions

Esta clase de permisos se integra con el [framework de permisos de objeto estándar][objectpermissions] de Django que permite permisos por objeto en modelos. Para usar esta clase de permisos, también necesitarás agregar un backend de permisos que soporte permisos a nivel de objeto, como [django-guardian][guardian].

Al igual que con `DjangoModelPermissions`, este permiso solo debe aplicarse a vistas que tienen una propiedad `.queryset` o un método `.get_queryset()`. La autorización solo se concederá si el usuario _está autenticado_ y tiene asignados los _permisos por objeto relevantes_ y los _permisos de modelo relevantes_.

- Las solicitudes `POST` requieren que el usuario tenga el permiso `add` en la instancia del modelo.
- Las solicitudes `PUT` y `PATCH` requieren que el usuario tenga el permiso `change` en la instancia del modelo.
- Las solicitudes `DELETE` requieren que el usuario tenga el permiso `delete` en la instancia del modelo.

Ten en cuenta que `DjangoObjectPermissions` **no** requiere el paquete `django-guardian`, y debería soportar otros backends a nivel de objeto igualmente bien.

Al igual que con `DjangoModelPermissions`, puedes usar permisos de modelo personalizados sobrescribiendo `DjangoObjectPermissions` y estableciendo la propiedad `.perms_map`. Consulta el código fuente para más detalles.

---

**Nota**: Si necesitas permisos `view` a nivel de objeto para solicitudes `GET`, `HEAD` y `OPTIONS` y estás usando django-guardian para tu backend de permisos a nivel de objeto, querrás considerar usar la clase `DjangoObjectPermissionsFilter` proporcionada por el [paquete `djangorestframework-guardian2`][django-rest-framework-guardian2]. Asegura que los endpoints de lista solo devuelvan resultados incluyendo objetos para los cuales el usuario tiene los permisos de vista apropiados.

# Permisos personalizados

Para implementar un permiso personalizado, sobrescribe `BasePermission` e implementa uno o ambos de los siguientes métodos:

- `.has_permission(self, request, view)`
- `.has_object_permission(self, request, view, obj)`

Los métodos deben devolver `True` si la solicitud debe ser concedida el acceso, y `False` en caso contrario.

Si necesitas probar si una solicitud es una operación de lectura o de escritura, debes verificar el método de solicitud contra la constante `SAFE_METHODS`, que es una tupla que contiene `'GET'`, `'OPTIONS'` y `'HEAD'`. Por ejemplo:

```python
if request.method in permissions.SAFE_METHODS:
    # Verificar permisos para solicitud de solo lectura
else:
    # Verificar permisos para solicitud de escritura
```

---

**Nota**: El método `has_object_permission` a nivel de instancia solo será llamado si las verificaciones `has_permission` a nivel de vista ya han pasado. También ten en cuenta que para que las verificaciones a nivel de instancia se ejecuten, el código de la vista debe llamar explícitamente a `.check_object_permissions(request, obj)`. Si estás usando las vistas genéricas, esto será manejado automáticamente. (Las vistas basadas en funciones necesitarán verificar permisos de objeto explícitamente, lanzando `PermissionDenied` en caso de fallo.)

---

Los permisos personalizados lanzarán una excepción `PermissionDenied` si la prueba falla. Para cambiar el mensaje de error asociado con la excepción, implementa un atributo `message` directamente en tu permiso personalizado. De lo contrario, se usará el atributo `default_detail` de `PermissionDenied`. De manera similar, para cambiar el identificador de código asociado con la excepción, implementa un atributo `code` directamente en tu permiso personalizado; de lo contrario, se usará el atributo `default_code` de `PermissionDenied`.

```python
from rest_framework import permissions

class CustomerAccessPermission(permissions.BasePermission):
    message = 'No se permite agregar clientes.'

    def has_permission(self, request, view):
            ...
```

## Ejemplos

El siguiente es un ejemplo de una clase de permisos que verifica la dirección IP de la solicitud entrante contra una lista de bloqueo, y deniega la solicitud si la IP ha sido bloqueada.

```python
from rest_framework import permissions

class BlocklistPermission(permissions.BasePermission):
    """
    Verificación global de permisos para IPs bloqueadas.
    """

    def has_permission(self, request, view):
        ip_addr = request.META['REMOTE_ADDR']
        blocked = Blocklist.objects.filter(ip_addr=ip_addr).exists()
        return not blocked
```

Además de los permisos globales, que se ejecutan contra todas las solicitudes entrantes, también puedes crear permisos a nivel de objeto, que solo se ejecutan contra operaciones que afectan a una instancia de objeto particular. Por ejemplo:

```python
class IsOwnerOrReadOnly(permissions.BasePermission):
    """
    Permiso a nivel de objeto para permitir solo a los propietarios de un objeto editarlo.
    Asume que la instancia del modelo tiene un atributo `owner`.
    """

    def has_object_permission(self, request, view, obj):
        # Los permisos de lectura están permitidos para cualquier solicitud,
        # así que siempre permitiremos solicitudes GET, HEAD u OPTIONS.
        if request.method in permissions.SAFE_METHODS:
            return True

        # La instancia debe tener un atributo llamado `owner`.
        return obj.owner == request.user
```

Ten en cuenta que las vistas genéricas verificarán los permisos apropiados a nivel de objeto, pero si estás escribiendo tus propias vistas personalizadas, necesitarás asegurarte de verificar las verificaciones de permisos a nivel de objeto tú mismo. Puedes hacerlo llamando a `self.check_object_permissions(request, obj)` desde la vista una vez que tienes la instancia del objeto. Esta llamada lanzará una `APIException` apropiada si alguna verificación de permisos a nivel de objeto falla, y de lo contrario simplemente retornará.

También ten en cuenta que las vistas genéricas solo verificarán los permisos a nivel de objeto para vistas que recuperan una sola instancia de modelo. Si requieres filtrado a nivel de objeto de vistas de lista, necesitarás filtrar el queryset por separado. Consulta la [documentación de filtrado][filtering] para más detalles.

# Resumen de métodos de restricción de acceso

REST framework ofrece tres métodos diferentes para personalizar las restricciones de acceso caso por caso. Estos se aplican en diferentes escenarios y tienen diferentes efectos y limitaciones.

- `queryset`/`get_queryset()`: Limita la visibilidad general de los objetos existentes de la base de datos. El queryset limita qué objetos serán listados y qué objetos pueden ser modificados o eliminados. El método `get_queryset()` puede aplicar diferentes querysets basados en la acción actual.
- `permission_classes`/`get_permissions()`: Verificaciones generales de permisos basadas en la acción actual, solicitud y objeto objetivo. Los permisos a nivel de objeto solo pueden aplicarse a acciones de recuperación, modificación y eliminación. Las verificaciones de permisos para lista y creación se aplicarán a todo el tipo de objeto. (En caso de lista: sujeto a restricciones en el queryset.)
- `serializer_class`/`get_serializer()`: Restricciones a nivel de instancia que se aplican a todos los objetos en entrada y salida. El serializador puede tener acceso al contexto de la solicitud. El método `get_serializer()` puede aplicar diferentes serializadores basados en la acción actual.

La siguiente tabla lista los métodos de restricción de acceso y el nivel de control que ofrecen sobre qué acciones.

|                                   | `queryset` | `permission_classes` | `serializer_class` |
| --------------------------------- | ---------- | -------------------- | ------------------ |
| Acción: list                      | global     | global               | a nivel de objeto\*     |
| Acción: create                    | no         | global               | a nivel de objeto       |
| Acción: retrieve                  | global     | a nivel de objeto         | a nivel de objeto       |
| Acción: update                    | global     | a nivel de objeto         | a nivel de objeto       |
| Acción: partial_update            | global     | a nivel de objeto         | a nivel de objeto       |
| Acción: destroy                   | global     | a nivel de objeto         | no                 |
| Puede referenciar acción en decisión  | no\*\*     | sí                  | no\*\*             |
| Puede referenciar solicitud en decisión | no\*\*     | sí                  | sí                |

- Una clase Serializer no debería lanzar `PermissionDenied` en una acción de lista, o toda la lista no sería devuelta.
- Los métodos `get__*()` tienen acceso a la vista actual y pueden devolver diferentes instancias de `Serializer` o `QuerySet` basadas en la solicitud o acción.

# Paquetes de terceros

Los siguientes paquetes de terceros también están disponibles.

## DRF - Access Policy

El paquete [Django REST - Access Policy][drf-access-policy] proporciona una forma de definir reglas de acceso complejas en clases de políticas declarativas que se adjuntan a viewsets o vistas basadas en funciones. Las políticas se definen en JSON en un formato similar a las políticas de Identity & Access Management de AWS.

## Composed Permissions

El paquete [Composed Permissions][composed-permissions] proporciona una forma simple de definir objetos de permisos complejos y multi-nivel (con operadores lógicos), usando componentes pequeños y reutilizables.

## REST Condition

El paquete [REST Condition][rest-condition] es otra extensión para construir permisos complejos de forma simple y conveniente. La extensión te permite combinar permisos con operadores lógicos.

## DRY Rest Permissions

El paquete [DRY Rest Permissions][dry-rest-permissions] proporciona la capacidad de definir diferentes permisos para acciones predeterminadas y personalizadas individuales. Este paquete está hecho para aplicaciones con permisos que se derivan de relaciones definidas en el modelo de datos de la aplicación. También soporta que las verificaciones de permisos se devuelvan a una aplicación cliente a través del serializador de la API. Adicionalmente, soporta agregar permisos a las acciones de lista predeterminadas y personalizadas para restringir los datos que recuperan por usuario.

## Django Rest Framework Roles

El paquete [Django Rest Framework Roles][django-rest-framework-roles] facilita parametrizar tu API sobre múltiples tipos de usuarios.

## Rest Framework Roles

[Rest Framework Roles][rest-framework-roles] hace súper fácil proteger vistas basadas en roles. Lo más importante es que te permite desacoplar la lógica de accesibilidad de modelos y vistas de forma limpia y legible.

## Django REST Framework API Key

El paquete [Django REST Framework API Key][djangorestframework-api-key] proporciona clases de permisos, modelos y ayudantes para agregar autorización de clave API a tu API. Puede usarse para autorizar backends y servicios internos o de terceros (es decir, _máquinas_) que no tienen una cuenta de usuario. Las claves API se almacenan de forma segura usando la infraestructura de hashing de contraseñas de Django, y pueden ser vistas, editadas y revocadas en cualquier momento en el administrador de Django.

## Django Rest Framework Role Filters

El paquete [Django Rest Framework Role Filters][django-rest-framework-role-filters] proporciona filtrado simple sobre múltiples tipos de roles.

## Django Rest Framework PSQ

El paquete [Django Rest Framework PSQ][drf-psq] es una extensión que da soporte para tener **permission_classes**, **serializer_class** y **queryset** basados en acciones y dependientes de reglas basadas en permisos.
