# Schemas

> Un [schema] legible por máquina describe qué recursos están disponibles a través de la API, cuáles son sus URLs, cómo se representan y qué operaciones soportan.
>
> &mdash; Heroku, [JSON Schema for the Heroku Platform API][cite]

---

**Aviso de obsolescencia:**

El soporte integrado de REST framework para generar schemas de OpenAPI está
**en desuso** en favor de paquetes de terceros que pueden proporcionar esta
funcionalidad en su lugar. El soporte integrado se moverá a un paquete
separado y posteriormente se retirará en las próximas versiones.

Como reemplazo completo, recomendamos el paquete [drf-spectacular].
Tiene soporte extensivo para generar schemas de OpenAPI 3 desde
APIs de REST framework, con opciones tanto automáticas como personalizables disponibles.
Para más información, consulta
[Documenting your API](../topics/documenting-your-api.md#drf-spectacular).

---

Los schemas de API son una herramienta útil que permiten una variedad de casos de uso, incluyendo
generar documentación de referencia, o impulsar librerías cliente dinámicas que
puedan interactuar con tu API.

Django REST Framework proporciona soporte para la generación automática de
[OpenAPI][openapi].

## Vista General

La generación de schemas tiene varias partes móviles. Vale la pena tener una visión general:

- `SchemaGenerator` es una clase de alto nivel responsable de recorrer tus
  patrones de URL configurados, encontrar subclases de `APIView`, solicitar su
  representación de schema y compilar el objeto de schema final.
- `AutoSchema` encapsula todos los detalles necesarios para la introspección de schema por vista.
  Se adjunta a cada vista a través del atributo `schema`. Subclasificas
  `AutoSchema` para personalizar tu schema.
- El comando de gestión `generateschema` te permite generar un schema estático
  sin conexión.
- Alternativamente, puedes enrutar `SchemaView` para generar y servir
  dinámicamente tu schema.
- `settings.DEFAULT_SCHEMA_CLASS` te permite especificar una subclase de `AutoSchema`
  para que sirva como predeterminada de tu proyecto.

Las siguientes secciones explican más.

## Generando un Schema de OpenAPI

### Instalar dependencias

    pip install pyyaml uritemplate inflection

- `pyyaml` se usa para generar schema en formato OpenAPI basado en YAML.
- `uritemplate` se usa internamente para obtener parámetros en la ruta.
- `inflection` se usa para pluralizar operaciones más apropiadamente en los endpoints de lista.

### Generando un schema estático con el comando de gestión `generateschema`

Si tu schema es estático, puedes usar el comando de gestión `generateschema`:

```bash
./manage.py generateschema --file openapi-schema.yml
```

Una vez que has generado un schema de esta manera, puedes anotarlo con cualquier
información adicional que no pueda ser inferida automáticamente por el generador de schema.

Puedes querer verificar tu schema de API en control de versiones y actualizarlo
con cada nueva versión, o servir el schema de API desde los medios estáticos de tu sitio.

### Generando un schema dinámico con `SchemaView`

Si requieres un schema dinámico, porque las elecciones de clave foránea dependen de valores
de base de datos, por ejemplo, puedes enrutar un `SchemaView` que generará y servirá
tu schema bajo demanda.

Para enrutar un `SchemaView`, usa el helper `get_schema_view()`.

En `urls.py`:

```python
from rest_framework.schemas import get_schema_view

urlpatterns = [
    # ...
    # Usa el helper `get_schema_view()` para agregar un `SchemaView` a las URLs del proyecto.
    #   * Los parámetros `title` y `description` se pasan a `SchemaGenerator`.
    #   * Proporciona nombre de vista para usar con `reverse()`.
    path(
        "openapi",
        get_schema_view(
            title="Your Project", description="API for all things …", version="1.0.0"
        ),
        name="openapi-schema",
    ),
    # ...
]
```

#### `get_schema_view()`

El helper `get_schema_view()` toma los siguientes argumentos de palabra clave:

- `title`: Puede usarse para proporcionar un título descriptivo para la definición del schema.
- `description`: Texto descriptivo más largo.
- `version`: La versión de la API.
- `url`: Puede usarse para pasar una URL base canónica para el schema.

```python
schema_view = get_schema_view(
    title='Server Monitoring API',
    url='https://www.example.org/api/'
)
```

- `urlconf`: Una cadena que representa la ruta de importación a la configuración de URL para la que
  quieres generar un schema de API. Esto por defecto es el valor de la configuración
  `ROOT_URLCONF` de Django.

```python
      schema_view = get_schema_view(
          title='Server Monitoring API',
          url='https://www.example.org/api/',
          urlconf='myproject.urls'
      )
```

- `patterns`: Lista de patrones de URL para limitar la introspección del schema. Si solo
  quieres que las URLs `myproject.api` se expongan en el schema:

```python
schema_url_patterns = [
    path('api/', include('myproject.api.urls')),
]

schema_view = get_schema_view(
    title='Server Monitoring API',
    url='https://www.example.org/api/',
    patterns=schema_url_patterns,
)
```

- `public`: Puede usarse para especificar si el schema debe omitir los permisos de las vistas. Por defecto es False

- `generator_class`: Puede usarse para especificar una subclase de `SchemaGenerator` que se
  pasará al `SchemaView`.
- `authentication_classes`: Puede usarse para especificar lista de clases de autenticación
  que se aplicarán al endpoint del schema. Por defecto es
  `settings.DEFAULT_AUTHENTICATION_CLASSES`
- `permission_classes`: Puede usarse para especificar lista de clases de permisos
  que se aplicarán al endpoint del schema. Por defecto es
  `settings.DEFAULT_PERMISSION_CLASSES`.
- `renderer_classes`: Puede usarse para pasar conjunto de clases de renderer que pueden
  usarse para renderizar el endpoint raíz de la API.

## SchemaGenerator

**Personalización a nivel de schema**

```python
from rest_framework.schemas.openapi import SchemaGenerator
```

`SchemaGenerator` es una clase que recorre una lista de patrones de URL enrutados, solicita
el schema para cada vista y colapsa el schema de OpenAPI resultante.

Típicamente no necesitarás instanciar `SchemaGenerator` tú mismo, pero puedes
hacerlo así:

```python
generator = SchemaGenerator(title='Stock Prices API')
```

Argumentos:

- `title` **requerido**: El nombre de la API.
- `description`: Texto descriptivo más largo.
- `version`: La versión de la API. Por defecto es `0.1.0`.
- `url`: La URL raíz del schema de API. Esta opción no se requiere a menos que el schema se incluya bajo prefijo de ruta.
- `patterns`: Una lista de URLs para inspeccionar al generar el schema. Por defecto es la configuración de URL del proyecto.
- `urlconf`: Un nombre de módulo de configuración de URL para usar al generar el schema. Por defecto es `settings.ROOT_URLCONF`.

Para personalizar el schema de nivel superior, subclasifica
`rest_framework.schemas.openapi.SchemaGenerator` y proporciona tu subclase
como argumento al comando `generateschema` o la función helper
`get_schema_view()`.

### get_schema(self, request=None, public=False)

Devuelve un diccionario que representa el schema de OpenAPI:

```python
generator = SchemaGenerator(title='Stock Prices API')
schema = generator.get_schema()
```

El argumento `request` es opcional, y puede usarse si quieres aplicar
permisos por usuario a la generación del schema resultante.

Este es un buen punto para anular si quieres personalizar el diccionario
generado. Por ejemplo, podrías desear añadir términos de servicio al [objeto
`info` de nivel superior][info-object]:

```python
class TOSSchemaGenerator(SchemaGenerator):
    def get_schema(self, *args, **kwargs):
        schema = super().get_schema(*args, **kwargs)
        schema["info"]["termsOfService"] = "https://example.com/tos.html"
        return schema
```

## AutoSchema

**Personalización por Vista**

```python
from rest_framework.schemas.openapi import AutoSchema
```

Por defecto, la introspección de vista es realizada por una instancia de `AutoSchema`
accesible a través del atributo `schema` en `APIView`.

```python
auto_schema = some_view.schema
```

`AutoSchema` proporciona los elementos de OpenAPI necesarios para cada vista, método de solicitud
y ruta:

- Una lista de [componentes de OpenAPI][openapi-components]. En términos de DRF estos son
  mapeos de serializadores que describen cuerpos de solicitud y respuesta.
- El [objeto de operación de OpenAPI][openapi-operation] apropiado que describe
  el endpoint, incluyendo parámetros de ruta y consulta para paginación, filtrado,
  etc.

```python
components = auto_schema.get_components(...)
operation = auto_schema.get_operation(...)
```

Al compilar el schema, `SchemaGenerator` llama a `get_components()` y
`get_operation()` para cada vista, método permitido y ruta.

---

**Nota**: La introspección automática de componentes, y muchos parámetros
de operación se basa en atributos y métodos relevantes de
`GenericAPIView`: `get_serializer()`, `pagination_class`, `filter_backends`,
etc. Para subclases básicas de `APIView`, la introspección predeterminada es esencialmente limitada a
parámetros de ruta de kwarg de URL por esta razón.

---

`AutoSchema` encapsula la introspección de vista necesaria para la generación de schema.
Debido a esto, toda la lógica de generación de schema se mantiene en un solo lugar,
en lugar de extenderse por las APIs de vista, serializador y campo ya extensas.

Manteniendo este patrón, intenta no dejar que la lógica del schema se filtre en tus
propias vistas, serializadores o campos al personalizar la generación del schema. Podrías
sentir la tentación de hacer algo así:

```python
class CustomSchema(AutoSchema):
    """
    Subclase de AutoSchema usando schema_extra_info en la vista.
    """

    ...


class CustomView(APIView):
    schema = CustomSchema()
    schema_extra_info = ...  # información extra
```

Aquí, la subclase `AutoSchema` busca `schema_extra_info` en
la vista. Esto está _bien_ (en realidad no hace daño) pero significa que terminarás con
tu lógica de schema dispersa en varios lugares diferentes.

En su lugar, intenta subclasificar `AutoSchema` de manera que `extra_info` no se filtre
hacia la vista:

```python
class BaseSchema(AutoSchema):
    """
    Subclase de AutoSchema que sabe cómo usar extra_info.
    """

    ...


class CustomSchema(BaseSchema):
    extra_info = ...  # información extra


class CustomView(APIView):
    schema = CustomSchema()
```

Este estilo es ligeramente más verboso pero mantiene la encapsulación de
código relacionado con schema. Es más _cohesivo_ en la _jerga_. Mantendrá
el resto de tu código de API más ordenado.

Si una opción se aplica a muchas clases de vista, en lugar de crear una subclase
específica por vista, puedes encontrar más conveniente permitir especificar
la opción como un kwarg `__init__()` a tu subclase base `AutoSchema`:

```python
class CustomSchema(BaseSchema):
    def __init__(self, **kwargs):
        # almacenar extra_info para después
        self.extra_info = kwargs.pop("extra_info")
        super().__init__(**kwargs)


class CustomView(APIView):
    schema = CustomSchema(extra_info=...)  # información extra
```

Esto te ahorra tener que crear una subclase personalizada por vista para una opción comúnmente usada.

No todos los métodos `AutoSchema` exponen kwargs `__init__()` relacionados, pero aquellos para
opciones más comúnmente necesarias sí lo hacen.

### Métodos de `AutoSchema`

#### `get_components()`

Genera componentes de OpenAPI que describen cuerpos de solicitud y respuesta,
derivando sus propiedades del serializador.

Devuelve un diccionario mapeando nombre de componente a la representación
generada. Por defecto esto tiene solo un par único pero puedes anular
`get_components()` para devolver múltiples pares si tu vista usa múltiples
serializadores.

#### `get_component_name()`

Computa el nombre del componente desde el serializador.

Puedes ver advertencias si tu API tiene nombres de componente duplicados. Si es así, puedes anular `get_component_name()` o pasar el kwarg `component_name` `__init__()` (ver abajo) para proporcionar nombres diferentes.

#### `get_reference()`

Devuelve una referencia al componente del serializador. Esto puede ser útil si anulas `get_schema()`.

#### `map_serializer()`

Mapea serializadores a sus representaciones de OpenAPI.

La mayoría de los serializadores deberían conformar al tipo `object` estándar de OpenAPI, pero puedes
desear anular `map_serializer()` para personalizar esto u otros
campos a nivel de serializador.

#### `map_field()`

Mapea campos individuales de serializador a su representación de schema. La implementación base
manejará los campos predeterminados que Django REST Framework proporciona.

Para instancias de `SerializerMethodField`, para las cuales el schema es desconocido, o subclases de campo personalizadas deberías anular `map_field()` para generar el schema correcto:

```python
class CustomSchema(AutoSchema):
    """Extensión de ``AutoSchema`` para agregar soporte para schemas de campo personalizados."""

    def map_field(self, field):
        # Manejar SerializerMethodFields o campos personalizados aquí...
        # ...
        return super().map_field(field)
```

Los autores de paquetes de terceros deberían apuntar a proporcionar una subclase de `AutoSchema`,
y un mixin, anulando `map_field()` para que los usuarios puedan generar fácilmente schemas
para sus campos personalizados.

#### `get_tags()`

OpenAPI agrupa operaciones por etiquetas. Por defecto las etiquetas se toman del primer segmento
de ruta de la URL enrutada. Por ejemplo, una URL como `/users/{id}/` generará
la etiqueta `users`.

Puedes pasar un kwarg `__init__()` para especificar manualmente etiquetas (ver abajo), o
anular `get_tags()` para proporcionar lógica personalizada.

#### `get_operation()`

Devuelve el [objeto de operación de OpenAPI][openapi-operation] que describe
el endpoint, incluyendo parámetros de ruta y consulta para paginación, filtrado, etc.

Junto con `get_components()`, este es el punto de entrada principal a la
introspección de vista.

#### `get_operation_id()`

Debe haber un [operationid][openapi-operationid] único para cada operación.
Por defecto `operationId` se deduce del nombre del modelo, nombre del serializador o
nombre de la vista. El operationId se ve como "listItems", "retrieveItem",
"updateItem", etc. El `operationId` es camelCase por convención.

#### `get_operation_id_base()`

Si tienes varias vistas con el mismo nombre de modelo, puedes ver operationIds
duplicados.

Para solucionar esto, puedes anular `get_operation_id_base()` para
proporcionar una base diferente para la parte del nombre del ID.

#### `get_serializer()`

Si la vista ha implementado `get_serializer()`, devuelve el resultado.

#### `get_request_serializer()`

Por defecto devuelve `get_serializer()` pero puede anularse para
diferenciar entre objetos de solicitud y respuesta.

#### `get_response_serializer()`

Por defecto devuelve `get_serializer()` pero puede anularse para
diferenciar entre objetos de solicitud y respuesta.

### `AutoSchema.__init__()` kwargs

`AutoSchema` proporciona varios kwargs `__init__()` que pueden usarse para
personalizaciones comunes, si los valores generados predeterminados no son apropiados.

Los kwargs disponibles son:

- `tags`: Especifica una lista de etiquetas.
- `component_name`: Especifica el nombre del componente.
- `operation_id_base`: Especifica la parte del nombre del recurso de los IDs de operación.

Pasas los kwargs al declarar la instancia de `AutoSchema` en tu vista:

```python
class PetDetailView(generics.RetrieveUpdateDestroyAPIView):
    schema = AutoSchema(
        tags=['Pets'],
        component_name='Pet',
        operation_id_base='Pet',
    )
    ...
```

Asumiendo un modelo `Pet` y un serializador `PetSerializer`, los kwargs en este
ejemplo probablemente no se necesiten. A menudo, sin embargo, necesitarás pasar kwargs
si tienes múltiples vistas apuntando al mismo modelo, o tienes múltiples vistas con
serializadores de nombres idénticos.

Si tus vistas tienen personalizaciones relacionadas que se necesitan frecuentemente, puedes
crear una subclase base `AutoSchema` para tu proyecto que tome adicionales
kwargs `__init__()` para ahorrar la subclasificación de `AutoSchema` para cada vista.
