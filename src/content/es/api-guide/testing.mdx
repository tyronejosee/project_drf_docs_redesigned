# Pruebas

> El código sin pruebas está roto por diseño.
>
> &mdash; [Jacob Kaplan-Moss][cite]

REST framework incluye algunas clases de ayuda que extienden el framework de pruebas existente de Django, y mejoran el soporte para hacer solicitudes de API.

# APIRequestFactory

Extiende [la clase `RequestFactory` existente de Django][requestfactory].

## Creando solicitudes de prueba

La clase `APIRequestFactory` soporta una API casi idéntica a la clase `RequestFactory` estándar de Django. Esto significa que los métodos estándar `.get()`, `.post()`, `.put()`, `.patch()`, `.delete()`, `.head()` y `.options()` están todos disponibles.

```python
from rest_framework.test import APIRequestFactory

# Usando la API estándar de RequestFactory para crear una solicitud POST de formulario
factory = APIRequestFactory()
request = factory.post('/notes/', {'title': 'nueva idea'})

# Usando la API estándar de RequestFactory para codificar datos JSON
request = factory.post('/notes/', {'title': 'nueva idea'}, content_type='application/json')
```

#### Usando el argumento `format`

Los métodos que crean un cuerpo de solicitud, como `post`, `put` y `patch`, incluyen un argumento `format`, que facilita generar solicitudes usando un conjunto amplio de formatos de solicitud. Al usar este argumento, la fábrica seleccionará un renderizador apropiado y su `content_type` configurado. Por ejemplo:

```python
# Crear una solicitud POST JSON
factory = APIRequestFactory()
request = factory.post('/notes/', {'title': 'nueva idea'}, format='json')
```

Por defecto los formatos disponibles son `'multipart'` y `'json'`. Para compatibilidad con el `RequestFactory` existente de Django, el formato predeterminado es `'multipart'`.

Para soportar un conjunto más amplio de formatos de solicitud, o cambiar el formato predeterminado, [ver la sección de configuración][configuration].

#### Codificando explícitamente el cuerpo de la solicitud

Si necesitas codificar explícitamente el cuerpo de la solicitud, puedes hacerlo estableciendo el flag `content_type`. Por ejemplo:

```python
request = factory.post('/notes/', yaml.dump({'title': 'nueva idea'}), content_type='application/yaml')
```

#### PUT y PATCH con datos de formulario

Una diferencia que vale la pena notar entre el `RequestFactory` de Django y el `APIRequestFactory` de REST framework es que los datos de formulario multipart serán codificados para métodos distintos a solo `.post()`.

Por ejemplo, usando `APIRequestFactory`, puedes hacer una solicitud PUT de formulario así:

```python
factory = APIRequestFactory()
request = factory.put('/notes/547/', {'title': 'recordar email a dave'})
```

Usando el `RequestFactory` de Django, necesitarías codificar explícitamente los datos tú mismo:

```python
from django.test.client import encode_multipart, RequestFactory

factory = RequestFactory()
data = {'title': 'recordar email a dave'}
content = encode_multipart('BoUnDaRyStRiNg', data)
content_type = 'multipart/form-data; boundary=BoUnDaRyStRiNg'
request = factory.put('/notes/547/', content, content_type=content_type)
```

## Forzando autenticación

Al probar vistas directamente usando una fábrica de solicitudes, a menudo es conveniente poder autenticar directamente la solicitud, en lugar de tener que construir las credenciales de autenticación correctas.

Para forzar la autenticación de una solicitud, usa el método `force_authenticate()`.

```python
from rest_framework.test import force_authenticate

factory = APIRequestFactory()
user = User.objects.get(username='olivia')
view = AccountDetail.as_view()

# Hacer una solicitud autenticada a la vista...
request = factory.get('/accounts/django-superstars/')
force_authenticate(request, user=user)
response = view(request)
```

La firma del método es `force_authenticate(request, user=None, token=None)`. Al hacer la llamada, se pueden establecer uno o ambos del usuario y token.

Por ejemplo, al forzar la autenticación usando un token, podrías hacer algo como lo siguiente:

```python
user = User.objects.get(username='olivia')
request = factory.get('/accounts/django-superstars/')
force_authenticate(request, user=user, token=user.auth_token)
```

---

**Nota**: `force_authenticate` establece directamente `request.user` a la instancia `user` en memoria. Si estás reutilizando la misma instancia `user` a través de múltiples pruebas que actualizan el estado guardado del `user`, podrías necesitar llamar a [`refresh_from_db()`][refresh_from_db_docs] entre pruebas.

---

**Nota**: Al usar `APIRequestFactory`, el objeto que se devuelve es el `HttpRequest` estándar de Django, y no el objeto `Request` de REST framework, que solo se genera una vez que se llama a la vista.

Esto significa que establecer atributos directamente en el objeto de solicitud puede no siempre tener el efecto que esperas. Por ejemplo, establecer `.token` directamente no tendrá efecto, y establecer `.user` directamente solo funcionará si se está usando autenticación de sesión.

```python
# La solicitud solo se autenticará si `SessionAuthentication` está en uso.
request = factory.get('/accounts/django-superstars/')
request.user = user
response = view(request)
```

---

## Forzando validación CSRF

Por defecto, las solicitudes creadas con `APIRequestFactory` no tendrán validación CSRF aplicada cuando se pasen a una vista de REST framework. Si necesitas activar explícitamente la validación CSRF, puedes hacerlo estableciendo el flag `enforce_csrf_checks` al instanciar la fábrica.

```python
factory = APIRequestFactory(enforce_csrf_checks=True)
```

---

**Nota**: Vale la pena notar que el `RequestFactory` estándar de Django no necesita incluir esta opción, porque al usar Django regular la validación CSRF tiene lugar en el middleware, que no se ejecuta al probar vistas directamente. Al usar REST framework, la validación CSRF tiene lugar dentro de la vista, así que la fábrica de solicitudes necesita deshabilitar las verificaciones CSRF a nivel de vista.

# APIClient

Extiende [la clase `Client` existente de Django][client].

## Haciendo solicitudes

La clase `APIClient` soporta la misma interfaz de solicitud que la clase `Client` estándar de Django. Esto significa que los métodos estándar `.get()`, `.post()`, `.put()`, `.patch()`, `.delete()`, `.head()` y `.options()` están todos disponibles. Por ejemplo:

```python
from rest_framework.test import APIClient

client = APIClient()
client.post('/notes/', {'title': 'nueva idea'}, format='json')
```

Para soportar un conjunto más amplio de formatos de solicitud, o cambiar el formato predeterminado, [ver la sección de configuración][configuration].

## Autenticando

#### .login(**kwargs)

El método `login` funciona exactamente como lo hace con la clase `Client` regular de Django. Esto te permite autenticar solicitudes contra cualquier vista que incluya `SessionAuthentication`.

```python
# Hacer todas las solicitudes en el contexto de una sesión iniciada.
client = APIClient()
client.login(username='lauren', password='secret')
```

Para cerrar sesión, llama al método `logout` como de costumbre.

```python
# Cerrar sesión
client.logout()
```

El método `login` es apropiado para probar APIs que usan autenticación de sesión, por ejemplo sitios web que incluyen interacción AJAX con la API.

#### .credentials(**kwargs)

El método `credentials` puede usarse para establecer encabezados que luego se incluirán en todas las solicitudes subsiguientes del cliente de prueba.

```python
from rest_framework.authtoken.models import Token
from rest_framework.test import APIClient

# Incluir un encabezado `Authorization:` apropiado en todas las solicitudes.
token = Token.objects.get(user__username='lauren')
client = APIClient()
client.credentials(HTTP_AUTHORIZATION='Token ' + token.key)
```

Ten en cuenta que llamar a `credentials` una segunda vez sobrescribe cualquier credencial existente. Puedes desestablecer cualquier credencial existente llamando al método sin argumentos.

```python
# Dejar de incluir cualquier credencial
client.credentials()
```

El método `credentials` es apropiado para probar APIs que requieren encabezados de autenticación, como autenticación básica, autenticación OAuth1a y OAuth2, y esquemas simples de autenticación por token.

#### .force_authenticate(user=None, token=None)

A veces podrías querer omitir completamente la autenticación y forzar que todas las solicitudes del cliente de prueba sean tratadas automáticamente como autenticadas.

Esto puede ser un atajo útil si estás probando la API pero no quieres tener que construir credenciales de autenticación válidas para hacer solicitudes de prueba.

```python
user = User.objects.get(username='lauren')
client = APIClient()
client.force_authenticate(user=user)
```

Para desautenticar solicitudes subsiguientes, llama a `force_authenticate` estableciendo el usuario y/o token a `None`.

```python
client.force_authenticate(user=None)
```

## Validación CSRF

Por defecto la validación CSRF no se aplica al usar `APIClient`. Si necesitas habilitar explícitamente la validación CSRF, puedes hacerlo estableciendo el flag `enforce_csrf_checks` al instanciar el cliente.

```python
client = APIClient(enforce_csrf_checks=True)
```

Como de costumbre, la validación CSRF solo se aplicará a cualquier vista autenticada por sesión. Esto significa que la validación CSRF solo ocurrirá si el cliente ha iniciado sesión llamando a `login()`.

# RequestsClient

REST framework también incluye un cliente para interactuar con tu aplicación
usando la popular biblioteca de Python, `requests`. Esto puede ser útil si:

- Esperas interactuar con la API principalmente desde otro servicio Python,
  y quieres probar el servicio al mismo nivel que el cliente verá.
- Quieres escribir pruebas de tal manera que también puedan ejecutarse contra un entorno de staging
  o de producción. (Ver "Pruebas en vivo" abajo.)

Esto expone exactamente la misma interfaz que si estuvieras usando una sesión de requests
directamente.

```python
from rest_framework.test import RequestsClient

client = RequestsClient()
response = client.get('http://testserver/users/')
assert response.status_code == 200
```

Ten en cuenta que el cliente de solicitudes requiere que pases URLs completamente calificadas.

## RequestsClient y trabajando con la base de datos

La clase `RequestsClient` es útil si quieres escribir pruebas que interactúen únicamente con la interfaz del servicio. Esto es un poco más estricto que usar el cliente de prueba estándar de Django, ya que significa que todas las interacciones deberían ser a través de la API.

Si estás usando `RequestsClient`, querrás asegurar que la configuración de prueba y las aserciones de resultados se realicen como llamadas de API regulares, en lugar de interactuar directamente con los modelos de la base de datos. Por ejemplo, en lugar de verificar que `Customer.objects.count() == 3`, listarías el endpoint de clientes y asegurarías que contiene tres registros.

## Encabezados y Autenticación con RequestsClient

Los encabezados personalizados y las credenciales de autenticación pueden proporcionarse de la misma manera
que [al usar una instancia estándar de `requests.Session`][session_objects].

```python
from requests.auth import HTTPBasicAuth

client.auth = HTTPBasicAuth('user', 'pass')
client.headers.update({'x-test': 'true'})
```

## CSRF

Si estás usando `SessionAuthentication`, entonces necesitarás incluir un token CSRF
para cualquier solicitud `POST`, `PUT`, `PATCH` o `DELETE`.

Puedes hacerlo siguiendo el mismo flujo que un cliente basado en JavaScript usaría.
Primero, haz una solicitud `GET` para obtener un token CSRF, luego presenta ese
token en la siguiente solicitud.

Por ejemplo...

```python
client = RequestsClient()

# Obtener un token CSRF.
response = client.get('http://testserver/homepage/')
assert response.status_code == 200
csrftoken = response.cookies['csrftoken']

# Interactuar con la API.
response = client.post('http://testserver/organisations/', json={
    'name': 'MegaCorp',
    'status': 'active'
}, headers={'X-CSRFToken': csrftoken})
assert response.status_code == 200
```

## Pruebas en vivo

Con un uso cuidadoso, tanto el `RequestsClient` como el `CoreAPIClient` proporcionan
la capacidad de escribir casos de prueba que pueden ejecutarse ya sea en desarrollo, o ejecutarse
directamente contra tu servidor de staging o entorno de producción.

Usar este estilo para crear pruebas básicas de algunas piezas centrales de funcionalidad es
una manera poderosa de validar tu servicio en vivo. Hacerlo puede requerir alguna atención
cuidadosa a la configuración y desmontaje para asegurar que las pruebas se ejecuten de una manera que no
afecten directamente los datos del cliente.

# CoreAPIClient

El CoreAPIClient te permite interactuar con tu API usando la biblioteca de cliente
de Python `coreapi`.

```python
# Obtener el esquema de la API
client = CoreAPIClient()
schema = client.get('http://testserver/schema/')

# Crear una nueva organización
params = {'name': 'MegaCorp', 'status': 'active'}
client.action(schema, ['organisations', 'create'], params)

# Asegurar que la organización existe en el listado
data = client.action(schema, ['organisations', 'list'])
assert(len(data) == 1)
assert(data == [{'name': 'MegaCorp', 'status': 'active'}])
```

## Encabezados y Autenticación con CoreAPIClient

Los encabezados personalizados y la autenticación pueden usarse con `CoreAPIClient` de una
manera similar a con `RequestsClient`.

```python
from requests.auth import HTTPBasicAuth

client = CoreAPIClient()
client.session.auth = HTTPBasicAuth('user', 'pass')
client.session.headers.update({'x-test': 'true'})
```

# Casos de prueba de API

REST framework incluye las siguientes clases de casos de prueba, que reflejan las [clases de casos de prueba existentes de Django][provided_test_case_classes], pero usan `APIClient` en lugar del `Client` predeterminado de Django.

- `APISimpleTestCase`
- `APITransactionTestCase`
- `APITestCase`
- `APILiveServerTestCase`

**Ejemplo**

Puedes usar cualquiera de las clases de caso de prueba de REST framework como lo harías para las clases de caso de prueba regulares de Django. El atributo `self.client` será una instancia de `APIClient`.

```python
from django.urls import reverse
from rest_framework import status
from rest_framework.test import APITestCase
from myproject.apps.core.models import Account

class AccountTests(APITestCase):
    def test_create_account(self):
        """
        Asegurar que podemos crear un nuevo objeto de cuenta.
        """
        url = reverse('account-list')
        data = {'name': 'DabApps'}
        response = self.client.post(url, data, format='json')
        self.assertEqual(response.status_code, status.HTTP_201_CREATED)
        self.assertEqual(Account.objects.count(), 1)
        self.assertEqual(Account.objects.get().name, 'DabApps')
```

# URLPatternsTestCase

REST framework también proporciona una clase de caso de prueba para aislar `urlpatterns` en una base por clase. Ten en cuenta que esto hereda de `SimpleTestCase` de Django, y muy probablemente necesitará mezclarse con otra clase de caso de prueba.

**Ejemplo**

```python
from django.urls import include, path, reverse
from rest_framework.test import APITestCase, URLPatternsTestCase


class AccountTests(APITestCase, URLPatternsTestCase):
    urlpatterns = [
        path('api/', include('api.urls')),
    ]

    def test_create_account(self):
        """
        Asegurar que podemos crear un nuevo objeto de cuenta.
        """
        url = reverse('account-list')
        response = self.client.get(url, format='json')
        self.assertEqual(response.status_code, status.HTTP_200_OK)
        self.assertEqual(len(response.data), 1)
```

# Probando respuestas

## Verificando los datos de respuesta

Al verificar la validez de las respuestas de prueba, a menudo es más conveniente inspeccionar los datos con los que se creó la respuesta, en lugar de inspeccionar la respuesta completamente renderizada.

Por ejemplo, es más fácil inspeccionar `response.data`:

```python
response = self.client.get('/users/4/')
self.assertEqual(response.data, {'id': 4, 'username': 'lauren'})
```

En lugar de inspeccionar el resultado de parsear `response.content`:

```python
response = self.client.get('/users/4/')
self.assertEqual(json.loads(response.content), {'id': 4, 'username': 'lauren'})
```

## Renderizando respuestas

Si estás probando vistas directamente usando `APIRequestFactory`, las respuestas que se devuelven aún no estarán renderizadas, ya que el renderizado de respuestas de plantilla es realizado por el ciclo solicitud-respuesta interno de Django. Para acceder a `response.content`, primero necesitarás renderizar la respuesta.

```python
view = UserDetail.as_view()
request = factory.get('/users/4')
response = view(request, pk='4')
response.render()  # No se puede acceder a `response.content` sin esto.
self.assertEqual(response.content, '{"username": "lauren", "id": 4}')
```

# Configuración

## Estableciendo el formato predeterminado

El formato predeterminado usado para hacer solicitudes de prueba puede establecerse usando la clave de configuración `TEST_REQUEST_DEFAULT_FORMAT`. Por ejemplo, para usar siempre JSON para solicitudes de prueba por defecto en lugar de solicitudes de formulario multipart estándar, establece lo siguiente en tu archivo `settings.py`:

```python
REST_FRAMEWORK = {
    ...
    'TEST_REQUEST_DEFAULT_FORMAT': 'json'
}
```

## Estableciendo los formatos disponibles

Si necesitas probar solicitudes usando algo diferente a solicitudes multipart o json, puedes hacerlo estableciendo la configuración `TEST_REQUEST_RENDERER_CLASSES`.

Por ejemplo, para agregar soporte para usar `format='html'` en solicitudes de prueba, podrías tener algo como esto en tu archivo `settings.py`.

```python
REST_FRAMEWORK = {
    ...
    'TEST_REQUEST_RENDERER_CLASSES': [
        'rest_framework.renderers.MultiPartRenderer',
        'rest_framework.renderers.JSONRenderer',
        'rest_framework.renderers.TemplateHTMLRenderer'
    ]
}
```
