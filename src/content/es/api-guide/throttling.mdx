# Estrangulación

> HTTP/1.1 420 Enhance Your Calm
>
> [Respuesta de limitación de tasa de la API de Twitter][cite]

La estrangulación es similar a los [permisos], en que determina si una solicitud debería ser autorizada. Las estrangulaciones indican un estado temporal, y se usan para controlar la tasa de solicitudes que los clientes pueden hacer a una API.

Al igual que con los permisos, pueden usarse múltiples estrangulaciones. Tu API podría tener una estrangulación restrictiva para solicitudes no autenticadas, y una estrangulación menos restrictiva para solicitudes autenticadas.

Otro escenario donde podrías querer usar múltiples estrangulaciones sería si necesitas imponer diferentes restricciones en diferentes partes de la API, debido a que algunos servicios son particularmente intensivos en recursos.

También pueden usarse múltiples estrangulaciones si quieres imponer tanto tasas de estrangulación de ráfaga, como tasas de estrangulación sostenidas. Por ejemplo, podrías querer limitar un usuario a un máximo de 60 solicitudes por minuto, y 1000 solicitudes por día.

Las estrangulaciones no necesariamente se refieren solo a la limitación de tasa de solicitudes. Por ejemplo, un servicio de almacenamiento también podría necesitar estrangular contra el ancho de banda, y un servicio de datos pagado podría querer estrangular contra un cierto número de registros siendo accedidos.

**La estrangulación a nivel de aplicación que proporciona REST framework no debería considerarse una medida de seguridad o protección contra ataques de fuerza bruta o de denegación de servicio. Los actores maliciosos deliberados siempre podrán falsificar orígenes IP. Además de esto, las implementaciones de estrangulación incorporadas se implementan usando el framework de caché de Django, y usan operaciones no atómicas para determinar la tasa de solicitudes, lo que a veces puede resultar en alguna imprecisión.

La estrangulación a nivel de aplicación proporcionada por REST framework está destinada a implementar políticas como diferentes niveles de negocio y protecciones básicas contra el uso excesivo del servicio.**

## Cómo se determina la estrangulación

Al igual que con los permisos y la autenticación, la estrangulación en REST framework siempre se define como una lista de clases.

Antes de ejecutar el cuerpo principal de la vista, cada estrangulación en la lista es verificada.
Si alguna verificación de estrangulación falla, se lanzará una excepción `exceptions.Throttled`, y el cuerpo principal de la vista no se ejecutará.

## Configurando la política de estrangulación

La política de estrangulación predeterminada puede establecerse globalmente, usando las configuraciones `DEFAULT_THROTTLE_CLASSES` y `DEFAULT_THROTTLE_RATES`. Por ejemplo:

```python
REST_FRAMEWORK = {
    'DEFAULT_THROTTLE_CLASSES': [
        'rest_framework.throttling.AnonRateThrottle',
        'rest_framework.throttling.UserRateThrottle'
    ],
    'DEFAULT_THROTTLE_RATES': {
        'anon': '100/day',
        'user': '1000/day'
    }
}
```

Las tasas usadas en `DEFAULT_THROTTLE_RATES` pueden especificarse sobre un período de segundo, minuto, hora o día. El período debe especificarse después del separador `/` usando `s`, `m`, `h` o `d`, respectivamente. Para mayor claridad, se permiten unidades extendidas como `second`, `minute`, `hour`, `day` o incluso abreviaturas como `sec`, `min`, `hr`, ya que solo el primer carácter es relevante para identificar la tasa.

También puedes establecer la política de estrangulación en una base por vista o por viewset,
usando las vistas basadas en clases `APIView`.

```python
from rest_framework.response import Response
from rest_framework.throttling import UserRateThrottle
from rest_framework.views import APIView

class ExampleView(APIView):
    throttle_classes = [UserRateThrottle]

    def get(self, request, format=None):
        content = {
            'status': 'la solicitud fue permitida'
        }
        return Response(content)
```

Si estás usando el decorador `@api_view` con vistas basadas en funciones, puedes usar el siguiente decorador.

```python
@api_view(['GET'])
@throttle_classes([UserRateThrottle])
def example_view(request, format=None):
    content = {
        'status': 'la solicitud fue permitida'
    }
    return Response(content)
```

También es posible establecer clases de estrangulación para rutas que se crean usando el decorador `@action`.
Las clases de estrangulación establecidas de esta manera anularán cualquier configuración de clase a nivel de viewset.

```python
@action(detail=True, methods=["post"], throttle_classes=[UserRateThrottle])
def example_adhoc_method(request, pk=None):
    content = {
        'status': 'la solicitud fue permitida'
    }
    return Response(content)
```

## Cómo se identifican los clientes

El encabezado HTTP `X-Forwarded-For` y la variable WSGI `REMOTE_ADDR` se usan para identificar únicamente las direcciones IP de los clientes para la estrangulación. Si el encabezado `X-Forwarded-For` está presente, entonces se usará, de lo contrario se usará el valor de la variable `REMOTE_ADDR` del entorno WSGI.

Si necesitas identificar estrictamente direcciones IP de cliente únicas, primero necesitarás configurar el número de proxies de aplicación detrás de los cuales se ejecuta la API estableciendo la configuración `NUM_PROXIES`. Esta configuración debería ser un entero de cero o más. Si se establece en no cero, entonces la IP del cliente se identificará como la última dirección IP en el encabezado `X-Forwarded-For`, una vez que primero se hayan excluido las direcciones IP de los proxies de aplicación. Si se establece en cero, entonces el valor `REMOTE_ADDR` siempre se usará como la dirección IP identificadora.

Es importante entender que si configuras la configuración `NUM_PROXIES`, entonces todos los clientes detrás de una puerta de enlace [NAT](https://es.wikipedia.org/wiki/Traducci%C3%B3n_de_direcciones_de_red) única serán tratados como un solo cliente.

Más contexto sobre cómo funciona el encabezado `X-Forwarded-For`, e identificar una IP de cliente remota puede ser [encontrado aquí][identifying-clients].

## Configurando la caché

Las clases de estrangulación proporcionadas por REST framework usan el backend de caché de Django. Deberías asegurarte de haber establecido [configuraciones de caché][cache-setting] apropiadas. El valor predeterminado del backend `LocMemCache` debería estar bien para configuraciones simples. Ver la [documentación de caché de Django][cache-docs] para más detalles.

Si necesitas usar una caché diferente a `'default'`, puedes hacerlo creando una clase de estrangulación personalizada y estableciendo el atributo `cache`. Por ejemplo:

```python
from django.core.cache import caches

class CustomAnonRateThrottle(AnonRateThrottle):
    cache = caches['alternate']
```

Necesitarás recordar también establecer tu clase de estrangulación personalizada en la clave de configuración `'DEFAULT_THROTTLE_CLASSES'`, o usando el atributo de vista `throttle_classes`.

## Una nota sobre concurrencia

Las implementaciones de estrangulación incorporadas están abiertas a [condiciones de carrera][race], así que bajo alta concurrencia podrían permitir pasar algunas solicitudes adicionales.

Si tu proyecto depende de garantizar el número de solicitudes durante solicitudes concurrentes, necesitarás implementar tu propia clase de estrangulación.

# Referencia de la API

## AnonRateThrottle

`AnonRateThrottle` solo estrangulará a usuarios no autenticados. La dirección IP de la solicitud entrante se usa para generar una clave única contra la cual estrangular.

La tasa de solicitud permitida se determina de una de las siguientes (en orden de preferencia).

- La propiedad `rate` en la clase, que puede ser proporcionada sobrescribiendo `AnonRateThrottle` y estableciendo la propiedad.
- La configuración `DEFAULT_THROTTLE_RATES['anon']`.

`AnonRateThrottle` es adecuado si quieres restringir la tasa de solicitudes de fuentes desconocidas.

## UserRateThrottle

`UserRateThrottle` estrangulará a los usuarios a una tasa dada de solicitudes a través de la API. El id de usuario se usa para generar una clave única contra la cual estrangular. Las solicitudes no autenticadas recurrirán a usar la dirección IP de la solicitud entrante para generar una clave única contra la cual estrangular.

La tasa de solicitud permitida se determina de una de las siguientes (en orden de preferencia).

- La propiedad `rate` en la clase, que puede ser proporcionada sobrescribiendo `UserRateThrottle` y estableciendo la propiedad.
- La configuración `DEFAULT_THROTTLE_RATES['user']`.

Una API puede tener múltiples `UserRateThrottles` en su lugar al mismo tiempo. Para hacerlo, sobrescribe `UserRateThrottle` y establece un "scope" único para cada clase.

Por ejemplo, múltiples tasas de estrangulación de usuario podrían implementarse usando las siguientes clases...

```python
class BurstRateThrottle(UserRateThrottle):
    scope = 'burst'

class SustainedRateThrottle(UserRateThrottle):
    scope = 'sustained'
```

...y las siguientes configuraciones.

```python
REST_FRAMEWORK = {
    'DEFAULT_THROTTLE_CLASSES': [
        'example.throttles.BurstRateThrottle',
        'example.throttles.SustainedRateThrottle'
    ],
    'DEFAULT_THROTTLE_RATES': {
        'burst': '60/min',
        'sustained': '1000/day'
    }
}
```

`UserRateThrottle` es adecuado si quieres restricciones de tasa global simples por usuario.

## ScopedRateThrottle

La clase `ScopedRateThrottle` puede usarse para restringir el acceso a partes específicas de la API. Esta estrangulación solo se aplicará si la vista que está siendo accedida incluye una propiedad `.throttle_scope`. La clave de estrangulación única se formará entonces concatenando el "scope" de la solicitud con el id de usuario único o dirección IP.

La tasa de solicitud permitida se determina por la configuración `DEFAULT_THROTTLE_RATES` usando una clave del "scope" de la solicitud.

Por ejemplo, dadas las siguientes vistas...

```python
class ContactListView(APIView):
    throttle_scope = 'contacts'
    ...

class ContactDetailView(APIView):
    throttle_scope = 'contacts'
    ...

class UploadView(APIView):
    throttle_scope = 'uploads'
    ...
```

...y las siguientes configuraciones.

```python
REST_FRAMEWORK = {
    'DEFAULT_THROTTLE_CLASSES': [
        'rest_framework.throttling.ScopedRateThrottle',
    ],
    'DEFAULT_THROTTLE_RATES': {
        'contacts': '1000/day',
        'uploads': '20/day'
    }
}
```

Las solicitudes de usuario a `ContactListView` o `ContactDetailView` serían restringidas a un total de 1000 solicitudes por día. Las solicitudes de usuario a `UploadView` serían restringidas a 20 solicitudes por día.

# Estrangulaciones personalizadas

Para crear una estrangulación personalizada, hereda de `BaseThrottle` e implementa `.allow_request(self, request, view)`. El método debería devolver `True` si la solicitud debería ser permitida, y `False` en caso contrario.

Opcionalmente también puedes sobrescribir el método `.wait()`. Si se implementa, `.wait()` debería devolver un número recomendado de segundos a esperar antes de intentar la siguiente solicitud, o `None`. El método `.wait()` solo será llamado si `.allow_request()` previamente ha devuelto `False`.

Si el método `.wait()` se implementa y la solicitud es estrangulada, entonces se incluirá un encabezado `Retry-After` en la respuesta.

## Ejemplo

Lo siguiente es un ejemplo de una estrangulación de tasa, que aleatoriamente estrangulará 1 de cada 10 solicitudes.

```python
import random

class RandomRateThrottle(throttling.BaseThrottle):
    def allow_request(self, request, view):
        return random.randint(1, 10) != 1
```
