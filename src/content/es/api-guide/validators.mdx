# Validadores

> Los validadores pueden ser útiles para reutilizar la lógica de validación entre diferentes tipos de campos.
>
> &mdash; [Documentación de Django][cite]

La mayor parte del tiempo que estás tratando con validación en REST framework simplemente te estarás apoyando en la validación de campo predeterminada, o escribiendo métodos de validación explícitos en clases de serializador o de campo.

Sin embargo, a veces querrás colocar tu lógica de validación en componentes reutilizables, para que pueda ser fácilmente reutilizada a lo largo de tu base de código. Esto puede lograrse usando funciones de validador y clases de validador.

## Validación en REST framework

La validación en los serializadores de Django REST framework se maneja un poco diferente a cómo funciona la validación en la clase `ModelForm` de Django.

Con `ModelForm` la validación se realiza parcialmente en el formulario, y parcialmente en la instancia del modelo. Con REST framework la validación se realiza enteramente en la clase del serializador. Esto es ventajoso por las siguientes razones:

- Introduce una separación adecuada de preocupaciones, haciendo que el comportamiento de tu código sea más obvio.
- Es fácil cambiar entre usar clases de atajo `ModelSerializer` y usar clases explícitas `Serializer`. Cualquier comportamiento de validación que se use para `ModelSerializer` es simple de replicar.
- Imprimir el `repr` de una instancia de serializador te mostrará exactamente qué reglas de validación aplica. No hay comportamiento de validación oculta adicional siendo llamado en la instancia del modelo.

Cuando estás usando `ModelSerializer` todo esto se maneja automáticamente para ti. Si quieres bajar a usar clases `Serializer` en su lugar, entonces necesitas definir las reglas de validación explícitamente.

#### Ejemplo

Como ejemplo de cómo REST framework usa validación explícita, tomaremos una clase de modelo simple que tiene un campo con una restricción de unicidad.

```python
class CustomerReportRecord(models.Model):
    time_raised = models.DateTimeField(default=timezone.now, editable=False)
    reference = models.CharField(unique=True, max_length=20)
    description = models.TextField()
```

Aquí hay un `ModelSerializer` básico que podemos usar para crear o actualizar instancias de `CustomerReportRecord`:

```python
class CustomerReportSerializer(serializers.ModelSerializer):
    class Meta:
        model = CustomerReportRecord
```

Si abrimos el shell de Django usando `manage.py shell` podemos ahora

```bash
>>> from project.example.serializers import CustomerReportSerializer
>>> serializer = CustomerReportSerializer()
>>> print(repr(serializer))
CustomerReportSerializer():
    id = IntegerField(label='ID', read_only=True)
    time_raised = DateTimeField(read_only=True)
    reference = CharField(max_length=20, validators=[UniqueValidator(queryset=CustomerReportRecord.objects.all())])
    description = CharField(style={'type': 'textarea'})
```

La parte interesante aquí es el campo `reference`. Podemos ver que la restricción de unicidad está siendo explícitamente forzada por un validador en el campo del serializador.

Debido a este estilo más explícito, REST framework incluye algunas clases de validador que no están disponibles en el núcleo de Django. Estas clases se detallan a continuación. Los validadores de REST framework, como sus contrapartes de Django, implementan el método `__eq__`, permitiéndote comparar instancias para igualdad.

## UniqueValidator

Este validador puede usarse para forzar la restricción `unique=True` en campos de modelo.
Toma un solo argumento requerido, y un argumento opcional `messages`:

- `queryset` _requerido_ - Este es el queryset contra el cual debería forzarse la unicidad.
- `message` - El mensaje de error que debería usarse cuando la validación falla.
- `lookup` - La búsqueda usada para encontrar una instancia existente con el valor siendo validado. Por defecto es `'exact'`.

Este validador debería aplicarse a _campos del serializador_, así:

```python
from rest_framework.validators import UniqueValidator

slug = SlugField(
    max_length=100,
    validators=[UniqueValidator(queryset=BlogPost.objects.all())]
)
```

## UniqueTogetherValidator

Este validador puede usarse para forzar restricciones `unique_together` en instancias de modelo.
Tiene dos argumentos requeridos, y un solo argumento opcional `messages`:

- `queryset` _requerido_ - Este es el queryset contra el cual debería forzarse la unicidad.
- `fields` _requerido_ - Una lista o tupla de nombres de campo que deberían hacer un conjunto único. Estos deben existir como campos en la clase del serializador.
- `message` - El mensaje de error que debería usarse cuando la validación falla.

El validador debería aplicarse a _clases del serializador_, así:

```python
from rest_framework.validators import UniqueTogetherValidator

class ExampleSerializer(serializers.Serializer):
    # ...
    class Meta:
        # Los elementos ToDo pertenecen a una lista padre, y tienen un ordenamiento definido
        # por el campo 'position'. No dos elementos en una lista dada pueden compartir
        # la misma posición.
        validators = [
            UniqueTogetherValidator(
                queryset=ToDoItem.objects.all(),
                fields=['list', 'position']
            )
        ]
```

---

**Nota**: La clase `UniqueTogetherValidator` siempre impone una restricción implícita de que todos los campos a los que aplica siempre son tratados como requeridos. Los campos con valores `default` son una excepción a esto ya que siempre suministran un valor incluso cuando se omiten de la entrada del usuario.

## UniqueForYearValidator

Estos validadores pueden usarse para forzar las restricciones `unique_for_date`, `unique_for_month` y `unique_for_year` en instancias de modelo. Toman los siguientes argumentos:

- `queryset` _requerido_ - Este es el queryset contra el cual debería forzarse la unicidad.
- `field` _requerido_ - Un nombre de campo contra el cual se validará la unicidad en el rango de fecha dado. Este debe existir como un campo en la clase del serializador.
- `date_field` _requerido_ - Un nombre de campo que se usará para determinar el rango de fecha para la restricción de unicidad. Este debe existir como un campo en la clase del serializador.
- `message` - El mensaje de error que debería usarse cuando la validación falla.

El validador debería aplicarse a _clases del serializador_, así:

```python
from rest_framework.validators import UniqueForYearValidator

class ExampleSerializer(serializers.Serializer):
    # ...
    class Meta:
        # Las publicaciones de blog deberían tener un slug que sea único para el año actual.
        validators = [
            UniqueForYearValidator(
                queryset=BlogPostItem.objects.all(),
                field='slug',
                date_field='published'
            )
        ]
```

El campo de fecha que se usa para la validación siempre se requiere que esté presente en la clase del serializador. No puedes simplemente confiar en una clase de modelo `default=...`, porque el valor siendo usado para el predeterminado no se generaría hasta después de que la validación haya corrido.

Hay un par de estilos que podrías querer usar para esto dependiendo de cómo quieres que se comporte tu API. Si estás usando `ModelSerializer` probablemente simplemente te apoyarás en los predeterminados que REST framework genera para ti, pero si estás usando `Serializer` o simplemente quieres más control explícito, usa uno de los estilos demostrados abajo.

#### Usando con un campo de fecha escribible.

Si quieres que el campo de fecha sea escribible, lo único que vale la pena notar es que deberías asegurar que siempre esté disponible en los datos de entrada, ya sea estableciendo un argumento `default`, o estableciendo `required=True`.

```python
published = serializers.DateTimeField(required=True)
```

#### Usando con un campo de fecha de solo lectura.

Si quieres que el campo de fecha sea visible, pero no editable por el usuario, entonces establece `read_only=True` y adicionalmente establece un argumento `default=...`.

```python
published = serializers.DateTimeField(read_only=True, default=timezone.now)
```

#### Usando con un campo de fecha oculto.

Si quieres que el campo de fecha esté completamente oculto del usuario, entonces usa `HiddenField`. Este tipo de campo no acepta entrada del usuario, sino que siempre devuelve su valor predeterminado al `validated_data` en el serializador.

```python
published = serializers.HiddenField(default=timezone.now)
```

---

**Nota**: Las clases `UniqueFor<Range>Validator` imponen una restricción implícita de que los campos a los que aplican siempre son tratados como requeridos. Los campos con valores `default` son una excepción a esto ya que siempre suministran un valor incluso cuando se omiten de la entrada del usuario.

---

---

**Nota:** `HiddenField()` no aparece en el serializador `partial=True` (cuando se hace una solicitud `PATCH`).

# Valores predeterminados avanzados de campo

Los validadores que se aplican a través de múltiples campos en el serializador a veces pueden requerir una entrada de campo que no debería ser proporcionada por el cliente de la API, pero que _está_ disponible como entrada para el validador.
Para este propósito usa `HiddenField`. Este campo estará presente en `validated_data` pero _no_ será usado en la representación de salida del serializador.

**Nota:** Usar un campo `read_only=True` se excluye de los campos escribibles así que no usará un argumento `default=…`. Mira el [anuncio 3.8](https://www.django-rest-framework.org/community/3.8-announcement/#altered-the-behaviour-of-read_only-plus-default-on-field).

REST framework incluye un par de valores predeterminados que pueden ser útiles en este contexto.

#### CurrentUserDefault

Una clase predeterminada que puede usarse para representar el usuario actual. Para usar esto, la 'request' debe haber sido proporcionada como parte del diccionario de contexto al instanciar el serializador.

```python
owner = serializers.HiddenField(
    default=serializers.CurrentUserDefault()
)
```

#### CreateOnlyDefault

Una clase predeterminada que puede usarse para _solo establecer un argumento predeterminado durante operaciones de creación_. Durante las actualizaciones el campo se omite.

Toma un solo argumento, que es el valor predeterminado o callable que debería usarse durante las operaciones de creación.

```python
created_at = serializers.DateTimeField(
    default=serializers.CreateOnlyDefault(timezone.now)
)
```

# Limitaciones de los validadores

Hay algunos casos ambiguos donde necesitarás manejar la validación
explícitamente, en lugar de confiar en las clases de serializador predeterminadas que
`ModelSerializer` genera.

En estos casos podrías querer deshabilitar los validadores generados automáticamente,
especificando una lista vacía para el atributo `Meta.validators` del serializador.

## Campos opcionales

Por defecto la validación "unique together" fuerza que todos los campos sean
`required=True`. En algunos casos, podrías querer aplicar explícitamente
`required=False` a uno de los campos, en cuyo caso el comportamiento deseado
de la validación es ambiguo.

En este caso típicamente necesitarás excluir el validador de la
clase del serializador, y en su lugar escribir cualquier lógica de validación explícitamente, ya sea
en el método `.validate()`, o en la vista.

Por ejemplo:

```python
class BillingRecordSerializer(serializers.ModelSerializer):
    def validate(self, attrs):
        # Aplica validación personalizada aquí, o en la vista.

    class Meta:
        fields = ['client', 'date', 'amount']
        extra_kwargs = {'client': {'required': False}}
        validators = []  # Elimina una restricción "unique together" predeterminada.
```

## Actualizando serializadores anidados

Al aplicar una actualización a una instancia existente, los validadores de unicidad
excluirán la instancia actual de la verificación de unicidad. La instancia actual
está disponible en el contexto de la verificación de unicidad, porque existe como
un atributo en el serializador, habiendo sido inicialmente pasada usando
`instance=...` al instanciar el serializador.

En el caso de operaciones de actualización en serializadores _anidados_ no hay forma de
aplicar esta exclusión, porque la instancia no está disponible.

De nuevo, probablemente querrás eliminar explícitamente el validador de la
clase del serializador, y escribir el código para la restricción de validación
explícitamente, en un método `.validate()`, o en la vista.

## Depurando casos complejos

Si no estás seguro exactamente de qué comportamiento una clase `ModelSerializer`
generará, usualmente es una buena idea ejecutar `manage.py shell`, e imprimir
una instancia del serializador, para que puedas inspeccionar los campos y
validadores que genera automáticamente para ti.

```bash
>>> serializer = MyComplexModelSerializer()
>>> print(serializer)
class MyComplexModelSerializer:
    my_fields = ...
```

También ten en cuenta que con casos complejos a menudo puede ser mejor definir
explícitamente tus clases de serializador, en lugar de confiar en el comportamiento
predeterminado de `ModelSerializer`. Esto involucra un poco más de código, pero asegura
que el comportamiento resultante sea más transparente.

# Escribiendo validadores personalizados

Puedes usar cualquiera de los validadores existentes de Django, o escribir tus propios validadores personalizados.

## Basados en funciones

Un validador puede ser cualquier callable que lance una `serializers.ValidationError` en caso de fallo.

```python
def even_number(value):
    if value % 2 != 0:
        raise serializers.ValidationError('Este campo debe ser un número par.')
```

#### Validación a nivel de campo

Puedes especificar validación personalizada a nivel de campo añadiendo métodos `.validate_<field_name>`
a tu subclase de `Serializer`. Esto está documentado en la
[documentación de Serializadores](https://www.django-rest-framework.org/api-guide/serializers/#field-level-validation)

## Basados en clases

Para escribir un validador basado en clases, usa el método `__call__`. Los validadores basados en clases son útiles ya que te permiten parametrizar y reutilizar comportamiento.

```python
class MultipleOf:
    def __init__(self, base):
        self.base = base

    def __call__(self, value):
        if value % self.base != 0:
            message = 'Este campo debe ser un múltiplo de %d.' % self.base
            raise serializers.ValidationError(message)
```

#### Accediendo al contexto

En algunos casos avanzados podrías querer que un validador reciba el campo del serializador
con el que se está usando como contexto adicional. Puedes hacerlo estableciendo
un atributo `requires_context = True` en la clase del validador. El método `__call__`
entonces será llamado con el `serializer_field`
o `serializer` como un argumento adicional.

```python
class MultipleOf:
    requires_context = True

    def __call__(self, value, serializer_field):
        ...
```
