# Versionamiento

> Versionar una interfaz es solo una forma "educada" de matar clientes desplegados.
>
> &mdash; [Roy Fielding][cite].

El versionamiento de API te permite alterar el comportamiento entre diferentes clientes. REST framework proporciona varios esquemas de versionamiento diferentes.

El versionamiento se determina por la solicitud entrante del cliente, y puede basarse ya sea en la URL de la solicitud, o en los encabezados de la solicitud.

Hay varios enfoques válidos para el versionamiento. [Los sistemas sin versionamiento también pueden ser apropiados][roy-fielding-on-versioning], particularmente si estás diseñando para sistemas a muy largo plazo con múltiples clientes fuera de tu control.

## Versionamiento con REST framework

Cuando el versionamiento de API está habilitado, el atributo `request.version` contendrá una cadena que corresponde a la versión solicitada en la solicitud entrante del cliente.

Por defecto, el versionamiento no está habilitado, y `request.version` siempre devolverá `None`.

#### Variar el comportamiento basado en la versión

Cómo varías el comportamiento de la API depende de ti, pero un ejemplo que típicamente podrías querer es cambiar a un estilo de serialización diferente en una versión más nueva. Por ejemplo:

```python
def get_serializer_class(self):
    if self.request.version == 'v1':
        return AccountSerializerVersion1
    return AccountSerializer
```

#### Invertir URLs para APIs versionadas

La función `reverse` incluida por REST framework se integra con el esquema de versionamiento. Necesitas asegurarte de incluir la `request` actual como un argumento de palabra clave, así.

```python
from rest_framework.reverse import reverse

reverse('bookings-list', request=request)
```

La función anterior aplicará cualquier transformación de URL apropiada para la versión de la solicitud. Por ejemplo:

- Si se estuviera usando `NamespaceVersioning`, y la versión de la API fuera 'v1', entonces la búsqueda de URL usada sería `'v1:bookings-list'`, que podría resolverse a una URL como `http://example.org/v1/bookings/`.
- Si se estuviera usando `QueryParameterVersioning`, y la versión de la API fuera `1.0`, entonces la URL devuelta podría ser algo como `http://example.org/bookings/?version=1.0`

#### APIs versionadas y serializadores con hipervínculos

Cuando usas estilos de serialización con hipervínculos junto con un esquema de versionamiento basado en URL, asegúrate de incluir la solicitud como contexto para el serializador.

```python
def get(self, request):
    queryset = Booking.objects.all()
    serializer = BookingsSerializer(queryset, many=True, context={'request': request})
    return Response({'all_bookings': serializer.data})
```

Hacer esto permitirá que cualquier URL devuelta incluya el versionamiento apropiado.

## Configurando el esquema de versionamiento

El esquema de versionamiento se define por la clave de configuración `DEFAULT_VERSIONING_CLASS`.

```python
REST_FRAMEWORK = {
    'DEFAULT_VERSIONING_CLASS': 'rest_framework.versioning.NamespaceVersioning'
}
```

A menos que se establezca explícitamente, el valor de `DEFAULT_VERSIONING_CLASS` será `None`. En este caso el atributo `request.version` siempre devolverá `None`.

También puedes establecer el esquema de versionamiento en una vista individual. Típicamente no necesitarás hacer esto, ya que tiene más sentido tener un solo esquema de versionamiento usado globalmente. Si necesitas hacerlo, usa el atributo `versioning_class`.

```python
class ProfileList(APIView):
    versioning_class = versioning.QueryParameterVersioning
```

#### Otras configuraciones de versionamiento

Las siguientes claves de configuración también se usan para controlar el versionamiento:

- `DEFAULT_VERSION`. El valor que debería usarse para `request.version` cuando no hay información de versionamiento presente. Por defecto es `None`.
- `ALLOWED_VERSIONS`. Si se establece, este valor restringirá el conjunto de versiones que pueden ser devueltas por el esquema de versionamiento, y lanzará un error si la versión proporcionada no está en este conjunto. Ten en cuenta que el valor usado para la configuración `DEFAULT_VERSION` siempre se considera parte del conjunto `ALLOWED_VERSIONS` (a menos que sea `None`). Por defecto es `None`.
- `VERSION_PARAM`. La cadena que debería usarse para cualquier parámetro de versionamiento, como en el tipo de medio o parámetros de consulta de URL. Por defecto es `'version'`.

También puedes establecer tu clase de versionamiento más esos tres valores en una base por vista o por viewset definiendo tu propio esquema de versionamiento y usando las variables de clase `default_version`, `allowed_versions` y `version_param`. Por ejemplo, si quieres usar `URLPathVersioning`:

```python
from rest_framework.versioning import URLPathVersioning
from rest_framework.views import APIView

class ExampleVersioning(URLPathVersioning):
    default_version = ...
    allowed_versions = ...
    version_param = ...

class ExampleView(APIVIew):
    versioning_class = ExampleVersioning
```

# Referencia de la API

## AcceptHeaderVersioning

Este esquema requiere que el cliente especifique la versión como parte del tipo de medio en el encabezado `Accept`. La versión se incluye como un parámetro de tipo de medio, que supplementa el tipo de medio principal.

Aquí hay un ejemplo de solicitud HTTP usando el estilo de versionamiento de encabezado accept.

```http
GET /bookings/ HTTP/1.1
Host: example.com
Accept: application/json; version=1.0
```

En la solicitud de ejemplo anterior el atributo `request.version` devolvería la cadena `'1.0'`.

El versionamiento basado en encabezados accept es [generalmente considerado][klabnik-guidelines] como [mejor práctica][heroku-guidelines], aunque otros estilos pueden ser apropiados dependiendo de los requisitos de tu cliente.

#### Usando encabezados accept con tipos de medio de proveedor

Estrictamente hablando, el tipo de medio `json` no está especificado como [incluyendo parámetros adicionales][json-parameters]. Si estás construyendo una API pública bien especificada podrías considerar usar un [tipo de medio de proveedor][vendor-media-type]. Para hacerlo, configura tus renderizadores para usar un renderizador basado en JSON con un tipo de medio personalizado:

```python
class BookingsAPIRenderer(JSONRenderer):
    media_type = 'application/vnd.megacorp.bookings+json'
```

Tus solicitudes de cliente ahora se verían así:

```http
GET /bookings/ HTTP/1.1
Host: example.com
Accept: application/vnd.megacorp.bookings+json; version=1.0
```

## URLPathVersioning

Este esquema requiere que el cliente especifique la versión como parte de la ruta de la URL.

```http
GET /v1/bookings/ HTTP/1.1
Host: example.com
Accept: application/json
```

Tu configuración de URL debe incluir un patrón que coincida con la versión con un argumento de palabra clave `'version'`, para que esta información esté disponible para el esquema de versionamiento.

```python
urlpatterns = [
    re_path(
        r'^(?P<version>(v1|v2))/bookings/$',
        bookings_list,
        name='bookings-list'
    ),
    re_path(
        r'^(?P<version>(v1|v2))/bookings/(?P<pk>[0-9]+)/$',
        bookings_detail,
        name='bookings-detail'
    )
]
```

## NamespaceVersioning

Para el cliente, este esquema es el mismo que `URLPathVersioning`. La única diferencia es cómo se configura en tu aplicación Django, ya que usa espacios de nombres de URL, en lugar de argumentos de palabra clave de URL.

```http
GET /v1/something/ HTTP/1.1
Host: example.com
Accept: application/json
```

Con este esquema el atributo `request.version` se determina basado en el `namespace` que coincide con la ruta de solicitud entrante.

En el siguiente ejemplo estamos dando un conjunto de vistas dos posibles prefijos de URL diferentes, cada uno bajo un espacio de nombres diferente:

```python
# bookings/urls.py
urlpatterns = [
    re_path(r'^$', bookings_list, name='bookings-list'),
    re_path(r'^(?P<pk>[0-9]+)/$', bookings_detail, name='bookings-detail')
]

# urls.py
urlpatterns = [
    re_path(r'^v1/bookings/', include('bookings.urls', namespace='v1')),
    re_path(r'^v2/bookings/', include('bookings.urls', namespace='v2'))
]
```

Tanto `URLPathVersioning` como `NamespaceVersioning` son razonables si solo necesitas un esquema de versionamiento simple. El enfoque `URLPathVersioning` podría ser más adecuado para proyectos pequeños ad-hoc, y `NamespaceVersioning` es probablemente más fácil de manejar para proyectos más grandes.

## HostNameVersioning

El esquema de versionamiento de nombre de host requiere que el cliente especifique la versión solicitada como parte del nombre de host en la URL.

Por ejemplo, lo siguiente es una solicitud HTTP a la URL `http://v1.example.com/bookings/`:

```http
GET /bookings/ HTTP/1.1
Host: v1.example.com
Accept: application/json
```

Por defecto esta implementación espera que el nombre de host coincida con esta expresión regular simple:

```python
^([a-zA-Z0-9]+)\.[a-zA-Z0-9]+\.[a-zA-Z0-9]+$
```

Ten en cuenta que el primer grupo está encerrado en corchetes, indicando que esta es la porción coincidente del nombre de host.

El esquema `HostNameVersioning` puede ser incómodo de usar en modo de depuración ya que típicamente estarás accediendo a una dirección IP cruda como `127.0.0.1`. Hay varios tutoriales en línea sobre cómo [acceder a localhost con un subdominio personalizado][lvh] que podrías encontrar útiles en este caso.

El versionamiento basado en nombre de host puede ser particularmente útil si tienes requisitos para enrutar solicitudes entrantes a diferentes servidores basados en la versión, ya que puedes configurar diferentes registros DNS para diferentes versiones de API.

## QueryParameterVersioning

Este esquema es un estilo simple que incluye la versión como un parámetro de consulta en la URL. Por ejemplo:

```http
GET /something/?version=0.1 HTTP/1.1
Host: example.com
Accept: application/json
```

# Esquemas de versionamiento personalizados

Para implementar un esquema de versionamiento personalizado, hereda de `BaseVersioning` y sobrescribe el método `.determine_version`.

## Ejemplo

El siguiente ejemplo usa un encabezado personalizado `X-API-Version` para determinar la versión solicitada.

```python
class XAPIVersionScheme(versioning.BaseVersioning):
    def determine_version(self, request, *args, **kwargs):
        return request.META.get('HTTP_X_API_VERSION', None)
```

Si tu esquema de versionamiento se basa en la URL de la solicitud, también querrás alterar cómo se determinan las URLs versionadas. Para hacerlo, deberías sobrescribir el método `.reverse()` en la clase. Ver el código fuente para ejemplos.
