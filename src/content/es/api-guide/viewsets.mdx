# ViewSets

> Después de que el enrutamiento ha determinado qué controlador usar para una petición, tu controlador es responsable de darle sentido a la petición y producir la salida apropiada.
>
> &mdash; [Documentación de Ruby on Rails][cite]

Django REST framework te permite combinar la lógica para un conjunto de vistas relacionadas en una sola clase, llamada `ViewSet`. En otros frameworks también puedes encontrar implementaciones conceptualmente similares llamadas algo como 'Resources' o 'Controllers'.

Una clase `ViewSet` es simplemente **un tipo de vista basada en clases, que no proporciona ningún manejador de métodos** como `.get()` o `.post()`, y en su lugar proporciona acciones como `.list()` y `.create()`.

Los manejadores de métodos para un `ViewSet` solo se enlazan a las acciones correspondientes en el punto de finalizar la vista, usando el método `.as_view()`.

Típicamente, en lugar de registrar explícitamente las vistas en un viewset en la urlconf, registrarás el viewset con una clase de router, que automáticamente determina la urlconf por ti.

**Ejemplo**

Definamos un viewset simple que pueda usarse para listar o recuperar todos los usuarios del sistema.

```python
from django.contrib.auth.models import User
from django.shortcuts import get_object_or_404
from myapps.serializers import UserSerializer
from rest_framework import viewsets
from rest_framework.response import Response

class UserViewSet(viewsets.ViewSet):
    """
    Un ViewSet simple para listar o recuperar usuarios.
    """
    def list(self, request):
        queryset = User.objects.all()
        serializer = UserSerializer(queryset, many=True)
        return Response(serializer.data)

    def retrieve(self, request, pk=None):
        queryset = User.objects.all()
        user = get_object_or_404(queryset, pk=pk)
        serializer = UserSerializer(user)
        return Response(serializer.data)
```

Si necesitamos, podemos enlazar este viewset en dos vistas separadas, así:

```python
user_list = UserViewSet.as_view({'get': 'list'})
user_detail = UserViewSet.as_view({'get': 'retrieve'})
```

Típicamente no haríamos esto, sino que registraríamos el viewset con un router, y permitiríamos que la urlconf se genere automáticamente.

```python
from myapp.views import UserViewSet
from rest_framework.routers import DefaultRouter

router = DefaultRouter()
router.register(r'users', UserViewSet, basename='user')
urlpatterns = router.urls
```

En lugar de escribir tus propios viewsets, a menudo querrás usar las clases base existentes que proporcionan un conjunto predeterminado de comportamiento. Por ejemplo:

```python
class UserViewSet(viewsets.ModelViewSet):
    """
    Un viewset para ver y editar instancias de usuario.
    """
    serializer_class = UserSerializer
    queryset = User.objects.all()
```

Hay dos ventajas principales de usar una clase `ViewSet` sobre usar una clase `View`.

- La lógica repetida puede combinarse en una sola clase. En el ejemplo anterior, solo necesitamos especificar el `queryset` una vez, y se usará en múltiples vistas.
- Al usar routers, ya no necesitamos ocuparnos de conectar la configuración de URL nosotros mismos.

Ambas vienen con una compensación. Usar vistas regulares y configuraciones de URL es más explícito y te da más control. Los ViewSets son útiles si quieres empezar y funcionar rápidamente, o cuando tienes una API grande y quieres imponer una configuración de URL consistente en toda.

## Acciones de ViewSet

Los routers predeterminados incluidos con REST framework proporcionarán rutas para un conjunto estándar de acciones de estilo crear/recuperar/actualizar/destruir, como se muestra a continuación:

```python
class UserViewSet(viewsets.ViewSet):
    """
    Ejemplo de viewset vacío demostrando las acciones estándar
    que serán manejadas por una clase de router.

    Si estás usando sufijos de formato, asegúrate de incluir también
    el argumento de palabra clave `format=None` para cada acción.
    """

    def list(self, request):
        pass

    def create(self, request):
        pass

    def retrieve(self, request, pk=None):
        pass

    def update(self, request, pk=None):
        pass

    def partial_update(self, request, pk=None):
        pass

    def destroy(self, request, pk=None):
        pass
```

## Introspección de acciones de ViewSet

Durante el despacho, los siguientes atributos están disponibles en el `ViewSet`.

- `basename` - la base a usar para los nombres de URL que son creados.
- `action` - el nombre de la acción actual (ej., `list`, `create`).
- `detail` - booleano indicando si la acción actual está configurada para una vista de lista o de detalle.
- `suffix` - el sufijo de visualización para el tipo de viewset - refleja el atributo `detail`.
- `name` - el nombre de visualización para el viewset. Este argumento es mutuamente exclusivo con `suffix`.
- `description` - la descripción de visualización para la vista individual de un viewset.

Puedes inspeccionar estos atributos para ajustar el comportamiento basado en la acción actual. Por ejemplo, podrías restringir permisos a todo excepto la acción `list` de manera similar a esto:

```python
def get_permissions(self):
    """
    Instancia y devuelve la lista de permisos que esta vista requiere.
    """
    if self.action == 'list':
        permission_classes = [IsAuthenticated]
    else:
        permission_classes = [IsAdminUser]
    return [permission() for permission in permission_classes]
```

**Nota**: el atributo `action` no está disponible en los métodos `get_parsers`, `get_authenticators` y `get_content_negotiator`, ya que se establece _después_ de que son llamados en el ciclo de vida del framework. Si sobrescribes uno de estos métodos e intentas acceder al atributo `action` en ellos, obtendrás un error `AttributeError`.

## Marcando acciones adicionales para enrutamiento

Si tienes métodos ad-hoc que deberían ser enrutables, puedes marcarlos como tales con el decorador `@action`. Como las acciones regulares, las acciones adicionales pueden estar destinadas a un solo objeto, o a una colección completa. Para indicar esto, establece el argumento `detail` en `True` o `False`. El router configurará sus patrones de URL en consecuencia. Por ejemplo, el `DefaultRouter` configurará las acciones de detalle para contener `pk` en sus patrones de URL.

Un ejemplo más completo de acciones adicionales:

```python
from django.contrib.auth.models import User
from rest_framework import status, viewsets
from rest_framework.decorators import action
from rest_framework.response import Response
from myapp.serializers import UserSerializer, PasswordSerializer

class UserViewSet(viewsets.ModelViewSet):
    """
    Un viewset que proporciona las acciones estándar
    """
    queryset = User.objects.all()
    serializer_class = UserSerializer

    @action(detail=True, methods=['post'])
    def set_password(self, request, pk=None):
        user = self.get_object()
        serializer = PasswordSerializer(data=request.data)
        if serializer.is_valid():
            user.set_password(serializer.validated_data['password'])
            user.save()
            return Response({'status': 'contraseña establecida'})
        else:
            return Response(serializer.errors,
                            status=status.HTTP_400_BAD_REQUEST)

    @action(detail=False)
    def recent_users(self, request):
        recent_users = User.objects.all().order_by('-last_login')

        page = self.paginate_queryset(recent_users)
        if page is not None:
            serializer = self.get_serializer(page, many=True)
            return self.get_paginated_response(serializer.data)

        serializer = self.get_serializer(recent_users, many=True)
        return Response(serializer.data)
```

El decorador `action` enrutará peticiones `GET` por defecto, pero también puede aceptar otros métodos HTTP estableciendo el argumento `methods`. Por ejemplo:

```python
@action(detail=True, methods=['post', 'delete'])
def unset_password(self, request, pk=None):
    ...
```

El argumento `methods` también soporta métodos HTTP definidos como [HTTPMethod](https://docs.python.org/3/library/http.html#http.HTTPMethod). El ejemplo de abajo es idéntico al de arriba:

```python
from http import HTTPMethod

@action(detail=True, methods=[HTTPMethod.POST, HTTPMethod.DELETE])
def unset_password(self, request, pk=None):
    ...
```

El decorador te permite sobrescribir cualquier configuración a nivel de viewset como `permission_classes`, `serializer_class`, `filter_backends`...:

```python
@action(detail=True, methods=['post'], permission_classes=[IsAdminOrIsSelf])
def set_password(self, request, pk=None):
    ...
```

Las dos nuevas acciones estarán entonces disponibles en las URLs `^users/{pk}/set_password/$` y `^users/{pk}/unset_password/$`. Usa los parámetros `url_path` y `url_name` para cambiar el segmento de URL y el nombre de URL inverso de la acción.

Para ver todas las acciones adicionales, llama al método `.get_extra_actions()`.

### Enrutamiento de métodos HTTP adicionales para acciones adicionales

Las acciones adicionales pueden mapear métodos HTTP adicionales a métodos separados de `ViewSet`. Por ejemplo, los métodos de establecimiento/eliminación de contraseña anteriores podrían consolidarse en una sola ruta. Ten en cuenta que las asignaciones adicionales no aceptan argumentos.

```python
@action(detail=True, methods=["put"], name="Cambiar Contraseña")
def password(self, request, pk=None):
    """Actualiza la contraseña del usuario."""
    ...


@password.mapping.delete
def delete_password(self, request, pk=None):
    """Elimina la contraseña del usuario."""
    ...
```

## Inversión de URLs de acción

Si necesitas obtener la URL de una acción, usa el método `.reverse_action()`. Este es un envoltorio de conveniencia para `reverse()`, pasando automáticamente el objeto `request` de la vista y prefijando el `url_name` con el atributo `.basename`.

Ten en cuenta que el `basename` es proporcionado por el router durante el registro del `ViewSet`. Si no estás usando un router, entonces debes proporcionar el argumento `basename` al método `.as_view()`.

Usando el ejemplo de la sección anterior:

```bash
>>> view.reverse_action("set-password", args=["1"])
'http://localhost:8000/api/users/1/set_password'
```

Alternativamente, puedes usar el atributo `url_name` establecido por el decorador `@action`.

```bash
>>> view.reverse_action(view.set_password.url_name, args=['1'])
'http://localhost:8000/api/users/1/set_password'
```

El argumento `url_name` para `.reverse_action()` debe coincidir con el mismo argumento para el decorador `@action`. Adicionalmente, este método puede usarse para invertir las acciones predeterminadas, como `list` y `create`.

# Referencia de API

## ViewSet

La clase `ViewSet` hereda de `APIView`. Puedes usar cualquiera de los atributos estándar como `permission_classes`, `authentication_classes` para controlar la política de API en el viewset.

La clase `ViewSet` no proporciona ninguna implementación de acciones. Para usar una clase `ViewSet`, sobrescribirás la clase y definirás las implementaciones de acción explícitamente.

## GenericViewSet

La clase `GenericViewSet` hereda de `GenericAPIView`, y proporciona el conjunto predeterminado de métodos `get_object`, `get_queryset` y otro comportamiento base de vista genérica, pero no incluye ninguna acción por defecto.

Para usar una clase `GenericViewSet`, sobrescribirás la clase y ya sea mezclarás las clases mixin requeridas, o definirás las implementaciones de acción explícitamente.

## ModelViewSet

La clase `ModelViewSet` hereda de `GenericAPIView` e incluye implementaciones para varias acciones, mezclando el comportamiento de varias clases mixin.

Las acciones proporcionadas por la clase `ModelViewSet` son `.list()`, `.retrieve()`, `.create()`, `.update()`, `.partial_update()`, y `.destroy()`.

#### Ejemplo

Porque `ModelViewSet` extiende `GenericAPIView`, normalmente necesitarás proporcionar al menos los atributos `queryset` y `serializer_class`. Por ejemplo:

```python
class AccountViewSet(viewsets.ModelViewSet):
    """
    Un ViewSet simple para ver y editar cuentas.
    """
    queryset = Account.objects.all()
    serializer_class = AccountSerializer
    permission_classes = [IsAccountAdminOrReadOnly]
```

Ten en cuenta que puedes usar cualquiera de los atributos estándar o sobrescrituras de método proporcionadas por `GenericAPIView`. Por ejemplo, para usar un `ViewSet` que determine dinámicamente el queryset en el que debe operar, podrías hacer algo como esto:

```python
class AccountViewSet(viewsets.ModelViewSet):
    """
    Un ViewSet simple para ver y editar las cuentas
    asociadas con el usuario.
    """
    serializer_class = AccountSerializer
    permission_classes = [IsAccountAdminOrReadOnly]

    def get_queryset(self):
        return self.request.user.accounts.all()
```

Ten en cuenta sin embargo que al eliminar la propiedad `queryset` de tu `ViewSet`, cualquier [router][routers] asociado no podrá derivar el basename de tu Modelo automáticamente, y así tendrás que especificar el kwarg `basename` como parte de tu [registro de router][routers].

También ten en cuenta que aunque esta clase proporciona el conjunto completo de acciones crear/listar/recuperar/actualizar/destruir por defecto, puedes restringir las operaciones disponibles usando las clases de permisos estándar.

## ReadOnlyModelViewSet

La clase `ReadOnlyModelViewSet` también hereda de `GenericAPIView`. Como con `ModelViewSet`, también incluye implementaciones para varias acciones, pero a diferencia de `ModelViewSet` solo proporciona las acciones de 'solo lectura', `.list()` y `.retrieve()`.

#### Ejemplo

Como con `ModelViewSet`, normalmente necesitarás proporcionar al menos los atributos `queryset` y `serializer_class`. Por ejemplo:

```python
class AccountViewSet(viewsets.ReadOnlyModelViewSet):
    """
    Un ViewSet simple para ver cuentas.
    """
    queryset = Account.objects.all()
    serializer_class = AccountSerializer
```

De nuevo, como con `ModelViewSet`, puedes usar cualquiera de los atributos estándar y sobrescrituras de método disponibles para `GenericAPIView`.

# Clases base de ViewSet personalizadas

Puedes necesitar proporcionar clases `ViewSet` personalizadas que no tengan el conjunto completo de acciones de `ModelViewSet`, o que personalicen el comportamiento de alguna otra manera.

**Ejemplo**

Para crear una clase base de viewset que proporcione operaciones `create`, `list` y `retrieve`, hereda de `GenericViewSet`, y mezcla las acciones requeridas:

```python
from rest_framework import mixins, viewsets

class CreateListRetrieveViewSet(mixins.CreateModelMixin,
                                mixins.ListModelMixin,
                                mixins.RetrieveModelMixin,
                                viewsets.GenericViewSet):
    """
    Un viewset que proporciona acciones `retrieve`, `create`, y `list`.

    Para usarlo, sobrescribe la clase y establece los atributos
    `.queryset` y `.serializer_class`.
    """
    pass
```

Al crear tus propias clases base de `ViewSet`, puedes proporcionar comportamiento común que puede reutilizarse en múltiples viewsets a través de tu API.
