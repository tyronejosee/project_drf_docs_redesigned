# Gestión del proyecto

> "Nadie puede silbar una sinfonía; se necesita una orquesta completa para tocarla"
>
> &mdash; Halford E. Luccock

Este documento describe nuestros procesos de gestión de proyectos para REST framework.

El objetivo es asegurar que el proyecto tenga un alto
["factor bus"][bus-factor], y pueda continuar siendo bien soportado en el futuro previsible. Las sugerencias de mejora para nuestro proceso son bienvenidas.

---

## Equipo de mantenimiento

[Participar activamente en el proyecto REST framework](contributing.md) **no requiere ser parte del equipo de mantenimiento**. Casi todas las partes importantes de la triaje de problemas y mejora del proyecto pueden ser trabajadas activamente independientemente de tu estado de colaborador en el repositorio.

#### Composición

La composición del equipo de mantenimiento es manejada por [@tomchristie](https://github.com/encode/). Los miembros del equipo serán agregados como colaboradores al repositorio.

#### Responsabilidades

Los miembros del equipo tienen las siguientes responsabilidades.

- Cerrar tickets inválidos o resueltos.
- Agregar etiquetas de triaje y hitos a los tickets.
- Fusionar pull requests finalizados.
- Construir y desplegar la documentación, usando `mkdocs gh-deploy`.
- Construir y actualizar los paquetes de traducción incluidos.

Notas adicionales para mantenedores:

- Los cambios de código deben venir en forma de pull request - no hacer push directamente a master.
- Los mantenedores generalmente no deben fusionar sus propios pull requests.
- Cada issue/pull request debe tener exactamente una etiqueta una vez triajado.

## Proceso de lanzamiento

- El gestor de lanzamientos es seleccionado por `@tomchristie`.
- El gestor de lanzamientos luego tendrá el rol de mantenedor agregado al paquete PyPI.
- El gestor anterior luego tendrá el rol de mantenedor eliminado del paquete PyPI.

Nuestros lanzamientos en PyPI serán manejados por el gestor de lanzamiento actual, o por `@tomchristie`. Cada lanzamiento debe tener un issue abierto etiquetado con la etiqueta `Release` y marcado contra el hito apropiado.

La siguiente plantilla debe ser usada para la descripción del issue, y sirve como una lista de verificación de lanzamiento.

```markdown
El gestor de lanzamiento es @**_.
El pull request es #_**.

Durante el ciclo de desarrollo:

- [ ] Subir el nuevo contenido para ser traducido a [transifex](https://www.django-rest-framework.org/topics/project-management/#translations).

Lista de verificación:

- [ ] Crear pull request para [notas de lanzamiento](https://github.com/encode/django-rest-framework/blob/master/docs/topics/release-notes.md) basadas en el [hito _._.\*](https://github.com/encode/django-rest-framework/milestones/***).
- [ ] Actualizar versiones soportadas:
  - [ ] lista `setup.py` `python_requires`
  - [ ] clasificadores de versión Python & Django en `setup.py`
  - [ ] versiones Python & Django en `README`
  - [ ] versiones Python & Django en `docs`
- [ ] Actualizar las traducciones desde [transifex](https://www.django-rest-framework.org/topics/project-management/#translations).
- [ ] Asegurar que el pull request incremente la versión a `*.*.*` en [`restframework/__init__.py`](https://github.com/encode/django-rest-framework/blob/master/rest_framework/__init__.py).
- [ ] Asegurar que la documentación sea válida
  - Construir y servir docs `mkdocs serve`
  - Validar enlaces `pylinkvalidate.py -P http://127.0.0.1:8000`
- [ ] Confirmar con @tomchristie que el lanzamiento está finalizado y listo para salir.
- [ ] Asegurar que la fecha de lanzamiento esté incluida en el pull request.
- [ ] Fusionar el pull request de lanzamiento.
- [ ] Subir el paquete a PyPI con `./setup.py publish`.
- [ ] Etiquetar el lanzamiento, con `git tag -a *.*.* -m 'versión *.*.*'; git push --tags`.
- [ ] Desplegar la documentación con `mkdocs gh-deploy`.
- [ ] Hacer un anuncio de lanzamiento en el [grupo de discusión](https://groups.google.com/forum/?fromgroups#!forum/django-rest-framework).
- [ ] Hacer un anuncio de lanzamiento en twitter.
- [ ] Cerrar el hito en GitHub.

Para modificar este proceso para lanzamientos futuros, haz un pull request a la documentación de [gestión del proyecto](https://www.django-rest-framework.org/topics/project-management/).
```

Al subir el lanzamiento a PyPI, asegúrate de que tu entorno ha sido instalado desde nuestro `requirement.txt` de desarrollo, para que la documentación y las instalaciones de PyPI se construyan consistentemente contra un conjunto anclado de paquetes.

## Traducciones

El equipo de mantenimiento es responsable de gestionar los paquetes de traducción incluidos en REST framework. La traducción de las cadenas fuente a múltiples idiomas se gestiona a través del [servicio transifex][transifex-project].

### Gestionando Transifex

El [cliente oficial de Transifex][transifex-client] se usa para subir y descargar traducciones a Transifex. El cliente se instala usando pip:

```bash
pip install transifex-client
```

Para usarlo necesitarás un login en Transifex que tenga una contraseña, y necesitarás tener acceso administrativo al proyecto Transifex. Necesitarás crear un archivo `~/.transifexrc` que contenga tus credenciales.

```bash
[https://www.transifex.com]
username = ***
token = ***
password = ***
hostname = https://www.transifex.com
```

### Subir nuevos archivos fuente

Cuando cualquier cadena visible por el usuario es cambiada, debe ser subida a Transifex para que los traductores puedan empezar a traducirlas. Para hacer esto, simplemente ejecuta:

```bash
# 1. Actualizar el archivo django.po fuente, que es la versión en inglés estadounidense.
cd rest_framework
django-admin makemessages -l en_US
# 2. Subir el archivo django.po fuente a Transifex.
cd ..
tx push -s
```

Al subir archivos fuente, Transifex actualizará las cadenas fuente de un recurso para que coincidan con las del nuevo archivo fuente.

Así es como se manejarán las diferencias entre los archivos fuente viejos y nuevos:

- Las nuevas cadenas serán agregadas.
- Las cadenas modificadas también serán agregadas.
- Las cadenas que no existen en el nuevo archivo fuente serán eliminadas de la base de datos, junto con sus traducciones. Si esas cadenas fuente se vuelven a agregar más tarde, la [Memoria de Traducción de Transifex][translation-memory] incluirá automáticamente la cadena de traducción.

### Descargar traducciones

Cuando un traductor ha terminado de traducir, su trabajo necesita ser descargado de Transifex al repositorio REST framework. Para hacer esto, ejecuta:

```bash
# 3. Descargar los archivos django.po traducidos de Transifex.
tx pull -a --minimum-perc 10
cd rest_framework
# 4. Compilar los archivos binarios .mo para todos los idiomas soportados.
django-admin compilemessages
```

## Requisitos del proyecto

Todos nuestros requisitos de prueba están anclados a versiones exactas, para asegurar que nuestras ejecuciones de prueba sean reproducibles. Mantenemos los requisitos en el directorio `requirements`. Los archivos de requisitos son referenciados desde el archivo de configuración `tox.ini`, asegurando que tengamos una única fuente de verdad para las versiones de paquetes usadas en las pruebas.

Las actualizaciones de paquetes generalmente deben ser tratadas como pull requests aislados. Puedes verificar si hay paquetes disponibles en una versión más nueva, usando `pip list --outdated`.
