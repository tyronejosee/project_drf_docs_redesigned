# Internacionalización

> Apoyar la internacionalización no es opcional. Debe ser una característica central.
>
> &mdash; [Jannis Leidel, hablando en Django Under the Hood, 2015][cite].

REST framework incluye mensajes de error traducibles. Puedes hacer que estos aparezcan en tu idioma habilitando [los mecanismos de traducción estándar de Django][django-translation].

Hacerlo te permitirá:

- Seleccionar un idioma distinto al inglés como predeterminado, usando la configuración estándar de Django `LANGUAGE_CODE`.
- Permitir que los clientes elijan un idioma ellos mismos, usando el `LocaleMiddleware` incluido con Django. Un uso típico para los clientes de API sería incluir una cabecera de solicitud `Accept-Language`.

## Habilitando APIs internacionalizadas

Puedes cambiar el idioma predeterminado usando la configuración estándar de Django `LANGUAGE_CODE`:

```python
LANGUAGE_CODE = "es-es"
```

Puedes activar las solicitudes de idioma por solicitud añadiendo `LocalMiddleware` a tu configuración `MIDDLEWARE`:

```python
MIDDLEWARE = [
    ...
    'django.middleware.locale.LocaleMiddleware'
]
```

Cuando la internacionalización por solicitud está activada, las solicitudes de los clientes respetarán la cabecera `Accept-Language` cuando sea posible. Por ejemplo, hagamos una solicitud para un tipo de medio no compatible:

**Solicitud**

```http
GET /api/users HTTP/1.1
Accept: application/xml
Accept-Language: es-es
Host: example.org
```

**Respuesta**

```http
HTTP/1.0 406 NOT ACCEPTABLE
```

```json
{
  "detail": "No se ha podido satisfacer la solicitud de cabecera de Accept."
}
```

REST framework incluye estas traducciones incorporadas tanto para casos de excepción estándar como para errores de validación de serializadores.

Ten en cuenta que las traducciones solo se aplican a las cadenas de error themselves. El formato de los mensajes de error y las claves de los nombres de campo permanecerán iguales. Un cuerpo de respuesta `400 Bad Request` de ejemplo podría verse así:

```json
{
  "detail": {
    "username": ["Este campo debe ser único."]
  }
}
```

Si quieres usar diferentes cadenas para partes de la respuesta como `detail` y `non_field_errors` entonces puedes modificar este comportamiento usando un [manejador de excepciones personalizado][custom-exception-handler].

#### Especificando el conjunto de idiomas admitidos.

Por defecto, todos los idiomas disponibles serán admitidos.

Si solo deseas admitir un subconjunto de los idiomas disponibles, usa la configuración estándar de Django `LANGUAGES`:

```python
LANGUAGES = [
    ('de', _('Alemán')),
    ('en', _('Inglés')),
]
```

## Agregando nuevas traducciones

Las traducciones de REST framework se gestionan en línea usando [Transifex][transifex-project]. Puedes usar el servicio Transifex para agregar nuevos idiomas de traducción. El equipo de mantenimiento luego se asegurará de que estas cadenas de traducción se incluyan en el paquete REST framework.

A veces puedes necesitar agregar cadenas de traducción a tu proyecto localmente. Puede que necesites hacer esto si:

- Quieres usar REST Framework en un idioma que aún no ha sido traducido en Transifex.
- Tu proyecto incluye mensajes de error personalizados, que no son parte de las cadenas de traducción predeterminadas de REST framework.

#### Traduciendo un nuevo idioma localmente

Esta guía asume que ya estás familiarizado con cómo traducir una aplicación Django. Si no lo estás, comienza leyendo [la documentación de traducción de Django][django-translation].

Si estás traduciendo un nuevo idioma, necesitarás traducir los mensajes de error existentes de REST framework:

1. Crea una nueva carpeta donde desees almacenar los recursos de internacionalización. Agrega esta ruta a tu configuración [`LOCALE_PATHS`][django-locale-paths].

2. Ahora crea una subcarpeta para el idioma que quieres traducir. La carpeta debe nombrarse usando la notación [nombre de locale][django-locale-name]. Por ejemplo: `de`, `pt_BR`, `es_AR`.

3. Ahora copia el [archivo de traducciones base][django-po-source] del código fuente de REST framework en tu carpeta de traducciones.

4. Edita el archivo `django.po` que acabas de copiar, traduciendo todos los mensajes de error.

5. Ejecuta `manage.py compilemessages -l pt_BR` para hacer que las traducciones estén disponibles para que Django las use. Deberías ver un mensaje como `processing file django.po in <...>/locale/pt_BR/LC_MESSAGES`.

6. Reinicia tu servidor de desarrollo para ver que los cambios surtan efecto.

Si solo estás traduciendo mensajes de error personalizados que existen dentro de tu base de código del proyecto, no necesitas copiar el archivo `django.po` fuente de REST framework en una carpeta `LOCALE_PATHS`, y en su lugar simplemente puedes ejecutar el proceso estándar `makemessages` de Django.

## Cómo se determina el idioma

Si quieres permitir preferencias de idioma por solicitud, necesitarás incluir `django.middleware.locale.LocaleMiddleware` en tu configuración `MIDDLEWARE`.

Puedes encontrar más información sobre cómo se determina la preferencia de idioma en la [documentación de Django][django-language-preference]. Como referencia, el método es:

1. Primero, busca el prefijo de idioma en la URL solicitada.
2. Si no lo encuentra, busca la clave `LANGUAGE_SESSION_KEY` en la sesión del usuario actual.
3. Si no la encuentra, busca una cookie.
4. Si no la encuentra, mira la cabecera HTTP `Accept-Language`.
5. Si no la encuentra, usa la configuración global `LANGUAGE_CODE`.

Para los clientes de API, el más apropiado de estos será típicamente usar la cabecera `Accept-Language`; las sesiones y las cookies no estarán disponibles a menos que uses autenticación de sesión, y generalmente es mejor práctica preferir una cabecera `Accept-Language` para clientes de API en lugar de usar prefijos de idioma en la URL.
